# 测试场景与排查题

> 独立模块：测试场景与排查题（中小厂面试杀手锏——场景题答好了直接过）
> 来源：字节/腾讯/百度面经真题、测试实战排查题。这类题没有标准答案，考的是排查链路的完整性。

## 一、线上问题排查（中小厂必考）

### 1. 用户反馈上传头像失败，怎么排查
- tags: 排查场景, 必考
- difficulty: medium
- frequency: 高频
- prompt: 用户反馈上传头像失败，你怎么分析？
- answer: 先定位影响面：一个人还是所有人（日志+监控）。单用户：让用户提供账号复现，查请求是否发出（抓包看是前端没发还是后端报错）、图片格式大小是否超限。全量用户：查服务是否发布变更（时间点对齐）、OSS/存储服务状态、接口错误率监控。口诀：先分影响面，再看变更，最后看依赖。切忌一上来就猜代码问题。

### 2. 10% 用户反馈功能用不了，怎么排查
- tags: 排查场景, 真题
- difficulty: hard
- frequency: 高频
- prompt: 10% 的用户反馈某功能用不了，你怎么排查？
- answer: 10% 是关键线索——大概率是灰度发布（新版本只放量一部分）或分库分表某台故障或运营商/地域网络问题。排查：①拿反馈用户的账号查版本号/所在集群；②对比能用和不能用的用户差异（版本、地域、机型）；③查灰度计划和发布记录时间点。这类题考的是对"部分用户故障"的敏感度：先找共性再定位。

### 3. APP 偶然闪退怎么排查
- tags: 移动端, 真题
- difficulty: hard
- frequency: 中高频
- prompt: APP 偶发闪退，复现不了，怎么排查？
- answer: 偶发问题不能靠复现，靠数据：①收集崩溃日志（Android: tombstone/ANR 日志、bugly 等崩溃平台拿堆栈）；②分析闪退用户的共性（机型/系统版本/内存状态/操作路径）；③内存型闪退看 OOM 和内存泄漏（反复进出页面后内存曲线）；④版本对比：新版本闪退率 vs 老版本。收尾句：偶发问题先上崩溃采集，靠聚合分析不靠碰运气复现。

### 4. 网页打开白屏/加载慢，怎么排查
- tags: Web, 真题
- difficulty: medium
- frequency: 高频
- prompt: 用户说网页打不开或很慢，你的排查链路？
- answer: 分层：①自己先访问验证（排除个例）；②F12/抓包看请求：DNS 解析、建连、TTFB（后端慢）还是资源加载慢（前端）——时间瀑布图直接分层；③后端慢：查接口响应时间、慢 SQL、服务负载；④资源慢：图片未压缩、无 CDN、JS 包过大；⑤网络层：curl -w 看各阶段耗时，ping/traceroute 看链路。加分：说出"用浏览器瀑布图把耗时归因到 DNS/建连/后端/前端"这个分界线。

### 5. 登录按钮点不动，怎么排查
- tags: 前端, 真题
- difficulty: medium
- frequency: 高频
- prompt: 登录按钮点了没反应，你从哪些层面排查？
- answer: 从 UI 到逻辑五层：①按钮是否被遮挡/禁用（F12 看 disabled 属性和元素层级）；②JS 是否报错（Console 看异常，事件监听可能没绑上）；③事件是否触发（Network 看请求发没发）；④请求发了但失败（看响应码和后端日志）；⑤接口正常但前端没处理返回。这题本质是"你懂不懂前后端交互链路"，按数据流向排查是标准答法。

### 6. 压测 QPS 上不去，怎么排查
- tags: 性能排查, 真题
- difficulty: hard
- frequency: 中高频
- prompt: 压测时 QPS 一直上不去，瓶颈在哪怎么找？
- answer: 逐层二分：①先看施压端是不是瓶颈（压测机 CPU/带宽/JMeter 线程数不够——最常被忽略）；②单接口压 vs 场景压定位是否锁竞争；③服务端：应用 CPU 没满但 QPS 不涨→线程池/连接池打满、锁竞争；④数据库：慢 SQL、连接池耗尽（看活跃连接数）；⑤下游依赖和限流配置。口诀：先排施压端，再看池子（线程/连接池），最后看 DB 和锁。

## 二、业务场景设计题（真题高频）

### 7. 购物车模块怎么测试
- tags: 用例设计, 真题
- difficulty: medium
- frequency: 高频
- prompt: 设计淘宝购物车模块的测试用例。
- answer: 分块答：①功能：加购/删除/修改数量/全选/移入收藏夹、跨店铺、商品失效处理；②边界：购物车数量上限（如 120 件）、数量输入边界（0/负数/超大数）、库存不足时数量提示；③一致性：加购后价格变动/优惠变化显示、库存被抢光后购物车状态、多端同步（App 和网页购物车一致）；④性能：双 11 高并发加购；⑤异常：断网加购、登录态过期。亮点在"多端一致性"和"库存联动"，能说出这两块就超过多数候选人。

### 8. 微信朋友圈评论功能怎么测试
- tags: 用例设计, 真题
- difficulty: medium
- frequency: 中高频
- prompt: 设计微信朋友圈评论功能的测试用例。
- answer: ①功能：评论/回复评论（两层结构）、删除评论、点赞评论的通知；②权限：仅好友可见的朋友圈、被屏蔽的人能否看到评论、共同好友才可见的回复规则（微信特有逻辑：非共同好友看不到彼此评论）；③边界：超长评论（上限截断）、emoji/表情、敏感词过滤；④并发：两人同时评论同一条、评论后立刻删朋友圈；⑤通知：评论推送准确性、免打扰。权限矩阵（谁能看到谁的评论）是这题的灵魂。

### 9. 支付功能怎么测试
- tags: 用例设计, 真题
- difficulty: hard
- frequency: 高频
- prompt: 设计支付流程的测试用例。
- answer: 六块：①金额：边界（0.01/最大额度）、精度（分）、优惠计算（满减/折扣叠加）、退款金额校验；②状态机：支付中/成功/失败/超时/退款各状态流转，重复支付拦截；③幂等与并发：同一订单重复点击支付、双开页面同时支付、支付回调重试（回调可能来多次！）；④异常：支付中途断网/杀 APP/切后台、余额不足、第三方渠道挂了（mock 降级）；⑤对账：支付流水和订单金额核对（落库校验）；⑥安全：篡改支付金额抓包重放。回调重试和状态机是这题的专业分水岭。

### 10. 直播功能怎么测试
- tags: 用例设计, 真题
- difficulty: hard
- frequency: 中高频
- prompt: 设计抖音直播功能的测试点。
- answer: ①主播端：开播/断网重连、美颜摄像头权限、推流质量（弱网降码率）；②观众端：进房延迟（秒开）、弹幕实时性、礼物特效、连麦互动；③互动并发：万人同时发弹幕（弹幕风暴）、高并发送礼（排行榜实时性）；④弱网专项：不同丢包率/延迟下的体验降级；⑤异常：主播闪断观众端提示、房间被关闭的广播。性能和实时性是直播测试的主角，功能反而是配角。

### 11. 自动售货机怎么测试
- tags: 用例设计, 经典
- difficulty: medium
- frequency: 中高频
- prompt: 对一台自动售货机进行测试用例设计。
- answer: 硬件+软件双线：①功能：投币/扫码支付、出货、找零、缺货提示；②硬件异常：卡货（出货口卡住——钱扣了货没出，退款逻辑）、纸币识别故障、断电（订单状态和钱怎么办）；③支付异常：支付成功但出货失败（自动退款）、断网时扫码（离线补单）；④边界：货道存量的最后一件、连买多件、假币/残币；⑤性能：高峰排队购买。这题考"实体+软件混合系统"的异常思维，卡货退款是必说点。

### 12. 手机消息推送怎么测试
- tags: 移动端, 真题
- difficulty: medium
- frequency: 中高频
- prompt: 测 APP 消息推送要考虑哪些点？
- answer: ①到达率：推送发出→设备收到→展示，各环节统计；②时机：APP 前台/后台/杀进程（杀进程后能否收到，iOS/安卓规则不同）、锁屏展示；③内容：标题长度截断、emoji、点击跳转正确页面（深链）；④设置联动：系统通知权限关闭、APP 内推送开关关闭、免打扰时段；⑤批量：全量推送的到达延迟、厂商通道（华为/小米推送通道差异）。杀进程场景和厂商通道差异是移动端测试的特色考点。

## 三、测试策略场景题（测开进阶）

### 13. 需求都没写全，时间又紧，你怎么保证质量
- tags: 策略, 必考
- difficulty: hard
- frequency: 高频
- prompt: 项目排期很紧，需求文档也不完善，你怎么保证测试质量？
- answer: 承认约束，给降级策略：①风险分级：核心资金/主流程用例优先，边缘功能放后甚至只做冒烟；②沟通前置：拉产品和开发对齐核心逻辑边界（没文档就口头确认并留记录）；③借力：核心链路自动化兜底回归，把人力留给探索性测试；④透明风险：测试报告里明确"未覆盖项+风险声明"，让项目知情决策。这题考的是质量与进度的权衡能力，答"我加班全测完"是学生思维。

### 14. 开发说没时间修你这个低优先级 bug，怎么办
- tags: 协作, 真题
- difficulty: medium
- frequency: 中高频
- prompt: 版本要发了，开发不想修你提的 bug，怎么处理？
- answer: 先判断：真低优先级（不影响主流程、有绕行方案）→接受延期进 bug 池跟踪，别死磕；影响主流程但开发没意识到→摆证据（复现步骤+影响面+用户路径），升级到测试经理和项目侧决策；有分歧→拉产品对齐需求预期。核心：测试的职责是暴露风险和量化影响，修不修、发不发是项目集体决策，我不越位也不隐瞒。

### 15. 从版本发布到线上验证，测试还要做什么
- tags: 流程, 中高频
- difficulty: medium
- frequency: 中高频
- prompt: 版本上线后测试的工作就结束了吗？
- answer: 没有，上线后半场同样重要：①线上冒烟：核心链路真机真账号验证（灰度阶段就介入）；②监控盯盘：错误率/告警/用户反馈群盯 24~48 小时；③灰度验证：按比例放量观察，异常即触发回滚预案（回滚方案上线前就要准备好）；④复盘：本版本漏测分析、用例补全、下版本改进项。回答完补一句：测试左移到需求、右移到线上，才是完整的质量闭环。

### 16. 怎么说服团队投入资源做自动化
- tags: 策略, 测开特色
- difficulty: hard
- frequency: 中高频
- prompt: 团队全是手工测试，你是测开，怎么推动自动化落地？
- answer: 用数据不喊口号：①算账：一轮回归 3 人天×每月 4 轮 = 全年成本，自动化一次性投入 N 天+维护成本， ROI 摆出来；②小步快跑：先挑最痛的一小块（如登录+下单冒烟 20 条），两周见效给老板看；③降低门槛：用例 YAML 化让功能同学也能写，不是只有你会；④自动化结果可视化：每轮回归报告自动推送，让大家看到价值。切忌一上来要做一个"大平台"，中小厂要先证明 ROI。

### 17. 你怎么评估测试排期
- tags: 管理, 真题
- difficulty: medium
- frequency: 中高频
- prompt: 领导让你评估这次测试要多久，你怎么估？
- answer: 三步：①拆解：按模块拆用例设计+执行+回归三段工作量；②系数：执行时间×1.5（bug 修复等待和返工）+预留 buffer（新需求变更、环境问题 20%）；③风险声明：依赖项（提测质量、环境就绪）提前说清，"提测延期一天我顺延一天"提前打预防针。加分：说你会用历史数据（上版本同类需求的实际耗时）校准估算，不是拍脑袋。

## 四、数据与 SQL 场景题（笔试高频）

### 18. 一个订单表，查每个用户最近一单
- tags: SQL, 真题
- difficulty: hard
- frequency: 高频
- prompt: orders 表（user_id, order_id, created_at），写 SQL 查每个用户最近的一笔订单。
- answer: 窗口函数：SELECT * FROM (SELECT *, ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY created_at DESC) rn FROM orders) t WHERE rn=1。老版本 MySQL 无窗口函数时用关联子查询：WHERE created_at = (SELECT MAX(created_at) FROM orders o2 WHERE o2.user_id=o1.user_id)。这题是测试岗 SQL 笔试出现率第一名。

### 19. 查询成绩排名（成绩表）
- tags: SQL, 真题
- difficulty: medium
- frequency: 高频
- prompt: scores 表（name, score），查出每个分数的排名（同分同名次）。
- answer: 三种：窗口函数 RANK()（同分同名次有空位）/DENSE_RANK()（同分同名次无空位）/ROW_NUMBER()（不并列）；老 MySQL：自关联数比它大的 distinct 分数个数+1。笔试常追问 RANK 和 DENSE_RANK 的区别：90,90,80 用 RANK 是 1,1,3，DENSE_RANK 是 1,1,2。

### 20. 统计接口调用日志中每个接口的失败率
- tags: SQL, 测试数据
- difficulty: medium
- frequency: 中高频
- prompt: api_logs 表（api, status），status=1 成功 0 失败，写 SQL 统计每个接口的失败率，降序。
- answer: SELECT api, ROUND(SUM(CASE WHEN status=0 THEN 1 ELSE 0 END)/COUNT(*)*100, 2) AS fail_rate FROM api_logs GROUP BY api ORDER BY fail_rate DESC。核心点：CASE WHEN 条件计数和聚合里做除法；这题在测试平台数据统计里天天用。
