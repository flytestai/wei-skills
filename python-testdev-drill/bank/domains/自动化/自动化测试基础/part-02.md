## Q002847

- 题型：简答
- 难度：中等

**题目**

```text
你项目中有多少case，通过率怎么样？
```

**答案**

```text
这个数量没有标准，可以按照自己项目功能用例乘以对应百分比来回答，比如功能用例1000个，自动化覆盖率60%，那么实际的自动化用例数量为600
一般而言，接口自动化用例实现的覆盖率会较高，UI自动化用例较低
比如接口80-90% UI 50-70%
```

**解析**

```text
【核心考点】 自动化测试覆盖率 测试用例管理
【题目解析】
本题考察面试者对自动化测试用例数量的估算能力和对通过率的理解。没有固定标准答案，关键在于展示对项目规模、测试策略和覆盖率目标的合理分析。回答时应结合项目实际情况，如功能用例总数、自动化覆盖目标（接口/UI）等，体现逻辑性和实战经验。
【参考答案要点】
1. 用例数量估算：基于项目功能用例总数乘以自动化覆盖率百分比。例如，功能用例1000个，接口自动化覆盖率80%，则接口自动化用例约800个；UI自动化覆盖率60%，则约600个。
2. 通过率说明：通过率通常指自动化用例执行通过的比例。接口自动化通过率较高（如90%以上），UI自动化因环境波动可能较低（如80%左右）。需说明失败原因（如环境问题、脚本维护等）。
3. 项目差异：不同项目规模、阶段和团队能力会影响具体数字，强调根据实际情况调整。
【面试角度】
面试官期望听到具体项目数据和覆盖率计算逻辑，而非空泛数字。建议举例说明如何根据测试策略确定覆盖率目标，以及如何跟踪通过率并优化脚本。
【易错提示】
避免给出绝对数字（如“1000个用例”），应强调估算依据。同时注意区分接口和UI自动化的覆盖率差异，这是常见考察点。
```

## Q002848

- 题型：简答
- 难度：中等

**题目**

```text
使用QTP(或其他自动测试工具)做功能测试，录制脚本的时候，要验证多个用户的登录情况，如何操作?
```

**答案**

```text
参数化用户名，使用csv记录user1、user2、user3...密码均为123456，然后将csv表格参数化替换${user}
```

**解析**

```text
【核心考点】 参数化测试 数据驱动 QTP/UFT
【题目解析】
本题考查自动化测试中参数化技术的应用，特别是多用户登录场景的测试数据驱动方法。通过参数化，可以用同一脚本执行多组数据，避免重复录制。
【参考答案要点】
1. 准备数据源：创建CSV或Excel文件，记录多组用户名（如user1, user2, user3）和密码（如123456）。
2. 参数化替换：在QTP/UFT中，将录制脚本中的用户名输入框的值替换为参数，数据源指向CSV文件，实现循环读取。
3. 执行验证：脚本运行时自动遍历数据行，完成多用户登录测试，并可在每轮迭代中添加断言验证登录结果。
【面试角度】
回答时若能提及其他工具的参数化方式（如Selenium的DataProvider、JMeter的CSV Data Set Config），并说明参数化对测试覆盖率和维护成本的影响，会显得知识面更广。
【易错提示】
常见误区：只录制一个用户登录，然后手动修改脚本重复执行，未使用参数化。面试中应强调数据驱动测试的思想，展示对自动化测试最佳实践的理解。
```

```text
2. 时间进度

7. 工程的管理后期的维护。
```

**解析**

```text
【核心考点】 自动化测试规划 测试策略

本题考查自动化测试的规划能力，面试官期望候选人从全局视角阐述自动化测试的引入和实施步骤。回答应涵盖技术选型、资源评估、流程设计、数据管理和维护策略等关键维度。

【易错提示】
避免只谈技术选型而忽略流程和管理，面试官更看重系统性思维。同时注意不要遗漏数据驱动和持续集成等关键点。
```

```text

【题目解析】
```

```text
哪些场景不适合做自动化测试？
```

```text
一、需求不稳定，频繁变更
二、研发和维护周期短
三、很难在多平台重复执行
四、自动化成本太高
五、流程不规范
```

**解析**

```text
【核心考点】 自动化测试 适用场景

【参考答案要点】
1. 需求不稳定，频繁变更：自动化脚本维护成本高，难以跟上变化。2. 研发和维护周期短：自动化开发时间不足，收益低。3. 很难在多平台重复执行：环境差异导致脚本失效。4. 自动化成本太高：投入资源超过手动测试。5. 流程不规范：缺乏标准流程，自动化难以落地。

注意区分不适合自动化与不适合手动测试，自动化更适合重复性高、稳定的场景。
```

## Q002867

- 题型：简答
- 难度：中等

**题目**

```text
哪些测试用例需要自动化测试？
```

```text
1、需要针对应用程序的每个构建/发布运行的测试，如冒烟测试，、健全测试和回归测试
2、需要在多个配置下运行的测试，如不同的操作系统和浏览器的组合
3、执行相同工作流但每次测试运行的输入数据不同的测试，例如数据驱动测试
4、涉及输入大量数据的测试，例如需要填写非常长的表单的测试
5、执行时间较长的测试，比如可能需要在休息或夜间运行的测试
6、手工测试无法实现的
```

**解析**

```text
【核心考点】 自动化测试 测试用例选择
【参考答案要点】
1. 重复性高的测试：如冒烟测试、健全测试、回归测试，每次构建/发布都需要执行。
2. 多配置测试：需要在不同操作系统、浏览器等组合下运行的测试。
3. 数据驱动测试：相同工作流但输入数据不同的测试，如参数化测试。

5. 长时间测试：执行时间较长的测试，如夜间运行的稳定性测试。
6. 手工难以实现的测试：如并发测试、压力测试等。
【面试角度】
回答时建议补充自动化投入产出比的考量，例如“对于高频回归的用例，自动化收益高；对于一次性或易变动的用例，手工更合适”。
```

## Q002869

- 题型：简答
- 难度：中等

**题目**

```text
在python中进行数据驱动测试
```

**答案**

```text
在unittest中，没有自带的数据驱动，我们得借助ddt来实现，
首先，我们得在python运行环境中安装ddt，用下列命令安装
pip install ddt
另外一个测试框架pytest，它自带数据驱动实现，是通过@pytest.mark.parametrize(argnames,argvalues) 来实现参数化的。
也可以根据自己需求用python实现数据的读取和驱动。
```

**解析**

```text
【核心考点】 数据驱动测试 unittest pytest
【参考答案要点】
1. unittest 框架：本身不内置数据驱动支持，需借助第三方库 ddt（Data-Driven Tests）。安装命令：pip install ddt，通过 @ddt 和 @data 装饰器实现参数化。
2. pytest 框架：原生支持数据驱动，使用 @pytest.mark.parametrize(argnames, argvalues) 装饰器，可传入列表、元组或函数返回值作为参数。
3. 自定义实现：可读取 Excel、CSV、JSON 等外部数据文件，结合循环或生成器动态生成测试用例。
【面试角度】
回答时建议结合实际项目中的数据驱动应用场景，例如“在接口测试中，我们将测试数据存储在 Excel 中，通过 ddt 实现多组参数验证”，能体现工程化思维。
【延伸知识】
数据驱动测试的核心是分离测试逻辑与测试数据，提高用例复用率。在 pytest 中，还可使用 pytest_generate_tests 钩子实现更灵活的参数化。
```

```text
4.精简测试用例和测试场景：测试用例和测试场景应该尽可能精简，不要重复测试同一个功能，避免无效的测试和冗余的测试，这样可以减少测试脚本的数量和复杂度，降低维护成本.
```

```text
持续集成（CI）和持续交付（CD）与自动化测试关系？
```

```text
【核心考点】 持续集成 持续交付 自动化测试
```

## Q002909

- 题型：简答
- 难度：中等

**题目**

```text
数据驱动框架和关键字驱动框架的基本区别是什么？
```

**答案**

```text
数据驱动框架
数据和用例步骤分离，通过excel、yaml等文件或数据库保存数据。数据驱动是把测试用例里面的数据提取到excel或者yam文件里面，然后通过改变excel或yaml中的数据驱动测试用例执行。
关键字驱动框架
测试用例的步骤(元素)和用例分离。关键字驱动表示把项目中的一些逻辑封装成关键字(一个函数名)。例如login、 register、order进行设置变量，调用不同的关键字组合实现不同的业务逻辑，从而驱动测试用例执行。
```

**解析**

```text
【核心考点】 自动化测试框架 数据驱动 关键字驱动
【参考答案要点】
数据驱动框架：将测试数据（如输入值、预期结果）从测试脚本中分离，存储在外部文件（如Excel、YAML、CSV）或数据库中。测试脚本通过读取数据驱动执行，同一脚本可复用多组数据，实现参数化测试。
关键字驱动框架：将测试步骤（如点击、输入、验证）抽象为关键字（函数名），测试用例由关键字序列组成。关键字封装了底层操作逻辑，测试人员通过组合关键字描述业务场景，无需关心实现细节。
主要区别：
1. 分离内容不同：数据驱动分离的是数据；关键字驱动分离的是操作步骤。
2. 抽象层次不同：数据驱动关注数据变化；关键字驱动关注业务逻辑封装。
3. 适用场景：数据驱动适合参数化测试；关键字驱动适合业务复杂、需多人协作的自动化项目。
【面试角度】
面试中常问两者如何结合使用，可回答：在实际项目中，常采用混合驱动框架，即关键字驱动结合数据驱动，既分离数据又封装操作，提升可维护性。
【易错提示】
不要混淆“数据驱动”与“参数化”，参数化是数据驱动的一种实现方式，但数据驱动更强调数据与脚本的完全分离。
```

```text
有误报过，有时候自动化测试报告中显示发现了bug,实际去通过手工测试去确认又不存在该bug。
误报原因一般是：

```

```text
【核心考点】 自动化测试 误报处理 脚本稳定性
【题目解析】
本题考察自动化测试中误报（false positive）的识别与处理。误报是指自动化测试报告了缺陷，但实际手工验证发现并不存在。这是自动化测试中常见问题，影响测试效率。
【参考答案要点】
1. 误报原因：
- 元素定位不稳定：如使用不稳定的XPath或CSS选择器，导致元素未找到或误判。
- 页面加载延迟：脚本执行过快，元素尚未渲染完成。

2. 处理方法：
- 增加等待机制：使用显式等待（如WebDriverWait）确保元素可交互。
- 优化定位策略：使用更稳定的属性（如id、data-testid）定位元素。
- 定期维护脚本：与开发同步，及时更新脚本以适应页面变化。
- 增加重试机制：对不稳定用例设置重试次数。
- 人工确认：对自动化报告的缺陷进行手工验证，减少误报影响。
【易错提示】
不要忽视误报，长期误报会导致团队对自动化测试失去信任。建议建立误报跟踪机制，定期分析并优化脚本。
【面试角度】
面试官可能要求举例说明实际项目中遇到的误报案例及解决方案，建议准备具体场景，如“某次因异步加载导致元素定位失败，通过添加显式等待解决”。
```

```text
是否遇到过误报：是的，常见。
产生误报的原因：
1. 元素定位不稳定：如使用XPath或CSS选择器时，页面结构变化导致定位失败。
2. 环境或数据问题：测试数据未准备好，或环境配置不一致。
3. 脚本未及时更新：开发修改了页面，但测试脚本未同步维护。
4. 等待机制不足：页面加载或异步请求未完成时即执行操作。
处理误报的方法：
1. 分析日志和截图：查看失败时的截图和日志，确认是否为真实缺陷。
2. 提高脚本稳定性：使用更稳定的定位方式（如ID），增加显式等待。
3. 定期维护脚本：与开发沟通页面变更，及时更新脚本。
4. 区分误报和真实缺陷：对误报进行标记，避免干扰缺陷统计。
【面试角度】
面试官期望看到实际项目经验，例如“在我们项目中，曾因Ajax请求延迟导致误报，后来通过添加显式等待解决”。这能体现解决问题的能力。
【易错提示】
不要简单回答“没有误报”，这显得缺乏经验。误报是自动化测试的常态，关键在于如何识别和减少。
```

```text
说一说PageObject
```

**答案**

```text
PageObject 见名知意，就是页面对象。说白就是把页面元素定位和页面元素操作分开。
PageObject在实战过程中我们会对脚本实现进行分层。
通常做法是分三层：
1、对象库层
2、逻辑层
3、业务层
```

**解析**

```text
【核心考点】 PageObject模式 自动化测试设计模式
【题目解析】
本题考查对PageObject（PO）设计模式的理解。PO模式是UI自动化测试中常用的设计模式，核心思想是将页面元素定位与操作逻辑分离，通过分层提高脚本的可维护性和可读性。回答需要清晰阐述PO的基本概念、分层结构（对象库层、逻辑层、业务层）以及各层职责。
【参考答案要点】
1. 概念：PageObject即页面对象，将每个页面封装为一个类，页面元素和操作方法封装在类中，实现页面元素定位与操作逻辑的分离。
2. 分层结构：通常分为三层：
- 对象库层：定义页面元素定位表达式（如By.id、By.xpath），不包含操作逻辑。
- 逻辑层：封装页面操作（如点击、输入），调用对象库层的元素定位。
- 业务层：组合逻辑层方法，实现业务场景（如登录、下单），供测试用例调用。
3. 优点：提高脚本复用性、降低维护成本、增强可读性。
【面试角度】
回答时建议结合实际项目案例说明PO的应用，例如“在电商项目中，我们将商品详情页封装为PO类，对象库层定义元素定位，逻辑层封装点击加入购物车等操作，业务层组合成下单流程”。同时可补充PO的封装原则（如不暴露页面内部、不做断言），以展示深度。
【易错提示】
常见错误是只描述概念而忽略分层细节，或混淆PO与关键字驱动模式。务必强调分层思想和各层职责。
```

## Q002980

- 题型：简答
- 难度：中等

**题目**

```text
谈谈你对自动化测试中关键字驱动模式理解。
```

**答案**

```text
关键字驱动测试也被称为表格驱动测试或者基于动作字的测试。
关键字驱动的框架的基本工作是将测试用例分成四个不同的部分。
首先是测试步骤（Test Step），二是测试步骤中的对象（Test Object），三是测试对象执行的动作(Action)，四是测试对象需要的数据（Test Data），
我们可以把关键字和需要执行的测试内容映射起来，当使用关键字时、执行对应的动作。
关键字的驱动的思想，可以把编码从测试用例和测试步骤中分离出来，这样对于不会编码的人员更容易理解自动化，从而让手工测试人员也可以编写自动脚本。
```

**解析**

```text
【核心考点】 关键字驱动测试 自动化测试框架
【题目解析】
本题考查对关键字驱动测试模式的理解，这是自动化测试中一种重要的框架设计思想。关键字驱动将测试用例抽象为关键字序列，每个关键字对应一个操作（如点击、输入），使得非技术人员也能编写和维护自动化脚本。其核心优势在于将测试逻辑与底层代码解耦，提升可维护性和可扩展性。
【参考答案要点】
1. 核心概念：关键字驱动（Keyword-Driven Testing）是一种自动化测试框架，通过预定义的关键字（如“点击”、“输入文本”）来描述测试步骤，每个关键字对应一个具体的操作函数。
2. 框架组成：通常包括关键字库、测试数据文件（如Excel、CSV）、测试执行引擎和报告模块。关键字库封装了底层操作，测试数据文件定义了测试用例的步骤和数据。
3. 优点：降低自动化门槛，手工测试人员可通过编写关键字序列参与自动化；提高复用性，关键字可在多个用例中重复使用；便于维护，当UI变化时只需更新关键字实现，无需修改所有用例。
4. 与数据驱动的关系：关键字驱动是数据驱动的扩展，数据驱动仅分离测试数据，而关键字驱动进一步分离了操作步骤。
【面试角度】
面试中，建议结合实际项目经验说明关键字驱动的应用场景，例如“在Web自动化测试中，我们使用Selenium结合关键字驱动框架，将登录、搜索等操作封装为关键字，测试人员只需在Excel中填写关键字和数据即可执行测试”。同时，可以对比其他框架（如数据驱动、行为驱动开发）的优缺点，展示对自动化测试体系的全面理解。
【易错提示】
关键字驱动与数据驱动容易混淆，注意区分：数据驱动侧重于测试数据的参数化，而关键字驱动侧重于测试步骤的抽象和复用。两者常结合使用，但概念不同。
```

## Q002725

- 题型：简答
- 难度：较难

**题目**

```text
QTP中的RO和TO的区别？
```

**答案**

```text
TO是Test Object（测试对象）的简称，RO是Runtime Object（运行时对象）简称，既用来区分仓库对象和实际对象，又用来区分对象的封装接口和自身接口。

从实际作用上来看，应该说TO就是是仓库文件里定义的仓库对象，RO是被测试软件的实际对象。换句话说，TO就是封装了的RO，QTP就是通过TO来操作RO。
QTP为用户提供了两种操作对象的接口，一种就是对象的封装接口（TO），另一种是对象的自身接口（RO）。对象的自身接口是对象控件本身的接口，对象的封装接口是QTP为对象封装的另一层接口，它是QTP通过调用对象的自身接口来实现的。
```

**解析**

```text
【核心考点】 QTP/UFT 对象识别 TO与RO
【题目解析】
本题考查QTP（现UFT）中测试对象（TO）和运行时对象（RO）的区别。这是自动化测试框架的核心概念，理解两者关系有助于编写稳定的测试脚本。
【参考答案要点】
TO（Test Object）：仓库中定义的封装对象，是QTP对实际控件的抽象，包含属性集合和操作方法。TO通过对象仓库管理，用于识别和操作控件。
RO（Runtime Object）：应用程序运行时的实际控件对象，具有控件的原生属性和方法。RO是TO的底层实现，QTP通过TO调用RO的接口。
区别：TO是静态定义，RO是动态实例；TO提供封装接口（如Click），RO提供自身接口（如GetROProperty）。
【面试角度】
面试官可能追问“如何获取RO的属性”，回答：使用GetROProperty方法获取运行时属性，如Browser().Page().WebEdit().GetROProperty("value")。同时，理解对象仓库的维护策略也很重要。
【易错提示】
常见错误是混淆TO和RO，认为TO直接操作控件。实际上，TO是代理，所有操作最终通过RO执行。面试中能清晰解释封装层次会加分。
```

## Q002788

```text
什么是数据驱动框架？它与关键字驱动框架有什么不同？
```

```text
数据驱动框架：
在这个框架中，测试用例逻辑驻留在测试脚本中。测试数据被分离并保存在测试脚本之外。测试数据是从外部文件（Excel文件）中读取的，并被加载到测试脚本中的变量中。变量用于输入值和验证值。

关键字驱动：
关键字/表驱动框架需要开发数据表和关键字。它们独立于执行它们的测试自动化工具。可以使用或不使用应用程序来设计测试。在关键字驱动的测试中，被测试的应用程序的功能记录在一个表格中，以及每个测试的分步说明。
```

**解析**

```text
【核心考点】 自动化测试框架 数据驱动 关键字驱动
【题目解析】
本题考查自动化测试框架设计中的两种常见模式：数据驱动和关键字驱动。两者都旨在提高测试用例的可维护性和复用性，但实现方式和抽象层次不同。理解它们的区别是面试中评估候选人框架设计能力的重要指标。
【参考答案要点】
数据驱动框架：测试用例逻辑驻留在测试脚本中，测试数据被分离并保存在外部文件（如Excel）中。测试数据被加载到脚本中的变量中，用于输入值和验证值。核心是“数据与脚本分离”。
关键字驱动框架：需要开发数据表和关键字，独立于测试自动化工具。测试设计可以脱离应用程序进行。被测试应用程序的功能记录在表格中，以及每个测试的分步说明。核心是“操作与数据分离，且操作被抽象为关键字”。

【延伸知识】
混合驱动框架结合了数据驱动和关键字驱动的优点，是大型项目的常见选择。此外，行为驱动开发（BDD）如Cucumber，与关键字驱动有相似之处，但更强调业务语言。
```

```text
自动化测试并非万能，对于探索性测试、UI频繁变动的项目，手工测试可能更高效。面试中也可讨论自动化测试金字塔（单元测试>接口测试>UI测试）的适用场景。
```

```text
2、页面对象层pages，管理所有的页面对象
3、测试用例层testcases，用来管理所有的测试用例
4、工具层util，封装一些常用工具方法，比如读取Excel、properities等配置文件，一些随机数生成工具方法

```

```text

【题目解析】
本题考察自动化测试框架的设计能力。一个成熟的自动化测试框架通常采用分层设计和Page Object（PO）模式，以提高代码复用性、可维护性和可扩展性。典型分层包括：基础封装层（common）：封装页面公用方法（如BasePage）和测试用例通用方法（如BaseTest）；页面对象层（pages）：管理所有页面对象，每个页面一个类，封装页面元素和操作；测试用例层（testcases）：编写测试用例，调用页面对象方法；工具层（util）：封装常用工具方法，如读取配置文件、生成随机数、日志处理等。此外，还可集成日志模块（如Log4j）、报告模块（如Allure）、失败重试机制、截图功能等，并集成到CI/CD流水线中。
```

## Q002836

- 题型：简答
- 难度：较难

**题目**

```text
你的自动化测试用例的执行策略是什么
```

**答案**

```text
自动化测试用例的执行策略是要看自动化测试的目的，通常有如下几种策略：
1、自动化测试用例是用来监控的，在此目的下，我们就把自动化测试用例设置成定时执行的，比如每五分钟或是一个小时执行一次，在 Jenkins 上创建一个定时任务即可。
2、必须回归的用例，有些测试用例在产品变动上线之前都需要回归执行，那我们就把测试用例设置成触发式执行，在 Jenkins 上将我们的自动化测试任务绑定到开发的build任务上，当开发人员在测试环境上部署代码的时候，我们的自动化测试用例就会被触发执行。
3、不需要经常执行的测试用例，像全量测试用例，我们没有必要一直回归执行，必竟还是有时间消耗的，有些非主要业务线也不需要时时回归，这类测试用例我们就采用人工执行，在 Jenkins 上创建一个任务，需要执行的时候人工去构建即可。
```

**解析**

```text
【核心考点】 自动化测试策略 CI/CD集成 测试执行管理
【参考答案要点】
1. 监控型用例：设置定时执行（如每5分钟或1小时），在Jenkins上创建定时任务，持续监控系统稳定性。
2. 回归型用例：设置触发式执行，绑定到开发部署任务，当代码变更时自动触发回归测试。
3. 全量用例：按需执行，如版本发布前或特定周期执行，避免频繁运行消耗资源。
【面试角度】
建议结合实际项目经验阐述，例如“在项目中，我们将冒烟测试用例设置为触发式，确保每次部署后核心功能正常”，并提及工具（如Jenkins、GitLab CI）和优化策略（如用例分级、并行执行）。
【延伸知识】
自动化测试执行策略需考虑测试环境稳定性、用例维护成本和反馈时效性。高级策略包括基于风险分析的用例选择、失败用例自动重试等。
```

## Q002852

- 题型：简答
- 难度：较难

**题目**

```text
做自动化测试时关注哪些指标？
```

**答案**

```text
1、自动化测试用例的覆盖率=自动化测试用例数/所用用例总数，这个比例越高测试反馈越快，成本节约越多
2、节省的时间成本=手工测试所花的时间-自动化测试所花的时间
3、自动化测试的投入=开发脚本的投入+脚本维护的投入+工具价格
4、自动化测试发现的缺陷数，每次回归测试时自动化测试发现的缺陷数及漏测数，反应了自动化用例的有效性
5、自动化测试投入产出比
ROI=（手工测试的成本-自动化测试成本）/自动化测试成本
ROI如果是负值说明自动化测试的成本未收回，ROI为正值说明自动化测试成本已回收，且值越大说明回报越好。
```

**解析**

```text
【核心考点】 自动化测试 测试指标 ROI
【参考答案要点】
1. 自动化测试覆盖率：自动化用例数 / 总用例数，比例越高，反馈越快，成本节约越多。
2. 节省的时间成本：手工测试时间 - 自动化测试时间，衡量效率提升。
3. 自动化测试投入：脚本开发成本 + 脚本维护成本 + 工具费用。
4. 缺陷发现数：每次回归测试中自动化发现的缺陷数及漏测数，反映用例有效性。
5. 投入产出比（ROI）：（手工测试成本 - 自动化测试成本）/ 自动化测试成本。ROI为正值表示成本回收，值越大回报越好。
```

```text
升环境稳定性。

d. 脚本的异常处理，在脚本中要多考虑可能出现的异常，尽量对每种异常都有对应的
处理方法，避免失败后程序退出
```

## Q002937

- 题型：简答
- 难度：较难

**题目**

```text
自动化测试工具QTP的原理，检查点的设置
```

**答案**

```text
1、QTP的工作原理
测试对象是QTP在测试或组件中创建的用于表示应用程序中的实际对象的对象，并且QuickTest在对象库中存储有关该对象的信息，包括对象的属性、操作等。录制的时候，QTP将操作过的所有对象都记录下来，保存在对象库Object repository中，记录的形式是一个逻辑名加上若干识别属性。因此，一个完整的脚本测试应该包括两部分：一个是测试脚本的代码，一个是对象库。

2、QTP识别对象的原理
QTP里的对象有两个概念，一个是Test Object(TO)，一个是Runtime Object(RO)
TO： 就是仓库文件里定义的仓库对象
RO：是被测试软件的实际对象

QTP识别对象，一般是要求先在对象仓库文件里定义仓库对象，里面存有实际对象的特征属性的值，
然后在运行的时候，QTP会根据脚本里的对象名，在对象仓库里找到对应的对象，接着根据对象的特征属性描述在被测试软件里搜索找到相匹配的实际对象，最后就可以实际对象进行操作了。

仓库对象TO一般在建制/编写脚本时加入仓库库文件它不仅可以在建制编写时进行修改，也可以在运行过和中动态修改，以匹配实际对象。
```

**解析**

```text
【核心考点】 QTP原理 检查点设置 自动化测试
【参考答案要点】
1. QTP工作原理：QTP通过对象识别和模拟用户操作实现自动化。录制时，QTP将操作过的对象及其属性记录到对象库（Object Repository）中，生成测试脚本。回放时，QTP根据对象库中的对象描述，在应用程序中查找匹配的对象，并执行相应操作。脚本由测试代码和对象库两部分组成。
2. 对象识别原理：QTP中有Test Object（TO）和Runtime Object（RO）两个概念。TO是对象库中定义的对象，RO是实际运行时的对象。QTP通过TO的识别属性（如name、class等）在应用程序中定位RO，若匹配成功则执行操作。
3. 检查点设置：检查点用于验证应用程序的特定属性或状态。QTP提供多种检查点，如标准检查点（验证对象属性）、文本检查点（验证文本内容）、表格检查点（验证表格数据）等。设置检查点时，需指定检查对象、属性和预期值，回放时QTP会比对实际值与预期值，并报告结果。
【面试角度】
回答时，建议结合实际项目经验说明QTP的应用场景，例如“在Web测试中，我们使用标准检查点验证页面元素”，并提及对象库维护的挑战，体现深度。
【延伸知识】
QTP已被UFT（Unified Functional Testing）取代，但原理相似。了解对象识别机制（如Smart Identification）和检查点类型有助于应对高级面试问题。
```

```text
测试可以从接口开发阶段介入接口自动化，可以在回归测试阶段介入接口和Ui自动化。
公司使用jenkins做自动化定时编译打包，自动化部署，自动化测试执行。
```

**解析**

```text
【核心考点】 持续交付 自动化测试 CI/CD工具
【参考答案要点】
1. 持续交付理解：开发人员在主干或短生命周期特性分支上小批量工作，定期合并，保持主干始终可发布状态，实现一键式发布。一旦引入回归错误（缺陷、性能、安全、可用性问题等），能快速反馈并立即修复。
```

```text
选择手动和自动化测试，为了作出一个合理的决定，需要做哪些方面假设？（7个）
```

```text
6.测试已经设计好之后，再决定是否进行自动化测试。
```

```text
【核心考点】 自动化测试 手动测试 测试策略

本题考查选择手动或自动化测试时的决策前提，属于测试策略的高级概念。题目要求列出7个假设，这些假设是合理决策的基础，涉及技术、资源、时间等多方面。
```
