## Q005741

- 题型：简答
- 难度：简单

**题目**

```text
多核的服务器，查看进程的CPU使用率，怎么会超过100%
```

**答案**

```text
进程列表中，显示的每个进程使用的CPU，当使用超过1个核的CPU时，就会出现超过100%，这在多核CPU的机器中是很正常的。
```

**解析**

```text
【核心考点】 系统监控 CPU使用率
【参考答案要点】
在多核CPU服务器中，进程的CPU使用率可能超过100%，因为CPU使用率是按单个核的百分比计算的。例如，一个进程使用2个核各50%，则显示为100%；若使用4个核各50%，则显示为200%。这是正常现象，表示进程利用了多个核心并行处理。
【面试角度】
本题考察对多核CPU监控指标的理解。回答时需解释计算方式，并指出在性能测试中，应关注总CPU使用率而非单个进程值。建议补充工具如 top 或 htop 的显示逻辑，体现实践能力。
【易错提示】
不要误认为CPU使用率超过100%是错误或异常，这是多核系统的正常行为。面试中可能追问如何计算总CPU利用率，需准备相关公式。
```

## Q005767

- 题型：简答
- 难度：简单

**题目**

```text
有个程序，发现在windows上运行很慢，怎么判别是程序存在问题还是软硬件系统存在问题？
```

**答案**

```text
把程序在B Windows电脑上运行，看是否慢？--->如果都运行的慢，判定不是电脑问题 ，是程序问题；如果运行的快，那就是电脑问题。
```

**解析**

```text
【核心考点】 问题定位 环境对比测试
【题目解析】
本题考察环境隔离法定位性能问题。通过控制变量，将程序运行在不同环境（如另一台Windows电脑）中，观察表现是否一致，从而区分是程序本身问题还是软硬件环境问题。
【参考答案要点】
1. 对比测试：将程序在另一台配置相近的Windows电脑上运行，观察速度。
2. 结果分析：
— 如果两台电脑都慢，则问题在程序本身（如代码效率、资源占用）。
— 如果仅原电脑慢，则问题在软硬件环境（如系统配置、后台进程、驱动等）。
【面试角度】
回答时可补充更系统的排查步骤，如检查CPU/内存占用、使用性能分析工具等，展示问题解决能力。
【易错提示】
避免直接下结论，需强调对比实验的科学性，这是面试官看重的逻辑思维。
```

```text
31接口测试过程中发现哪些对系统的性能问题
```

```text
1、数据量到了10万以上，查询如果不分页会很慢
2、导出数据量到10万以上，如果不用多线程导出会导致前端超时报错
```

**解析**

```text

接口性能测试还应关注并发用户数、吞吐量、错误率等指标。建议使用JMeter或LoadRunner进行压力测试，提前发现性能瓶颈。
```

## Q005719

- 题型：简答
- 难度：中等

**题目**

```text
vmstat中in、cs字段值很大会引起哪个资源消耗很高？
```

**答案**

```text
in 和cs 是system的数值项，这些项体现的是系统CPU使用的情况，所以，会导致CPU资源使用率高
```

**解析**

```text
【核心考点】 系统性能监控 vmstat
【题目解析】
本题考查vmstat命令中in（中断数）和cs（上下文切换数）字段的含义。这两个字段值高通常表示CPU资源消耗高，因为中断处理和上下文切换都需要CPU参与。
【参考答案要点】
1. in（interrupts）：每秒中断次数，包括硬件中断和软件中断。高in值表示设备或系统频繁请求CPU处理中断。
2. cs（context switches）：每秒上下文切换次数。高cs值表示进程或线程频繁切换，增加CPU开销。
3. 影响：两者都会导致CPU使用率升高，因为CPU需要处理中断和切换任务，降低系统吞吐量。
【面试角度】
面试中常问如何排查CPU高问题，建议回答：使用vmstat观察in和cs字段，结合top命令定位具体进程，再分析中断源或线程切换原因。
【易错提示】
不要混淆in和cs，in关注中断，cs关注切换，但两者都消耗CPU资源，面试中可能考查区分。
```

## Q005720

- 题型：简答
- 难度：中等

**题目**

```text
一个标准的性能调优过程是是什么？
```

**答案**

```text
（1）确定基准环境、基准负载和基准性能指标；
（2）调整系统运行环境和实现方法，执行测试。（包括硬件环境的调优、Weblogic调优、Oracle调优）；
（3）记录测试结果、进行分析。
```

**解析**

```text
【核心考点】 性能测试 性能调优
【题目解析】
本题考查性能调优的基本流程，属于中等难度。性能调优是一个迭代过程，通常包括：基准测试、瓶颈分析、调整优化、验证测试。回答时需要体现系统性思维，而非单一操作。
【参考答案要点】
1. 确定基准环境、基准负载和基准性能指标：在稳定环境下，使用典型负载运行，记录初始性能数据（如响应时间、吞吐量、资源利用率），作为后续优化的对比基线。
2. 调整系统运行环境和实现方法，执行测试：针对瓶颈进行调优，包括硬件环境（如CPU、内存、磁盘IO）、中间件（如Weblogic、Tomcat参数调优）、数据库（如SQL优化、索引调整）等，每次只改变一个变量，并重新测试。
3. 记录测试结果、进行分析：对比调优前后的性能数据，评估优化效果，若未达到目标则继续迭代。最终输出调优报告，总结优化措施和效果。
【面试角度】
回答时建议结合实际项目经验，例如“在某电商项目中，我们通过调整JVM堆大小和数据库连接池，将响应时间从3秒降低到1.2秒”，能体现实践能力。
【延伸知识】
性能调优常用工具：JMeter/LoadRunner（负载生成）、JProfiler/VisualVM（Java性能分析）、top/htop（系统资源监控）。调优原则：先定位瓶颈，再针对性优化，避免盲目调整。
```

## Q005721

- 题型：简答
- 难度：中等

**题目**

```text
一个进程的CPU消耗超过150%正常吗
```

**答案**

```text
是可能出现的，现在服务器一般都是多核，是会出现一个进程使用超过1个核的CPU
```

**解析**

```text
【核心考点】 性能测试 CPU使用率 多核系统
【题目解析】
本题考察对CPU使用率指标的理解。在单核系统中，CPU使用率上限为100%；但在多核系统中，一个进程可同时使用多个核心，因此CPU使用率可超过100%（如4核系统，单进程可达到400%）。
【参考答案要点】
正常。现代服务器多为多核CPU，操作系统将进程分配到多个核心并行执行。例如，一个进程使用2个核心的100%算力，则CPU使用率显示为200%。这是多线程/多进程应用的常见现象。
【易错提示】
面试中常混淆“进程CPU使用率”与“系统CPU使用率”。系统总CPU使用率不会超过100%（按所有核心平均），但单个进程可超过100%。
```

## Q005724

- 题型：简答
- 难度：中等

**题目**

```text
你会从哪些方面判断CPU资源消耗是否有问题？
```

**答案**

```text
CPU的总使用率
系统的平均负载load average
CPU每秒的中断数量
CPU每秒的上下文切换数量
CPU的缓存命中率
```

**解析**

```text
【核心考点】 性能测试 CPU监控
【题目解析】
本题考查性能测试中CPU资源消耗的监控指标。CPU问题不仅体现在使用率上，还包括上下文切换、中断、缓存命中率等，需全面分析。
【参考答案要点】
1. CPU总使用率：过高（如>80%）可能表示CPU瓶颈，需区分用户态、系统态、I/O等待等。
2. 系统平均负载（load average）：反映CPU任务队列长度，若远高于CPU核数，说明系统过载。
3. CPU每秒中断数量：过高可能由硬件或驱动问题引起，导致CPU频繁响应。
4. CPU每秒上下文切换数量：频繁切换（如>10000次/秒）可能因线程过多或锁竞争，降低性能。
5. CPU缓存命中率：命中率低会导致内存访问延迟，影响整体性能。
【面试角度】
回答时建议结合实际项目中的监控工具（如top、vmstat、perf）举例，例如“在压测中通过vmstat发现上下文切换过高，优化后吞吐量提升20%”。
```

```text
【延伸知识】
性能瓶颈可能出现在不同层面：应用层（代码效率）、中间件层（连接池）、数据库层（慢查询），需要分层排查。
```

## Q005729

- 题型：简答
- 难度：中等

**题目**

```text
假设在测试过程中某些事务的响应时间过长，但分析应用服务、数据库以及网络都属于正常现象，问题可能出现的原因有哪些？
```

**答案**

```text
可能是脚本运行较慢，性能测试的脚本，需要手工编写，如果编写的不合理，使用了性能比较差的元件，在运行测试脚本中的时间比较长，也会导致性能结果的响应时间指标值比较高。
```

**解析**

```text
【核心考点】 性能测试 响应时间分析 脚本优化
【题目解析】
本题考查性能测试中响应时间过长的排查思路。当应用、数据库和网络均正常时，问题可能出在测试脚本本身或测试环境配置上。
【参考答案要点】
1. 测试脚本效率低：脚本中使用了低效的元件（如不必要的循环、大量数据操作），导致执行时间过长。
2. 思考时间设置不当：脚本中插入了过长的思考时间或等待时间，影响事务响应时间。
3. 资源竞争：测试工具所在机器资源不足（CPU、内存、磁盘I/O），导致脚本执行缓慢。
4. 参数化数据问题：参数化数据量过大或数据源访问慢，增加脚本执行时间。
5. 日志记录过多：脚本中开启了详细日志记录，增加了I/O开销。
【易错提示】
不要忽略测试工具本身的性能瓶颈。建议使用性能监控工具（如PerfMon）分析测试机资源使用情况，并优化脚本逻辑。
```

## Q005731

- 题型：简答
- 难度：中等

**题目**

```text
做性能测试，资源不够是为什么？
```

**答案**

```text
项目部署在机器上，提供能力输出时，需要进行计算，这些计算就需要消耗机器上的计算资源，请求量越多，理论上需要的计算资源就要越大，但是机器硬件资源有限，所以当请求量消耗的资源大于我们设定的资源利用率标准线时，就出现了资源不够用。
```

**解析**

```text
【核心考点】 性能测试 资源瓶颈
【参考答案要点】
1. 资源有限性：服务器的CPU、内存、磁盘I/O、网络带宽等硬件资源是固定的，无法无限扩展。
2. 请求消耗资源：每个请求的处理都需要消耗一定的计算资源（如CPU时间片、内存空间）。
3. 资源利用率阈值：当请求量持续增加，资源消耗超过预设的利用率标准线（如CPU使用率>80%），就会出现资源不够用的情况。
4. 瓶颈点：通常某个资源最先达到极限（如CPU满载或内存耗尽），导致系统响应变慢或崩溃。
【面试角度】
回答时建议结合实际案例，例如“在一次压测中，我们发现CPU使用率飙升至95%，通过分析发现是数据库查询未优化导致”，能展示问题定位能力。
【延伸知识】
性能测试中常见的资源瓶颈包括：CPU瓶颈、内存泄漏、磁盘I/O等待、网络延迟。定位时通常使用top、vmstat、iostat等系统工具，或APM工具如Pinpoint、SkyWalking。
```

## Q005740

- 题型：简答
- 难度：中等

**题目**

```text
在性能测试的过程中，如何评估压测瓶颈？
```

**答案**

```text
1、平均响应时间是否超过能接受的范围、
2、是否有连续报错、
3、tps的趋势是否出现下降、
4、服务器资源利用率是否超过接受范围
```

**解析**

```text
【核心考点】 性能测试 瓶颈分析 监控指标
【题目解析】
本题考查性能测试过程中如何识别系统瓶颈。瓶颈评估需要综合多个指标，包括响应时间、错误率、吞吐量和资源利用率。
【参考答案要点】
1. 平均响应时间：检查是否超过可接受阈值。例如，核心交易接口响应时间超过3秒即认为存在瓶颈。
2. 连续报错：观察是否有连续的错误响应（如HTTP 500、超时），表明系统处理能力不足。
3. TPS趋势：监控每秒事务数（TPS）是否出现下降趋势。TPS下降通常意味着系统达到瓶颈。
4. 服务器资源利用率：检查CPU、内存、磁盘I/O、网络带宽是否超过可接受范围（如CPU>80%）。资源饱和往往是瓶颈的直接表现。
【面试角度】
面试官常问：如何区分瓶颈是应用层还是基础设施层？可回答：先检查资源利用率，若CPU高但TPS低，可能是代码效率问题；若CPU低但响应慢，可能是数据库或网络瓶颈。建议结合实际项目案例说明，如“某次压测发现TPS下降同时CPU飙升，最终定位为数据库连接池耗尽”。
【易错提示】
仅关注单一指标容易误判。例如，响应时间增加不一定代表瓶颈，可能是网络波动。应综合多个指标并观察趋势，同时结合系统架构分析。
```

```text
【最小响应时间】响应时间的最小值。反映服务最快处理能力。
【最大响应时间】响应时间的最大值。反映服务器最慢处理能力。
【CPU占用率】1-CPU空闲率，表示CPU被使用情况，反映了系统资源利用情况
```

## Q005717

- 题型：简答
- 难度：较难

**题目**

```text
JMeter模拟十个用户并发进行数据的添加，结果每次执行全部成功，但是数据却不是十条，每次数据不一样，但是都比十小。这种情况产生的原因是什么？
```

**答案**

```text
是数据库的问题。大多数的数据库都有记录锁的问题，
第一次的数据操作没有commit之前，第二次对同样表进行的操作可能就没有办法成功，所以每次数据的条数都达不到十条。又因为每次的操作服务器的响应时间是不同的，所以不同虚拟用户的提交时间也是不同的，这样就导致每次提交成功的数据量不一致，导致每次结果的条数可能是不同的。
```

**解析**

```text
【核心考点】 JMeter并发测试 数据库锁机制 事务提交
【题目解析】
本题考察JMeter并发测试中数据不一致问题的根因分析。模拟10个用户并发添加数据，但结果少于10条且每次数量不同，核心原因在于数据库层面的锁机制和事务隔离性。当多个虚拟用户同时向同一张表插入数据时，数据库会使用记录锁或表锁来保证数据一致性。如果第一个用户的事务未提交，后续用户的操作可能因锁等待而失败或回滚，导致实际插入成功的数据量少于并发用户数。此外，服务器响应时间差异导致各用户提交时间点不同，进一步影响最终成功插入的记录数。
【参考答案要点】
1. 数据库锁机制：多数数据库在并发写入时使用行级锁或表级锁。第一个事务未提交前，后续事务可能被阻塞或失败，导致部分插入操作未生效。
2. 事务隔离级别：默认隔离级别（如MySQL的REPEATABLE READ）可能导致幻读或不可重复读，影响并发插入的可见性。
3. 响应时间差异：不同虚拟用户的网络延迟、服务器处理速度不同，导致提交时间点分散，锁竞争结果随机，因此每次成功插入的数量不一致。
4. 解决方案：可考虑使用数据库事务重试机制、调整隔离级别为READ COMMITTED、或使用分布式锁（如Redis）控制并发。
【面试角度】
回答时建议结合实际项目经验，例如“在压测过程中，我们通过查看数据库死锁日志和慢查询日志定位问题，并优化了事务提交逻辑”。同时可补充说明JMeter的监听器（如聚合报告）如何辅助分析响应时间分布。
【易错提示】
不要误认为是JMeter工具本身的限制或网络丢包导致，应聚焦数据库并发控制机制。另外，需区分“并发用户数”与“实际成功事务数”的概念。
```

## Q005732

- 题型：简答
- 难度：较难

**题目**

```text
典型的数据库性能问题有哪些?解决办法分别有哪些?
```

**答案**

```text
(1)数据库连接池问题，连接池资源泄露，很难准确定位泄露的源头
解决办法：仔细分析程序代码，是否没有close（）连接？是否遗漏了finally块？或者尽管有close（）但并没有成功。

(2)连接池过小会导致连接池满后，新的客户无法连接上系统，在日志中出现错误信息。一般的解决方法是增大连接池。但另一方面，连接池过大会造成资源无效损耗，可能会出现新的性能问题
解决办法：
方法1：设置最初池大小=最大池大小
方法2：数据库连接池数=线程池数*每个线程需要连接数据库的平均数*1.1（1.1的含义是增加10%的峰值期负载），通常每个线程需要连接数据库的平均数是1，即当线程数为120时，数据库连接池数就是132

(3)SQL语句及其索引或锁定属性问题：SQL语句及其索引或锁定属性不合理可能引发DISKIO过忙（磁盘读/写数据）或者CPU过忙（在内存中索引排序），造成执行时间过长，阻塞线程的执行，最终引发系统挂起或者执行超时引发系统挂起。
解决办法：优化SQL语句及其索引或锁定属性

(4)过量的数据库调用:常见的性能瓶颈来自过量的数据库调用，引发这些问题不一定是SQL查询的Execute（）或Update（），而是应用程序与数据库的交互有关
解决办法：从数据库中大量取得所要求的数据，避免应用程序反复回掉数据库
```

**解析**

```text
【核心考点】 数据库性能 连接池管理
【题目解析】
数据库性能问题常见于连接池、查询优化和索引设计。连接池泄漏会导致资源耗尽，而连接池大小配置不当则影响并发能力。解决需结合代码审查和配置调优。
【参考答案要点】
1. 连接池泄漏：原因：未正确关闭连接（如缺少finally块）。解决：检查代码确保每次使用后close()，使用try-with-resources或连接池监控。

3. 连接池过大：原因：资源浪费，可能引发性能下降。解决：设置初始池大小=最大池大小，避免动态扩展开销。
```

## Q005733

- 题型：简答
- 难度：较难

**题目**

```text
出现内存泄露的根本原因是什么？你是怎么定位内存泄露原因的？
```

**答案**

```text
1. 内存泄露的根本原因是 Jvm 中老年代中存在着大量存活的对象，这些对象不能被 GC回收掉，从而占满了整个老年代，造成 Jvm 一直处于 FGC 的状态，程序没有响应，服务器
报 OOM 错误

2. 内存泄露主要通过分析老年代中占用空间最大的类都有哪些，然后去代码中找对应的
类的创建。通常可以使用 jdk 提供的 jvisualvm 和 jmap 进行堆内存的分析
```

**解析**

```text
【核心考点】 内存泄露 JVM调优 性能分析
【参考答案要点】
1. 根本原因：JVM老年代中存在大量存活对象，这些对象无法被GC回收，导致老年代被占满，JVM频繁进行Full GC，最终程序无响应并抛出OutOfMemoryError（OOM）。
2. 定位方法：
· 使用jvisualvm：连接JVM进程，通过Heap Dump分析老年代中占用空间最大的类，定位到具体对象。
· 使用jmap：生成堆转储文件（如jmap -dump:live,format=b,file=heap.hprof ），然后用MAT（Memory Analyzer Tool）分析。
· 分析代码：根据占用最大的类，在代码中查找对应的创建逻辑，检查是否存在未释放的引用（如静态集合、未关闭的资源等）。
【面试角度】
回答时建议结合实际排查经验，例如“在一次项目中，我们通过jvisualvm发现HashMap占用了大量内存，最终定位到是缓存未设置过期策略导致”，能体现实战能力。
【延伸知识】
常见内存泄露场景：长生命周期对象持有短生命周期对象引用（如ThreadLocal使用不当）、未关闭的数据库连接或IO流、静态集合类无限增长等。了解这些有助于预防和快速定位。
```

## Q005739

- 题型：简答
- 难度：较难

**题目**

```text
在web应用下，模拟十个用户并发进行数据的添加，结果每次执行全部成功，但是数据却不是十条，每次数据不一样，但是都比十小。这种情况产生的原因是什么？
```

**答案**

```text
是数据库的问题。大多数的数据库都有记录锁的问题，第一次的数据操作没有commit之前，第二次对同样表进行的操作可能就没有办法成功，所以每次数据的条数都达不到十条。又因为每次的操作服务器的响应时间是不同的，所以不同虚拟用户的提交时间也是不同的，这样就导致每次提交成功的数据量不一致，导致每次结果的条数可能是不同的。
```

**解析**

```text
【核心考点】 并发测试 数据库锁 事务隔离
【参考答案要点】
该现象的根本原因是数据库并发控制机制导致的数据不一致，具体分析如下：
1. 数据库锁机制：当多个用户并发插入数据时，数据库会使用锁（如行锁、表锁）来保证数据完整性。如果第一次插入操作未提交（commit），第二次对同一表的插入可能因锁冲突而等待或失败，导致实际成功插入的记录数少于10条。
2. 事务隔离级别：默认隔离级别（如可重复读或读已提交）可能影响并发行为。未提交的事务对其他会话不可见，若测试脚本未等待事务完成，可能导致部分插入被回滚或覆盖。
3. 响应时间差异：每个虚拟用户的请求到达服务器的时间不同，数据库处理速度也不同。这导致部分用户先提交成功，而后续用户可能因锁等待超时或死锁而失败，从而每次成功插入的记录数不一致。
【面试角度】
回答时建议结合实际项目中的并发测试经验，例如：“我们曾遇到类似问题，通过调整事务隔离级别为‘读已提交’并增加重试机制，最终解决了数据不一致。” 同时，可以提及数据库连接池配置和测试脚本设计（如是否使用事务）对结果的影响。
【延伸知识】
要彻底解决此类问题，可考虑：使用数据库乐观锁或悲观锁、将插入操作放在一个事务中、采用分布式锁（如Redis）。此外，性能测试工具（如JMeter）中的“事务控制器”可以确保一组操作作为一个整体提交。
```

```text
4. 线上压测：若需获取精确的线上性能数据，建议在线上环境进行压测（需在低峰期并做好熔断降级措施），这是最可靠的方式。
【面试角度】
回答时若能补充具体推算公式（如：线上QPS ≈ 线下单机QPS × 线上机器数 × 系数0.8），并提及线上压测的风险控制措施，会显著提升答案的专业度。
【延伸知识】
业界常用方法：通过线下基准测试建立性能基线，再结合线上监控数据（如CPU利用率、请求量）进行回归分析，使用线性回归或排队论模型推算线上容量。
```

```text
1. 调整请求脚本，去掉HTTP Keep-Alive，减少长连接；
2. 调整服务器操作系统TCP核心参数，如net.ipv4.tcp_tw_reuse和net.ipv4.tcp_tw_recycle（注意内核版本兼容性）；
3. 调整服务连接状态的保持时间相关参数，如缩短TIME-WAIT超时时间；
4. 优化应用层设计，减少短连接的使用。
【面试角度】
回答时建议结合实际项目中的性能调优案例，例如"在压测过程中发现响应时间升高，通过netstat定位到大量TIME-WAIT，调整了tcp_tw_reuse参数后问题解决"，能体现实战能力。
【易错提示】
注意tcp_tw_recycle在NAT环境下可能引发问题，新版内核已移除该参数，建议优先使用tcp_tw_reuse或调整应用层策略。
```

```text
【参考答案要点】
CPU问题常见类型包括：
1. 用户态使用率高： 应用程序计算密集，如循环、递归、复杂算法。
2. 系统态使用率高： 系统调用频繁，如文件I/O、网络I/O、锁竞争。
3. I/O等待高： 磁盘或网络I/O成为瓶颈，CPU等待I/O完成。
4. 上下文切换高： 线程数过多或锁竞争导致频繁切换。
5. 中断高： 硬件中断或软中断过多，如网络包处理。
6. 缓存命中率低： CPU缓存未命中导致访问内存延迟。
【易错提示】
常见错误：只关注CPU使用率，忽略其他指标。建议结合top、vmstat、perf等工具分析，并区分用户态和系统态。
```

## Q005756

- 题型：简答
- 难度：未标注
- 解析：AI 补全（原数据缺失解析）

**题目**

```text
性能测试怎么判断网络瓶颈？
```

**答案**

```text
1、看响应中的错误提示信息
2、观察网络监控展示的数据
3、通过网络命令，探测网络通信延迟情况
4、通过吞吐率和带宽数据，进行比较来确认
```

**解析**

```text
【核心考点】性能测试中网络瓶颈的定位。
【题目解析】可从四方面判断：先看响应中的错误提示，如超时、连接失败；再看网络监控的带宽、丢包、延迟数据；用网络命令探测通信延迟和路由；最后把吞吐率与带宽上限比较，接近上限就可能是网络瓶颈。
【答题要点】
1. 错误信息提供第一手线索。
2. 监控数据看带宽、丢包和延迟。
3. 吞吐率接近带宽上限时重点排查网络。
【面试提示】回答时强调先排除服务端和数据库，再定位网络，思路更专业。
```
