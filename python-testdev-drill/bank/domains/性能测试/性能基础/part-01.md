## Q005623

- 题型：简答
- 难度：入门

**题目**

```text
tps是什么
```

**答案**

```text
每秒事务处理量，是 Transaction per second 的缩写。是衡量服务器综合性能的最主要指标
```

**解析**

```text
【核心考点】 性能指标 TPS
【参考答案要点】
TPS（Transactions Per Second）是每秒事务处理量，用于衡量服务器综合性能。它反映系统在单位时间内能处理的事务数，是性能测试中的核心指标。
【面试角度】
回答时建议区分TPS与QPS：QPS（每秒查询数）通常用于查询场景，而TPS包含完整事务（如增删改查组合）。
【延伸知识】
TPS受硬件、网络、架构等多因素影响，性能测试中常与响应时间、并发数结合分析。
```

## Q005622

- 题型：简答
- 难度：简单

**题目**

```text
think_time的作用是什么？
```

**答案**

```text
思考时间，在loadrunner脚本中，模拟用户操作时的停顿，在真正执行性能测试时，默认会自动化忽略
```

**解析**

```text
【核心考点】 性能测试 LoadRunner 思考时间
【题目解析】
本题考查性能测试工具LoadRunner中思考时间（Think Time）的概念及其在测试执行中的作用。思考时间模拟了真实用户在操作过程中的停顿，如阅读页面、填写表单等，是性能测试中模拟真实用户行为的关键参数。
【参考答案要点】
1. 定义：思考时间是用户在操作步骤之间的等待时间，用于模拟真实用户的行为模式。
2. 作用：在性能测试中，思考时间影响并发用户的实际负载强度，忽略思考时间会导致服务器压力过大，测试结果失真。
3. 默认行为：LoadRunner在执行性能测试时，默认会忽略思考时间，以最大化压力，但实际测试中应根据业务场景决定是否保留或调整思考时间。
【面试角度】
回答时建议结合实际项目经验，例如“在电商系统性能测试中，我们通过录制脚本保留思考时间，并在压力测试时按比例缩放，以更准确地模拟用户行为”。
【易错提示】
不要混淆思考时间与响应时间：思考时间是用户主动停顿，响应时间是系统处理时间。
```

## Q005628

```text
下列说法正确的是
```

```text
B. 日常中，我们经常会把QPS当rps来说，因为他们是完全相同的
C. HPS和RPS都是描述用户发起的请求，所以他们俩是等价的
D. TPS是描述服务器每秒钟能处理的事务数
```

**答案**

```text
D
```

**正确选项**

```text
D. TPS是描述服务器每秒钟能处理的事务数
```

**解析**

```text
【核心考点】 性能测试指标 TPS/QPS/HPS/RPS
【题目解析】
本题考察性能测试中常见指标的概念辨析。TPS（Transactions Per Second）是服务器每秒钟处理的事务数，是衡量系统处理能力的核心指标。QPS（Queries Per Second）通常用于查询场景，HPS（Hits Per Second）指每秒点击次数，RPS（Requests Per Second）指每秒请求数。这些指标含义不同，不能混用。
【选项解析】
✗ A. 吞吐量就等于TPS — 错误。吞吐量是系统在单位时间内处理请求的总量，可能包含多种类型，而TPS特指事务数，两者不等价。
✗ B. QPS和RPS完全相同 — 错误。QPS侧重查询场景，RPS泛指所有请求，包括写入、更新等，并非完全相同。
✗ C. HPS和RPS等价 — 错误。HPS是每秒点击次数，通常指用户操作触发的HTTP请求，而RPS是服务器接收到的所有请求，包括非点击产生的请求。
✓ D. TPS是描述服务器每秒钟能处理的事务数 — 正确。这是TPS的标准定义，事务通常包含多个操作步骤，如登录、查询、退出等。
【易错提示】
面试中常混淆TPS和QPS，记住TPS包含完整事务，QPS仅针对查询。实际项目中，性能测试报告需明确指标定义，避免歧义。
```

## Q005630

- 题型：简答
- 难度：简单

**题目**

```text
什么是压力测试？
```

**答案**

```text
压力测试（Stress Test）也就是强度测试，压力测试是指模拟巨大的工作负荷来测试应用程序在峰值情况下如何执行操作。在实际的软硬件环境下，压力测试主要是以软件响应速度为测试目标，尤其是针对在较短时间内大量并发用户访问时软件的抗压能力。其目的是找到系统在哪里失效以及如何失效的地方。
```

**解析**


## Q005699

- 题型：简答
- 难度：简单

**题目**

```text
请解释以下性能指标：并发用户数，RT，TPS，QPS，RPS，资源利用率
```

**答案**

```text
1、并发用户数：同一时间执行请求的人，用来模拟真实用户调用接口请求，造成服务器压力。
2、RT：响应时间（rt）从发起请求，到接口响应，到页面渲染
3、TPS：服务器每秒完成事务数。------ 事务数：服务器每秒处理能力的性能指标值
4、QPS：每秒查询接口数
5、RPS：每秒请求数，由用户发起的请求数
6、资源利用率：服务器软、硬件资源使用情况
```

**解析**

```text
【核心考点】 性能测试 性能指标
【题目解析】
本题考察对性能测试基本指标的理解，是面试中的基础概念题。每个指标都有明确的定义和用途，需准确区分。
【参考答案要点】
1. 并发用户数：同一时间点向系统发起请求的用户数量，用于模拟真实负载。
2. RT（响应时间）：从用户发起请求到收到完整响应所经历的时间，包括网络延迟、服务器处理时间等。
3. TPS（每秒事务数）：服务器每秒能够处理的事务数量，事务通常包含多个操作，衡量服务器处理能力。
4. QPS（每秒查询数）：服务器每秒能够处理的查询请求数量，常用于衡量数据库或接口的查询性能。
5. RPS（每秒请求数）：客户端每秒发起的请求数量，反映用户请求的发送速率。
6. 资源利用率：服务器CPU、内存、磁盘、网络等硬件资源的使用百分比，反映系统负载程度。
【面试角度】
回答时需明确每个指标的定义和区别，例如TPS和QPS常被混淆。建议结合实际项目中的性能测试场景举例，如“在压测中，我们关注TPS和RT来评估系统瓶颈”。
【易错提示】
注意区分TPS和QPS：TPS通常包含多个操作（如登录、查询、退出），而QPS仅针对单个查询操作。
```

## Q005626

- 题型：简答
- 难度：中等

**题目**

```text
一台客户端有三百个客户与三百个客户端有三百个客户对服务器施压，有什么区别？
```

**答案**

```text
• 在这个情境中，三百个客户（Client）与三百个客户端（Client端）都对服务器施加压力，但具体的压力表现和效果可能会有所不同。
• 三百个独立的客户（Client）表示有三百个独立的个体与服务器交互，每个个体可能具有不同的行为和需求。
• 三百个独立的客户端（Client端）表示有三百个独立的软件或设备同时与服务器进行通信，每个客户端可能以不同的方式发送请求和处理响应。

总结：
客户（Client）是使用软件或服务的个体或实体，而客户端（Client端）是用于与服务器进行通信的软件或设备。在压力测试方面，三百个客户和三百个客户端都能对服务器施加压力，但从不同的角度和实现方式来看，其压力的表现和效果可能会有所不同。
```

**解析**

```text
【核心考点】 性能测试 并发模型 压力测试
【题目解析】
本题考察对性能测试中并发用户概念的理解。区别在于：一台客户端有三百个客户意味着单个客户端模拟三百个虚拟用户（如使用JMeter线程），共享同一IP和资源；三百个客户端有三百个客户意味着三百台物理或虚拟机器，每台模拟一个用户，更接近真实分布式场景。前者可能受单机资源限制（如CPU、内存、网络），后者更易模拟真实网络环境，但成本更高。
【参考答案要点】
1. 资源隔离：单客户端模拟多用户时，所有用户共享同一IP和系统资源，可能产生资源竞争；多客户端则更独立，模拟更真实。
2. 网络模拟：多客户端能模拟不同网络延迟和带宽，更贴近实际场景。
3. 压力分布：单客户端压力集中，可能成为瓶颈；多客户端压力分散，更易发现服务器端问题。
【面试角度】
回答时建议结合实际性能测试经验，如“在项目中我们使用JMeter分布式测试，多台负载机模拟真实用户”。
【易错提示】
不要混淆“客户”和“客户端”，前者是用户行为，后者是模拟工具。
```

## Q005638

- 题型：简答
- 难度：中等

**题目**

```text
什么是系统瓶颈?
```

**答案**

```text
瓶颈主要是指整个软硬件构成的软件系统某一方面或者几个方面能力不能满足用户的特定业务要求，“特定”是指瓶颈会在某些条件下会出现，因为毕竟大多数系统在投入前。

　严格的从技术角度讲，所有的系统都会有瓶颈，因为大多数系统的资源配置不是协调的，例如CPU使用率刚好达到100%时，内存也正好耗尽的系统不是很多见。因此我们讨论系统瓶颈要从应用的角度讨论：关键是看系统能否满足用户需求。在用户极限使用系统的情况下，系统的响应仍然正常，我们可以认为改系统没有瓶颈或者瓶颈不会影响用户工作。

　因此我们测试系统瓶颈主要是实现下面两个目的：

　
-发现“表面”的瓶颈。主要是模拟用户的操作，找出用户极限使用系统时的瓶颈，然后解决瓶颈，这是性能测试的基本目标。

　
-发现潜在的瓶颈并解决，保证系统的长期稳定性。主要是考虑用户在将来扩展系统或者业务发生变化时，系统能够适应变化。满足用户目前需求的系统不是最好的，我们设计系统的目标是在保证系统整个软件生命周期能够不断适应用户的变化，或者通过简单扩展系统就可以适应新的变化。
```

**解析**

```text
【核心考点】 性能测试 系统瓶颈 瓶颈分析
【参考答案要点】
系统瓶颈定义：系统瓶颈是指软硬件构成的系统中，某一或某些方面（如CPU、内存、磁盘I/O、网络带宽、数据库连接等）的能力不能满足用户特定业务需求，导致系统整体性能受限的现象。瓶颈通常具有条件性，即在特定负载或场景下才会显现。
瓶颈测试目的：
1. 发现"表面"瓶颈：通过模拟用户极限操作，找出影响用户正常使用的性能问题。
2. 评估系统容量：确定系统在何种负载下性能开始下降，为容量规划提供依据。
【面试角度】
回答时建议结合实际性能测试案例，例如："在某电商项目中，我们发现数据库连接池配置过小导致高并发时响应变慢，通过调整连接数解决了瓶颈"，能体现问题定位和解决能力。
【延伸知识】
常见的瓶颈分析方法包括：资源监控（CPU、内存、磁盘、网络）、数据库慢查询分析、应用日志分析、链路追踪等。面试中常追问如何定位瓶颈，建议掌握基本工具如top、iostat、慢查询日志等。
```

## Q005653

- 题型：简答
- 难度：中等

**题目**

```text
吞吐量和响应时间的关系。
```

**答案**

```text
吞吐量
吞吐量是指单位时间内系统能处理的请求数量，体现系统处理请求的能力，这是目前最常用的性能测试指标

响应时间RT(Response-time)
响应时间是一个系统最重要的指标之一，它的数值大小直接反应了系统的快慢。响应时间是指执行一个请求从开始到最后收到响应数据所花费的总体时间,即从客户端发起请求到收到服务器响应结果的时间

吞吐量图表显示的是Vuser每秒从服务器收到的以字节为单位的数据量。当我们比较它和事务响应时间，我们会发现，若吞吐量下降，响应时间也会下降。同样，高峰时期的吞吐量和最高的响应时间大约在同一个时间。
```

**解析**

```text
【核心考点】 性能指标 吞吐量 响应时间
【参考答案要点】
1. 定义：吞吐量是单位时间内系统处理的请求数量（如 TPS、QPS），响应时间是从请求发出到收到响应的总耗时。
2. 关系：通常呈负相关——吞吐量上升时，响应时间可能增加；反之亦然。但理想情况下，系统应在高吞吐量时仍保持低响应时间。
3. 关联分析：在性能测试中，若吞吐量下降，响应时间通常也会下降（因为负载降低）；若吞吐量达到峰值，响应时间往往达到最高点，表明系统接近瓶颈。
【面试角度】
回答时建议结合实际项目中的性能测试场景，例如“在压力测试中，我们发现当吞吐量超过 1000 TPS 时，响应时间从 200ms 飙升到 2s，说明系统存在瓶颈”，能展示分析能力。
【延伸知识】
吞吐量和响应时间的关系受系统架构影响，如缓存、异步处理等机制可改善两者平衡。了解 Little's Law（L=λW）有助于深入理解。
```

```text
资源利用率：对不同资源的使用程度，如	CPU，I/O, 内存， ,
```

```text
常见的性能测试策略有哪些？
```

```text
基准测试，并发测试，综合场景测试，场景测试，负载测试，疲劳测试，极限测
试，吞吐量测试，大数据量测试，内存泄漏测试等
```

**解析**

```text
【核心考点】 性能测试策略 性能测试类型
【题目解析】
本题考查性能测试中常见策略的分类与理解。性能测试策略根据测试目的不同，分为多种类型，每种策略关注不同的性能指标（如响应时间、吞吐量、资源利用率等）。
【参考答案要点】
1. 基准测试：在低负载下获取系统性能基线，作为后续对比依据。
2. 并发测试：模拟多用户同时操作，检查系统是否出现死锁、资源竞争等问题。
3. 综合场景测试：模拟真实用户混合操作（如登录、查询、下单），评估整体性能。

6. 疲劳测试：长时间运行（如24小时），检查系统是否出现内存泄漏或性能衰减。
7. 极限测试：超出系统设计容量，测试系统在极端条件下的行为（如崩溃或降级）。
8. 吞吐量测试：测量系统在单位时间内处理请求的能力（如TPS）。
9. 大数据量测试：测试系统处理大量数据（如数据库百万级记录）时的性能。
10. 内存泄漏测试：通过监控内存使用，检测是否存在未释放的内存。
【面试角度】
回答时建议结合实际项目经验，例如“在电商项目中，我们重点做了并发测试和疲劳测试，发现订单接口在200并发时响应时间超过3秒”，能体现对策略的深入理解。
【延伸知识】
性能测试策略还包括压力测试（Stress Testing）和容量测试（Capacity Testing），前者关注系统崩溃点，后者关注系统最大处理能力，面试中常被追问区别。
```

## Q005664

- 题型：简答
- 难度：中等

**题目**

```text
性能测试中，tps和qps的区别是什么？
```

**答案**

```text
QPS：
Queries Per Second，顾名思义：“每秒查询率”，是一台服务器每秒能够相应的查询次数，是对一个特定的查询服务器在规定时间内所处理流量多少的衡量标准。
TPS：
是TransactionsPerSecond的缩写，也就是事务数/秒。它是软件测试结果的测量单位。一个事务是指一个客户机向服务器发送请求然后服务器做出反应的过程。客户机在发送请求时开始计时，收到服务器响应后结束计时，以此来计算使用的时间和完成的事务个数。

TPS处理流程：
Tps即每秒处理事务数，包括了
1、用户请求服务器
2、服务器自己的内部查询等处理
3、服务器返回给用户
这三个过程，每秒能够完成N个这三个过程，Tps也就是N；

QPS基本类似于TPS，但是不同的是，对于一个页面的一次访问，形成一个TPS；但一次页面请求，可能产生多次对服务器的请求，服务器对这些请求，就可计入QPS之中。每秒查询率QPS是对一个特定的查询服务器在规定时间内所处理流量多少的衡量标准

一个事务是指一个客户机向服务器发送请求然后服务器做出反应的过程。客户机在发送请求时开始计时，收到服务器响应后结束计时，以此来计算使用的时间和完成的事务个数。
```

**解析**

```text
【核心考点】 性能测试指标 TPS QPS
【题目解析】
本题考查性能测试中两个核心指标的区别。QPS（Queries Per Second）指每秒查询率，常用于衡量查询类服务的处理能力；TPS（Transactions Per Second）指每秒事务数，一个事务包含完整的请求-处理-响应过程。TPS更侧重于完整业务操作，而QPS更侧重于单一查询请求。
【参考答案要点】
1. 定义不同：QPS是每秒查询次数，TPS是每秒事务数。一个事务可能包含多个查询。
2. 应用场景不同：QPS常用于数据库、搜索引擎等查询密集型系统；TPS常用于电商、支付等涉及完整业务流程的系统。
3. 衡量粒度不同：QPS关注单次请求，TPS关注完整业务单元（如一次下单包含查询库存、扣减余额等操作）。
4. 关系：在简单场景下，一个事务可能只包含一个查询，此时TPS≈QPS；复杂场景下，TPS通常小于QPS。
【面试角度】
建议结合实际项目举例，如“在XX电商项目中，我们使用TPS衡量下单接口的性能，使用QPS衡量商品搜索接口的性能”，体现对指标的理解深度。
【易错提示】
不要混淆两者概念，面试中常问“一个事务包含多个查询时，TPS和QPS的关系”，需明确TPS≤QPS。
```

## Q005676

- 题型：简答
- 难度：中等

**题目**

```text
性能测试考察的测试指标主要有哪些？
```

**答案**

```text
1、点击率(hit)：每秒的页面点击数。客户端每秒向服务端提交的请求数，在性能测试中，一般不测静态请求(如Js、css、图片文件等)，静态请求走缓存，不需要服务器处理。所以hit通常是指动态请求。
2、并发用户数：在真实的用户操作中，用户的每个相邻操作之间都会有一定的间隔时间(称之为用户思考时间)，所以并发用户分为绝对并发和相对并发。单就性能指标而言，系统的并发用户数是指系统可以同时承载的、正常使用系统功能的用户总数量。
3、响应时间RT：事务处理的响应时间。请求或者某个操作从发出的时间到收到服务器响应的时间的差值
4、TPS/吞吐量：每秒处理的事务数。系统在单位时间内处理客户端请求的数量
5、QPS：每秒查询率。对一个特定的查询服务器在规定时间内所处理流量多少的衡量标准，不考虑外界因素
```

**解析**

```text
【核心考点】 性能测试指标 性能测试基础
【参考答案要点】
1. 并发用户数：系统能同时承载的正常使用用户数量，分为绝对并发和相对并发。
2. 响应时间（RT）：从请求发出到收到响应的总时间，通常关注平均、90%分位和最大响应时间。
3. 吞吐量（TPS/QPS）：单位时间内系统处理的事务数或查询数，反映系统处理能力。
4. 点击率（Hits per Second）：每秒客户端向服务器发送的请求数，通常指动态请求。
```

## Q005688

- 题型：简答
- 难度：中等

**题目**

```text
简述压力测试与性能测试的联系与区别。
```

**答案**

```text
压力测试是用来保证产品发布后系统能否满足用户需求，关注的重点是系统整体；
性能测试可以发生在各个测试阶段，即使是在单元层，一个单独模块的性能也可以进行评估。
压力测试是通过确定一个系统的瓶颈，来获得系统能提供的最大服务级别的测试。
性能测试是检测系统在一定负荷下的表现，是正常能力的表现；而压力测试是极端情况下的系统能力的表现。
```

**解析**

```text
【核心考点】 性能测试 压力测试 概念辨析
【参考答案要点】
联系：两者都属于非功能测试，目的都是评估系统性能，常结合使用。
区别：
1. 测试目的不同：性能测试关注系统在正常负载下的响应时间、吞吐量等指标，验证是否满足性能需求；压力测试关注系统在极端负载（如高并发、资源耗尽）下的行为，寻找系统瓶颈和崩溃点。
2. 测试负载不同：性能测试通常使用预期或稍高于预期的负载；压力测试则持续增加负载直至系统失效。
3. 测试阶段不同：性能测试可在各个阶段进行（单元、集成、系统）；压力测试通常在系统测试后期或上线前进行。
4. 关注点不同：性能测试关注“正常能力”，压力测试关注“极限能力”和“恢复能力”。
【面试角度】
回答时建议结合实际项目案例，例如“在双十一活动前，我们通过压力测试发现数据库连接池瓶颈，并进行了优化”，能体现实战经验。
【延伸知识】
还可提及负载测试（逐步增加负载观察表现）和稳定性测试（长时间运行检测内存泄漏等），展示对性能测试体系的全面理解。
```

```text
（3）应用在服务器端性能的测试 对于应用在服务器上性能的测试，可以采用工具监控，也可以使用系统本身的监控命令，例如Tuxedo中可以使用Top命令监控资源使用情况。实施测试的目的是实现服务器设备、服务器操作系统、数据库系统、应用在服务器上性能的全面监控。
```

```text
【核心考点】 性能测试 客户端性能 网络性能 服务器性能

本题考查性能测试的分类和基本概念。性能测试从测试对象角度分为客户端、网络和服务器三类，每类关注点不同，需要掌握各自的测试目标和常用方法。

1. 应用在客户端性能的测试：目的是考察客户端应用的性能，测试入口是客户端。主要包括并发性能测试、疲劳强度测试、大数据量测试和速度测试等，其中并发性能测试是重点。常用工具如LoadRunner、JMeter模拟多用户操作。
```

## Q005707

- 题型：简答
- 难度：中等

**题目**

```text
负载测试 性能测试、压力测试的理解（区别）
```

**答案**

```text
1、负载测试：在一定的软硬件环境下，不段增加并发用户数，直到某项指标达到饱和状态，以检测服务器在不同负载情况下各项性能指标的情况，
2、压力测试：在一定的软硬件环境下，通过最大用户数测试系统的稳定性、可靠性，满足条件：足够的并发用户数+足够长的测试时间(7*24)
3、性能测试：性能测试是通过自动化测试工具模拟多种正常、峰值以及异常负载条件对系统各项指标进行的测试。
```

**解析**

```text
【核心考点】 性能测试分类 负载测试 压力测试
【参考答案要点】
1. 负载测试：在特定软硬件环境下，逐步增加并发用户数，直到系统某项指标达到饱和，检测系统在不同负载下的性能表现，如响应时间、吞吐量等。
2. 压力测试：在特定软硬件环境下，通过最大并发用户数（通常超过系统预期峰值）和长时间运行（如7×24小时）来测试系统的稳定性和可靠性，关注系统是否崩溃或资源泄漏。
3. 性能测试：广义上包含负载和压力测试，狭义上指通过自动化工具模拟正常、峰值和异常负载条件，对系统各项性能指标（如响应时间、CPU使用率、内存占用等）进行综合评估。
【面试角度】
回答时建议结合实际项目案例说明三者的应用场景，例如“在电商项目中，负载测试用于评估促销活动时的并发能力，压力测试则用于验证系统在极端流量下的恢复能力”。
【易错提示】
```

```text
本题考查三种测试类型的定义与区别。负载测试关注系统在不同负载下的性能表现；可靠性测试关注系统在特定条件下无故障运行的能力；可用性测试关注用户使用系统的便捷性和满意度。
```

## Q005619

- 题型：简答
- 难度：较难

**题目**

```text
WEB应用程序，在性能测试压力下出现的常见错误类型有哪些？
```

**答案**

```text
有两种错误类型是：
（1）内存泄漏（Memoryleak）：一种极难检测的现象。内存泄漏经常发生在已发行的产品中，原因很简单，很难设计测试用例来检测它们。使用简单的功能测试，几乎发现不了内存泄漏问题，因为在产品完成之前测试没对产品进行足够多的使用。内存泄漏通常要求操作要重复非常多的次数以使内存消耗达到能引起注意的程度。尽管与其它编程语言（如C/C++）相比，Java程序更难引入内存泄漏错误，但只要程序仍保持着对对象的引用，该对象仍有可能被实例化并且它占用的内存永远不会被释放。
（2）并发与同步（ConcurrencyandSynchronization）：压力测试在查找并发性问题上非常出众，这是因为在任何一个测试生命周期中，它都应用了许多不同的代码路径和定时条件。一般的规则是，压力测试运行的时间越长，涉及并应用的代码路径组合和定时条件就越多。当然，这也的确使得这些问题很难再现（错误可以在5分钟或5天后发生）。死锁、线程泄漏以及任何一般的同步问题通常只能在压力测试阶段被检测出来。这些类型的问题很难通过执行单元测试来发现。开发人员不会一直考虑他或她的代码将与其他地方的代码（在执行单元测试时这些代码可能还没写出来）进行交互。
```

**解析**

```text
【核心考点】 性能测试 内存泄漏 并发测试
【题目解析】
本题考查在Web应用性能压力下常见的错误类型。压力测试旨在发现系统在高负载下的稳定性问题，其中内存泄漏和并发同步问题是两种典型且难以检测的错误。内存泄漏会导致系统资源逐渐耗尽，而并发问题则可能引发数据不一致或死锁。
【参考答案要点】
1. 内存泄漏：程序未能释放不再使用的内存，导致可用内存持续减少，最终引起系统响应变慢或崩溃。在Java中，即使有垃圾回收，仍可能因对象引用未释放而发生泄漏。
2. 并发与同步问题：多线程环境下，对共享资源的访问未正确同步，可能导致数据竞争、死锁、活锁或线程饥饿。压力测试能放大这些问题的出现概率。
3. 其他常见错误：数据库连接池耗尽、CPU过载、磁盘I/O瓶颈、网络超时等。
【面试角度】
回答时，建议结合实际项目经验，例如“在某次压力测试中，我们发现随着并发用户数增加，响应时间急剧上升，通过分析堆转储文件定位到内存泄漏”。同时，区分内存泄漏和内存溢出是加分项。
【延伸知识】
性能测试工具（如JMeter、LoadRunner）通常提供监控指标，如GC活动、线程状态等，帮助定位问题。此外，压力测试应结合稳定性测试（长时间运行）来发现渐进式问题。
```

## Q005649


```text

然后 编写测试计划，人员、时间周期、工具，接着去搭建性能测试环境(如果没有单独的性能测试环境，也可以用功能测试环境来压测)，紧接着会对数据库，进行造数据。然后开始实战，我们用jmeter先保证接口能跑通、然后进行单接口压力测试、混合接口压力测试、稳定性测试
最后 进行性能结果分析，提交测试报告，以及等待开发性能调优，复测。
```

## Q005687

- 题型：简答
- 难度：较难

**题目**

```text
简介WEB应用程序在压力下的常见错误类型。
```

**答案**

```text
有两种错误类型是： （1）内存泄漏（Memoryleak）：一种极难检测的现象。内存泄漏经常发生在已发行的产品中，原因很简单，很难设计测试用例来检测它们。使用简单的功能测试，几乎发现不了内存泄漏问题，因为在产品完成之前测试没对产品进行足够多的使用。内存泄漏通常要求操作要重复非常多的次数以使内存消耗达到能引起注意的程度。尽管与其它编程语言（如C/C++）相比，Java程序更难引入内存泄漏错误，但只要程序仍保持着对对象的引用，该对象仍有可能被实例化并且它占用的内存永远不会被释放。 （2）并发与同步（ConcurrencyandSynchronization）：压力测试在查找并发性问题上非常出众，这是因为在任何一个测试生命周期中，它都应用了许多不同的代码路径和定时条件。一般的规则是，压力测试运行的时间越长，涉及并应用的代码路径组合和定时条件就越多。当然，这也的确使得这些问题很难再现（错误可以在5分钟或5天后发生）。死锁、线程泄漏以及任何一般的同步问题通常只能在压力测试阶段被检测出来。这些类型的问题很难通过执行单元测试来发现。开发人员不会一直考虑他或她的代码将与其他地方的代码（在执行单元测试时这些代码可能还没写出来）进行交互。
```

**解析**

```text
【核心考点】 性能测试 压力测试 内存泄漏 并发问题
【参考答案要点】
WEB应用程序在压力下的常见错误类型包括：
1. 内存泄漏（Memory leak）：程序持续持有对象引用，导致内存无法释放，最终耗尽系统资源。此类错误难以通过常规功能测试发现，通常需要长时间、高频率的压力测试才能暴露。
2. 并发与同步问题（Concurrency and Synchronization）：多线程或多用户同时访问时，因缺乏适当的同步机制，导致数据竞争、死锁或状态不一致。压力测试是发现此类问题的有效手段。
【面试角度】
回答此类问题时，建议结合实际项目经验举例说明，例如“在项目中，我们通过持续压力测试发现了一个内存泄漏，原因是缓存未及时清理”，能有效提升答案深度。
【延伸知识】
其他常见错误类型还包括：数据库连接池耗尽、线程池溢出、响应时间急剧增加等。了解这些有助于全面应对压力测试场景。
```

```text
本题考查性能测试、负载测试和压力测试的概念辨析及实际应用。这三种测试类型在性能测试领域中常被混淆，需要明确其目的和场景。

1. 性能测试例子：对一个电商网站，在预期并发用户数（如1000人）下，测试响应时间、吞吐量等指标是否满足SLA要求。
2. 负载测试例子：逐步增加并发用户数（如从100到5000），找到系统性能拐点（如响应时间急剧上升的临界点），确定最大支持用户数。
3. 压力测试例子：持续向系统施加超过设计容量的压力（如10000并发用户），观察系统何时崩溃、是否自动恢复，验证系统的稳定性和容错能力。
【面试角度】
面试时，建议结合实际项目经验举例，例如“在支付系统中，我们通过负载测试确定了最大并发交易数，并通过压力测试验证了系统在极端流量下的降级策略”。同时，可以提及性能测试工具（如JMeter、LoadRunner）的使用。
【易错提示】
注意区分：性能测试是验证性能指标是否达标；负载测试是寻找系统极限；压力测试是测试系统在极限状态下的行为。三者目的不同，不能混为一谈。
```

## Q005697

- 题型：简答
- 难度：较难

**题目**

```text
请描述一下性能测试的常见类型和方法。
```

**答案**

```text
常见的性能测试类型包括负载测试、压力测试、容量测试和稳定性测试。负载测试用于模拟正常工作负载并观察系统在此负载下的表现。压力测试是在负载的上限情况下测试系统的性能。容量测试用于确定系统能够处理的最大负载。稳定性测试则是通过长时间运行测试以验证系统在持续负载下的表现。
```

```text
2. 压力测试：在极限负载下测试系统稳定性，观察系统何时崩溃或性能下降。
3. 容量测试：确定系统能处理的最大用户数或数据量，为扩展提供依据。
```

## Q005701

- 题型：简答
- 难度：较难

**题目**

```text
请详细说明软件可靠性测试中需注意的问题。
```

**答案**

```text
软件可靠性测试需要注意的问题主要有3点：
1.功能识别 软件可靠性测试首先考虑的是功能识别，确定系统所使用的功能。 功能识别的目标是：识别系统所确定的功能（依据系统功能说明书进行审核）；识别系统功能所需的相关条件。
2.可靠性对时间的要求 软件可靠性对时间的要求是比较高的，测试时应将“运行时间”作为衡量可靠性的重要指标，所谓运行时间就是软件运行时应在“规定的时间”内完成所要完成的工作。对于时间的要求应根据系统性能说明书的要求进行审核。
3.可靠性对环境条件的要求 环境条件是指软件系统运行时所需的各种支持要素，主要表现为：硬件环境（服务器、路由器、交换机、防火墙、磁盘阵列）、网络操作系统、软件工具、应用系统的操作规程等。
```

**解析**

```text
【核心考点】 软件可靠性测试 非功能测试 质量属性
【题目解析】
本题考查软件可靠性测试中的关键注意事项。可靠性测试属于非功能测试范畴，关注软件在特定条件下无故障运行的能力。题目要求详细说明，属于较难的综合题，需要考生对可靠性测试有系统认识。
【参考答案要点】
1. 功能识别：明确系统需要测试的核心功能，依据功能说明书审核功能完整性，并识别功能运行所需的相关条件（如输入数据、前置状态）。
2. 时间要求：可靠性测试强调在"规定的时间"内完成功能，需将运行时间作为关键度量指标，包括连续运行时长、响应时间等。测试设计时应模拟长时间运行场景，验证系统是否会出现内存泄漏、资源耗尽等问题。
3. 环境条件：系统运行依赖的软硬件环境，包括服务器、网络设备、操作系统、中间件等。测试需在接近生产环境的条件下进行，并考虑环境异常（如网络中断、硬件故障）对可靠性的影响。
4. 其他注意事项：故障恢复能力（系统崩溃后能否快速恢复）、数据完整性（长时间运行后数据是否一致）、压力与负载（高并发下的稳定性）。
【面试角度】
回答时建议结合实际项目案例，例如"在测试银行交易系统时，我们设计了72小时连续运行测试，监控内存和CPU使用率，发现内存泄漏问题"，能显著提升答案的实践价值。此外，可提及可靠性测试的常用工具（如LoadRunner、JMeter）和度量指标（如MTBF、MTTR）。
【延伸知识】
可靠性测试与稳定性测试、压力测试有交叉但侧重点不同：可靠性更关注无故障运行的概率，而稳定性关注性能波动。ISTQB中可靠性测试属于质量属性测试的一部分，常与可用性测试结合进行。
```

## Q005702

- 题型：简答
- 难度：较难

**题目**

```text
请说明性能测试中响应时间和吞吐量的关系。
```

**答案**

```text
响应时间是提交请求和返回该请求的响应之间使用的时间。
示例包括：
（1）数据库查询花费的时间
将字符回显到终端上花费的时间
访问 Web 页面花费的时间
（2）吞吐量是对单位时间内完成的工作量的量度。
示例包括：
（1）每分钟的数据库事务
（2）每秒传送的文件千字节数
（3）每秒读或写的文件千字节数
（4）每分钟的 Web 服务器命中数
这些度量之间的关系很复杂。有时可能以响应时间为代价而得到较高的吞吐量，而有时候又要以吞吐量为代价得到较好的响应时间。在其他情况下，一个单独的更改可能对两者都有提高。可接受的性能基于合理的吞吐量与合理的响应时间相结合。"
```

**解析**

```text
【核心考点】 性能测试 响应时间 吞吐量
【题目解析】
本题考查性能测试中两个核心指标——响应时间（Response Time）和吞吐量（Throughput）的定义及其关系。这是性能测试的基础概念，也是面试高频考点。
【参考答案要点】
响应时间：从发送请求到收到完整响应所花费的时间，包括网络延迟、服务器处理时间等。示例：页面加载时间、数据库查询时间。
吞吐量：单位时间内系统处理的工作量。示例：每秒事务数（TPS）、每秒请求数（RPS）、每秒传输字节数。
关系：
两者通常呈负相关：
- 当系统负载增加时，吞吐量可能先上升，但响应时间会随之增加。
- 当响应时间过长时，用户可能放弃请求，导致吞吐量下降。
- 优化可能同时改善两者（如增加缓存），也可能需要权衡（如提高并发数可能增加响应时间但提升吞吐量）。
【面试角度】
回答时建议结合实际性能测试场景，例如“在电商秒杀活动中，我们通过调整连接池大小来平衡响应时间和吞吐量”。同时可提及Little's Law（L = λW）解释三者关系。
【易错提示】
常见误区：认为响应时间越短吞吐量越高。实际上，在系统资源未饱和时，适当增加负载可能提高吞吐量但响应时间略有增加；资源饱和后，继续增加负载会导致响应时间急剧上升，吞吐量下降（拐点效应）。
```

## Q005713

- 题型：简答
- 难度：较难

**题目**

```text
问：一台客户端有三百个客户与三百个客户端有三百个客户对服务器施压，有什么区别?
```

**答案**

```text
300个用户在一个客户端上，会占用客户机更多的资源，而影响测试的结果。线程之间可能发生干扰，而产生一些异常。

300个用户在一个客户端上，需要更大的带宽。

IP地址的问题，可能需要使用IP Spoof来绕过服务器对于单一IP地址最大连接数的限制。

所有用户在一个客户端上，不必考虑分布式管理的问题;而用户分布在不同的客户端上，需要考虑使用控制器来整体调配不同客户机上的用户。同时，还需要给予相应的权限配置和防火墙设置。
```

**解析**

```text
【核心考点】 性能测试 负载模型 分布式测试
【参考答案要点】
1. 资源占用差异：300个用户在一台客户端会占用更多本地资源（CPU、内存），可能影响测试结果准确性；而300个客户端各一个用户则资源分散，更接近真实场景。
2. 线程干扰风险：同一客户端多用户模拟时，线程间可能相互干扰，产生异常行为（如资源竞争）。
3. 网络带宽限制：单客户端需更大带宽来模拟300个用户的并发请求，可能成为瓶颈。
4. IP地址限制：单客户端需使用IP Spoof技术绕过服务器对单一IP最大连接数的限制；多客户端则自然分散IP。
5. 管理复杂度：多客户端需考虑分布式管理、控制器协调、权限配置和防火墙设置；单客户端则管理简单。
【面试角度】
此题考察对性能测试负载模型的理解，建议结合工具（如LoadRunner、JMeter）说明分布式测试的优缺点。
【延伸知识】
实际性能测试中，推荐使用分布式负载生成器，以模拟真实用户分布，避免单点瓶颈。同时需监控服务器端资源，确保测试数据有效。
```
