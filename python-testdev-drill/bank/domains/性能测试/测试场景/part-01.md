## Q005779

- 难度：简单

**题目**

```text
一般在哪个节点做性能测试？
```

**答案**

```text
性能测试，一般都是在性能测试环境中执行。当开发把接口开发完成，接口测试通过，就可以着手准备接口的性能测试。
```

**解析**

```text
【核心考点】 性能测试 测试流程

本题考察性能测试的执行时机。性能测试通常在功能测试通过后、系统相对稳定时进行，以确保测试结果的准确性和有效性。一般是在性能测试环境中，当接口测试通过后即可开始。
```

## Q005777

- 题型：简答
- 难度：中等

**题目**

```text
Nginx 常用负载均衡配置有哪些
```

**答案**

```text
1. nginx.conf

2. 轮询模式，默认；

3. weight 权重模式，权重越高被访问概率越大，weight=70；

4. ip_hash，在 upstream 中采用 ip_hash 指令,如果客户已经访问了某个服务器，
当用户再次访问时，会将该请求通过哈希算法，自动定位到该服务器。
每个请求按访问 ip 的 hash 结果分配，这样每个访客固定访问一个后端服务器，
可以解决 session 的问题。此种策略，可以实现同一个用户访问同一台服务器，
会话不会丢失，但是可能会分配不均
```

**解析**

```text
【核心考点】 Nginx负载均衡 配置方法
【题目解析】
Nginx通过upstream模块实现负载均衡，常用配置包括轮询、权重、IP哈希等。本题要求列出常用配置，属于运维和测试工程师的常见面试题。
【参考答案要点】
1. 配置文件：通常在nginx.conf的http块中定义upstream。
2. 轮询（默认）：每个请求按时间顺序分配到不同服务器，适用于服务器性能相近的场景。
3. 权重（weight）：通过weight参数设置服务器权重，权重越高被分配概率越大，如weight=70。
4. IP哈希（ip_hash）：使用ip_hash指令，根据客户端IP的哈希结果分配，确保同一IP固定访问同一后端，解决session问题，但可能导致负载不均。
【面试角度】
回答时建议补充实际应用场景，例如“在电商项目中，我们使用权重策略将更多流量分配给高性能服务器”，并说明每种策略的优缺点。
【延伸知识】
Nginx还支持least_conn（最少连接）、fair（响应时间）等第三方模块策略，了解这些可以展示深度。
```

## Q005781

- 题型：简答
- 难度：中等

**题目**

```text
什么时候开始进行性能测试？
```

**答案**

```text
性能测试一般分前期阶段和后期阶段。
前期阶段是功能实现后还没有到系统集成时期。可以针对功能实现进行性能测试，看看单独功能实现的响应时间
后期阶段是指系统功能通过功能性测试完毕后，到整体的性能测试阶段。
```

**解析**

```text
【核心考点】 性能测试 测试阶段
【参考答案要点】
性能测试的时机通常分为两个阶段：
1. 前期阶段（功能实现后、系统集成前）：针对已实现的单个功能模块进行性能测试，评估其响应时间、资源消耗等指标，以便早期发现性能瓶颈。
2. 后期阶段（系统功能测试完成后、整体性能测试前）：在系统集成和功能验证通过后，进行全面的性能测试，模拟真实负载，评估系统整体性能表现。
【面试角度】
回答时建议结合实际项目经验，例如“在我们的项目中，性能测试从功能模块开发完成后就开始介入，通过JMeter进行接口级性能测试，后期再结合全链路压测”，这样能体现对性能测试流程的深入理解。
【延伸知识】
性能测试应尽早开始，而非等到功能测试全部完成。早期发现性能问题可降低修复成本，常见误区是认为性能测试只在后期进行。
```

## Q005782

- 题型：简答
- 难度：中等
- 答案：AI 补全（原数据缺失文字答案）

**题目**

```text
什么是集合点，为什么要设，怎样设置，命令是什么？
```

**答案**

```text
什么是集合点：
集合点是指在性能测试脚本中设置的一个同步点，当多个虚拟用户到达该点时，会等待直到所有用户（或指定数量的用户）都到达，然后同时释放，模拟高并发场景。
为什么要设：
为了模拟真实场景中的并发访问，测试系统在瞬间高并发下的处理能力，如登录、下单等操作。如果不设置集合点，虚拟用户可能分散执行，无法达到真正的并发效果。
怎样设置：
在LoadRunner的VuGen中，在需要并发的操作前插入lr_rendezvous函数。例如：lr_rendezvous("login");。然后在Controller的场景设计中，设置集合点的策略，如释放条件（所有用户到达、指定百分比等）。
命令：
在LoadRunner中，使用lr_rendezvous("集合点名");函数。
```

**解析**

```text
【核心考点】 性能测试 LoadRunner 集合点
【题目解析】
本题考查性能测试中集合点的概念和使用。集合点（Rendezvous Point）是LoadRunner等性能测试工具中的一个重要功能，用于模拟多个虚拟用户在同一时刻并发执行某个操作，以测试系统在并发压力下的性能表现。
【参考答案要点】
什么是集合点：
集合点是指在性能测试脚本中设置的一个同步点，当多个虚拟用户到达该点时，会等待直到所有用户（或指定数量的用户）都到达，然后同时释放，模拟高并发场景。
为什么要设：
为了模拟真实场景中的并发访问，测试系统在瞬间高并发下的处理能力，如登录、下单等操作。如果不设置集合点，虚拟用户可能分散执行，无法达到真正的并发效果。
怎样设置：
在LoadRunner的VuGen中，在需要并发的操作前插入lr_rendezvous函数。例如：lr_rendezvous("login");。然后在Controller的场景设计中，设置集合点的策略，如释放条件（所有用户到达、指定百分比等）。
命令：
在LoadRunner中，使用lr_rendezvous("集合点名");函数。
【面试角度】
回答时建议结合实际项目中的性能测试场景，例如“在电商项目中，我们在下单接口前设置集合点，模拟秒杀场景”，能体现对工具和场景的理解。
【延伸知识】
集合点与思考时间（think time）的区别：思考时间模拟用户操作间隔，集合点模拟并发。两者在性能测试中作用不同，需合理搭配使用。
```

```text
以某web网站有一个webapi http://p.test.com?p1=${value1}&p0=${value2}为例，简述下完整的性能测试流程
```

```text

搭建或确认性能测试环境
编写脚本，在对脚本进行参数化，准备好数据
进行负载测试，获得最大可接受并发用户数
```

```text
2. 混合测试（负载测试）：按照实际业务比例（如登录10%、查询40%、下单30%、支付20%）同时压测多个接口，模拟真实用户混合访问场景，找出系统整体瓶颈。
3. 稳定性测试（耐久测试）：在一定的并发压力下（如70%峰值TPS），持续运行较长时间（如8小时或24小时），监控内存泄漏、数据库连接池耗尽、CPU持续高负载等问题，验证系统长期运行的可靠性。
4. 其他常见场景：峰值测试（模拟双11等突发流量）、容量测试（确定系统最大承载用户数）、压力测试（逐步加压直至系统崩溃，找到拐点）等。
【面试角度】
回答时建议结合实际项目案例，例如“在电商项目中，我们根据用户行为日志分析出各接口调用比例，设计混合测试场景，最终发现数据库连接池配置不当导致瓶颈”，能展示对性能测试的深入理解。
【易错提示】
常见误区：只做单交易测试而忽略混合场景，导致上线后出现资源争抢问题；或稳定性测试时间过短，无法暴露内存泄漏等慢性问题。
```


```text
1. 集合点是测试脚本中的一个标记，当每个虚拟用户执行到标记处时，会停留在标记处
等待其他的虚拟用户，当达到预期设置的并发数时，标记处的所有用户同时启动执行后续的
请求

2. 集合点会产生瞬间高并发，但是也会降低平均压力。所以在压测过程中，如果有要求
瞬间高并发的业务，就需要使用集合点，比如抢购，秒杀之类的业务。

3. 没有类似业务则不需要加集合点

4. lr_rendezvous（“集合点名称”），同步定时器
```

**解析**

```text
【核心考点】 性能测试 集合点 并发测试
【参考答案要点】
1. 概念：集合点是性能测试脚本中的一个同步点，当虚拟用户执行到该点时暂停，等待其他虚拟用户到达，达到预设并发数后同时释放，模拟瞬间高并发请求。
2. 应用场景：适用于需要模拟瞬间高并发的业务，如抢购、秒杀、抢票等。在这些场景中，集合点能有效测试系统在峰值压力下的表现。
3. 注意事项：集合点会产生瞬时高并发，但也会降低平均压力，因此仅在有明确业务需求时使用。若无此类业务，则不应添加集合点，以免影响测试结果的真实性。
4. 实现方式：在LoadRunner中使用lr_rendezvous("集合点名称")，在JMeter中使用同步定时器（Synchronizing Timer）。
【面试角度】
回答时建议结合实际项目经验，例如描述在某个秒杀项目中如何设置集合点、设置多少并发用户、观察到的系统瓶颈等，能显著提升答案的深度和可信度。
【易错提示】
容易混淆集合点与思考时间（think time）。集合点是同步等待其他用户，用于模拟并发；思考时间是模拟用户操作间隔，用于模拟真实用户行为。两者目的和使用场景完全不同。
```

```text
【易错提示】
```


**答案**

```text
通过逐步增加并发用户数调用接口的方式，找出当前系统环境配置下，最大可接受的并发用户数。
标准是： 1、没有出现连续报错；2、平均响应时间没有超过1.5s；3、服务器资源利用率监控数据，没有超过80%
```

```text
【核心考点】 性能测试 负载测试 性能指标
【题目解析】
本题考察性能测试中负载测试的设计方法和评判标准。负载测试的核心是逐步增加并发用户数，找到系统的性能拐点（即最大可接受并发数），同时监控关键指标。
【参考答案要点】
设计方法：采用阶梯式递增并发用户数（如从10开始，每次增加10），持续运行一段时间（如5分钟），观察系统表现。当出现以下任一情况时，停止增加，当前并发数即为最大可接受值。

1. 错误率：没有出现连续报错（如HTTP 500、超时等），错误率低于1%。
2. 响应时间：平均响应时间不超过1.5秒（可根据业务要求调整）。
3. 资源利用率：CPU、内存、磁盘I/O等关键资源使用率不超过80%。
【面试角度】
回答时应体现实际工具经验（如JMeter、LoadRunner）和指标阈值的设定依据。面试官可能追问“如果响应时间达标但CPU已100%，如何处理？”以考察综合判断能力。
【易错提示】
不要只回答“逐步增加并发”，而忽略具体标准和监控维度。同时，标准应结合业务场景，如金融系统对响应时间要求更高。
```

```text
在性能测试过程中，使用思考时间来描述这段时间。

在 LoadRunner 中主要通过 lr_think_time 函数+RTS 模拟随机思考时间，
在 jmeter 中通过高斯随机定时器来模拟随机思考时间。
思考时间的应用场景一般是构造测试数据接口、混合压测场景、稳定性压测场景
```

**解析**

```text
【核心考点】 性能测试 思考时间 负载模型
【参考答案要点】
1. 定义：思考时间是用户操作间隔，用于模拟真实用户行为，避免服务器压力过于集中。
2. 应用场景：构造测试数据、混合压测、稳定性压测时需加入思考时间；而并发测试或极限测试通常去掉思考时间。
3. 实现方式：LoadRunner中使用lr_think_time函数结合RTS设置随机范围；JMeter中使用高斯随机定时器或均匀随机定时器模拟随机思考时间。
4. 注意事项：思考时间应基于业务分析设定，通常为1-3秒随机变化，避免固定值导致测试失真。
【面试角度】
回答时建议结合实际项目案例，例如“在电商秒杀场景中，我们去掉思考时间模拟高并发；在普通浏览场景中，加入1-3秒随机思考时间模拟真实用户”。同时可提及思考时间对TPS和响应时间的影响，展示对性能测试模型的深入理解。
【延伸知识】
思考时间与Pacing（迭代间隔）的区别：思考时间是用户操作间的停顿，Pacing是迭代间的等待，两者在负载模型中作用不同，面试中可能被追问。
```

## Q005834

- 题型：简答
- 难度：较难

**题目**

```text
金融产品购买的场景中，用户登录之后，购买理财产品，查看交易记录，查看持仓\n和收益的比例为 2:3:4，使用 Jmeter 测试工具进行压力测试时，请问如何控制其比例？
```

**答案**

```text
使用Jmeter脚本实现方法：在采样器的上一级添加“逻辑控制器”－>“如果（If）控制器”：

金融产品购买业务比例，通过添加if逻辑条件：${__counter(true,)}%9<2进行比例控制在22%，即业务比例占整个业务场景的2/9

交易记录查询业务比例，通过添加if逻辑条件：${__counter(true,)}%9<=4&&${__counter(true,)}%9>=2进行比例控制在33%，即业务比例占整个业务场景的3/9

金融产品购买业务比例，通过添加if逻辑条件：${__counter(true,)}%9>4进行比例控制在44%，即业务比例占整个业务场景的4/9

通过在采样器上添加以上三个if逻辑控制器的比例控制，从而达到三种不同业务在整个业务上的比例为2/9:3/9:4/9即：2:3:4。
```

**解析**

```text
【核心考点】 JMeter 压力测试 业务比例控制
【参考答案要点】
使用JMeter的If控制器结合__counter函数实现比例控制：
1. 购买理财产品（比例22%）：在If控制器中设置条件 ${__counter(true,)}%9<2，表示每9次循环中前2次执行此业务。
2. 查看交易记录（比例33%）：条件 ${__counter(true,)}%9>=2 && ${__counter(true,)}%9<=4，对应第3-5次。
3. 查看持仓和收益（比例44%）：条件 ${__counter(true,)}%9>4，对应第6-9次。
通过计数器取模9，将9次循环按2:3:4分配，实现业务比例控制。
【面试角度】
面试官关注对JMeter逻辑控制器的掌握及实际场景的建模能力。可补充说明使用“吞吐量控制器”或“随机顺序控制器”的替代方案，体现思维广度。
【延伸知识】
实际项目中，业务比例可能随时间变化，可考虑使用CSV数据文件动态调整比例，或结合“常数吞吐量定时器”模拟真实用户行为。
```

## Q005804

- 题型：简答
- 难度：未标注
- 解析：AI 补全（原数据缺失解析）

**题目**

```text
如何确定最大可接受并发用户数？
```

**答案**

```text
通过逐步增加并发用户数的方式进行性能测试，观察性能测试的结果，在多少并发用户数前出现连续报错，或在多少并发用户数时的平均响应时间超过1.5s，或在多少并用户数时服务器资源利用率超过80%
```

**解析**

```text
【核心考点】最大可接受并发用户数的判定。
【题目解析】采用逐步加压的方法，持续增加并发用户数并观察结果。出现连续报错，或平均响应时间超过 1.5 秒，或服务器资源利用率超过 80% 时，说明已接近可接受上限，取该点之前的并发数作为最大可接受并发用户数。
【答题要点】
1. 用阶梯加压而非一次性压满。
2. 关注错误率、响应时间和资源利用率。
3. 以多项指标中先触发的阈值作为判断依据。
【面试提示】补充阈值要结合业务和系统基线，不能机械套用固定数值。
```
