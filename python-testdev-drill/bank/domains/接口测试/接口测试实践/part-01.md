## Q004148

- 题型：简答
- 难度：简单

**题目**

```text
JWT token是由那三部分构成
```

**答案**

```text
JWT token的内容主要包含三个部分
1、header(头部)：头部通常用来声明类型和加密算法

2、payload(载荷)：jwt的主要内容部分，包含签发者，所面向的用户、签发时间、过期时间等相关信息

3、signature(签名)：使用header中指定的加密算法，对载荷中的内容进行加密，加密等到的签名
```

**解析**

```text
【核心考点】 JWT Token 认证
【题目解析】
本题考查JWT（JSON Web Token）的基本结构。JWT是一种用于身份认证的令牌，由三部分组成，每部分用点号分隔。
【参考答案要点】
1. Header（头部）：声明类型（typ）和加密算法（alg），例如{"alg": "HS256", "typ": "JWT"}。
2. Payload（载荷）：包含声明信息，如签发者（iss）、用户（sub）、签发时间（iat）、过期时间（exp）等。
3. Signature（签名）：使用header中指定的算法，对header和payload进行加密，防止数据篡改。
【面试角度】
回答时建议结合实际项目中的JWT使用场景，例如“在前后端分离项目中，用户登录后返回JWT token，前端存储并在后续请求中携带”，能体现实战经验。
【易错提示】
注意JWT的payload部分默认是Base64编码，不是加密，敏感信息不应放入payload。签名部分用于验证完整性，但内容仍可被解码读取。
```

## Q004171

- 题型：简答
- 难度：简单

**题目**

```text
你们在做接口测试的过程中，会不会有人把这个接口给改掉的情况？在版本迭代的时候，比如说把接口名字改掉了？
```

**答案**

```text
不会，我们公司的接口是后端开发人员写好封装了的，版本在迭代增加接口时，不会去动之前的接口。而且若动了接口的名字或规则，开发人员会通知全技术人员的，包括产品、前端、测试、运维等。
更改了的接口，前端人员要做重新的调用，测试人员需要维护之前写的接口自动化测试脚本，若是与设备相关的接口，运维人员需要重新写配置文件。改动太大，所以我们公司基本不会对原有接口做修改
```

**解析**

```text
【核心考点】 接口测试 版本迭代 团队协作
【参考答案要点】
在规范的团队中，接口通常遵循向后兼容原则，不会随意修改已有接口。如果确实需要修改（如接口名、参数、返回值），会通过以下流程：
1. 变更通知：开发人员提前通知全技术人员（产品、前端、测试、运维等）。
2. 版本管理：通过接口版本号（如/v1/、/v2/）区分新旧接口，确保旧接口仍可用。
3. 测试维护：测试人员需更新接口自动化脚本，回归验证新接口及受影响功能。
4. 文档同步：更新接口文档，确保各方信息一致。
【面试角度】
回答时强调团队沟通和规范流程的重要性，体现对软件工程的理解。也可补充实际项目中遇到的接口变更案例及处理方式，展示问题解决能力。
```

## Q004189

```text
利用fiddler怎么进行抓包操作的？
```

**答案**

```text
fiddler抓包我们可以用来抓手机端的包，也可以用来抓web端的包；就是设置一个系统代理，让手机/web的流量走fiddler所在的电脑和端口，然后就可以捕获数据包了。
```

**解析**

```text
【核心考点】 Fiddler抓包原理 代理设置

本题考查Fiddler抓包工具的基本原理和使用方法。Fiddler通过设置系统代理，将HTTP/HTTPS流量转发到自身，从而捕获和修改请求/响应数据。对于手机端抓包，需要让手机连接到Fiddler所在电脑的代理端口（默认8888），并安装Fiddler的根证书以解密HTTPS流量。

【面试角度】
```

```text
fiddler抓包过程？设置断点过程？如何模拟界面返回404？
```

```text
1、fiddler抓包我们可以用来抓手机端的包，也可以用来抓web端的包；就是设置一个系统代理，让手机/web的流量走fiddler所在的电脑和端口，然后就可以捕获数据包了。
2、抓到这个请求后，在这个请求前或者响应后打一个断点，请求前做断点可以修改它请求发送之前修改他的数据来进行发送，响应后断点可以修改服务器返回的响应结果进行修改，然后再发送到客户端，察看客户端的显示。
3、设置Rules—>Automatic Breakpoints—>Before Requests
• 然后在界面点击提交订单，看到请求前有红色禁行标识，说明设置了断点，请求被拦截了
• 页面发起请求，看见对应的请求图标有红色禁行标识，表示响应过程已设置断点，此时页面返回的就是404状态
```

**解析**

```text
【核心考点】 抓包工具 Fiddler 断点调试 模拟响应
【题目解析】
本题考查Fiddler抓包工具的核心操作：抓包原理、断点设置和模拟响应。Fiddler作为代理工具，通过设置系统代理拦截HTTP/HTTPS流量。断点功能允许在请求发送前或响应返回后修改数据，用于测试异常场景。模拟404等状态码是测试错误处理能力的常用手段。

2. 设置断点过程：在Fiddler中，通过Rules菜单→Automatic Breakpoints→选择Before Requests（请求前断点）或After Responses（响应后断点）。请求前断点可修改请求数据再发送；响应后断点可修改服务器返回的响应再发给客户端。
3. 模拟界面返回404：在Fiddler中设置响应后断点，拦截目标请求，修改响应状态码为404，然后放行，客户端将收到404错误。

【易错提示】
注意区分请求前断点和响应后断点的用途：请求前用于修改输入，响应后用于模拟异常响应。模拟404时，需确保修改的是响应状态码而非请求URL。
```

```text
【核心考点】 接口自动化测试 覆盖率度量
【题目解析】
本题考查接口自动化测试覆盖率的计算方式。覆盖率是衡量自动化测试充分性的关键指标，但需要明确分母（有效接口总数）和分子（已覆盖接口数）的定义。

· 接口覆盖率：已自动化接口数 / 总接口数。
· 场景覆盖率：已覆盖业务场景数 / 总场景数。

【易错提示】
```

```text
本题考察非对称加密在身份鉴权中的应用。公钥和私钥是一对密钥，公钥公开，私钥保密。鉴权过程通常有两种方式：一是发送方用私钥加密数据，接收方用公钥解密以验证身份（数字签名）；二是接收方用公钥加密数据，仅持有私钥的发送方能解密（加密通信）。题目描述的是数字签名场景，即私钥签名、公钥验签。

2. 鉴权流程：发送方使用自己的私钥对信息进行加密（签名），接收方使用发送方的公钥进行解密（验签），若解密成功，则确认发送方身份。

【面试角度】
```

```text
本题考查接口测试中判断是否存在Bug的基本思路。接口测试的核心是验证请求与响应是否符合预期，以及数据处理的正确性。回答时应从请求本身、响应结果、数据库状态三个层面逐步排查。

```


```text

1. 使用业务编号（nonce）：在接口参数中设置唯一业务编号，每次请求携带，服务端校验是否重复，防止重放攻击。

本题考察接口安全防护策略，核心是防止数据被截包后的恶意提交（如重放、篡改）。业务编号（nonce）是常用手段，结合时间戳和签名可有效防御。此外，HTTPS加密传输是基础保障。
【面试角度】
回答时建议结合实际项目中的安全实践，例如支付接口或登录接口的防重放设计，展示对安全攻防的理解。可补充OAuth2.0或JWT等认证机制，提升答案深度。
【易错提示】
仅依赖HTTPS是不够的，因为中间人攻击或证书伪造可能绕过。业务编号需保证唯一性（如UUID），并设置过期时间，避免内存泄漏。签名算法需保密，防止伪造。
```

```text
首先不仅仅是把bug解决了，甚至流程设计上都要改。
一般提现，首先要在数据库生成提现记录，不管到没到银行卡，都应该即时减去余额。
再根据提现银行打款的状态来更新提现记录的状态，比如到账了，那么更新提现记录状态成功
```

```text
【核心考点】 缺陷分析 业务流程 数据库一致性
【题目解析】
本题考查提现流程中的缺陷分析能力。短信提示到账但余额未减少，表明提现操作在业务逻辑或数据一致性上存在缺陷。核心问题在于余额扣减与提现状态更新的时序或逻辑错误。
【参考答案要点】
1. 流程设计缺陷：提现操作应先在数据库中生成提现记录并即时扣减余额，再根据银行回调更新状态。若先发送短信再扣余额，可能导致短信成功但余额未减。
```

## Q004273

- 题型：简答
- 难度：较难

**题目**

```text
面试问题: 你们请求参数加密是怎么处理的？
```

**答案**

```text
1、通过jmeter里面自带加密函数
这个我主要是通过jmeter里面自带的函数做加密处理的，在jmeter里面通过插件安装用户自定义函数，然后函数助手里面就会有MD5和 base64的两个加密函数，使用者两个就可以了

2、如果加密函数处理不了，开发写代码打jar给我们使用，类似mysql数据库jar包一样
如果是其他的加密方式，我们基本通过我们开发写代码，把代码打成jar包，在测试计划里面导入进来，在beanshell里面通过import导入这个对象，然后调用开发的方法，把明文传入到这个方法里面就可以了，然后通过vars。put
这个值做成变量，jmeter就可以调用
```

**解析**

```text
【核心考点】 JMeter参数加密 接口测试 自定义函数
【参考答案要点】
方法一：使用JMeter内置函数
通过函数助手（Tools → Function Helper Dialog）选择 __MD5、__base64Encode 等函数，直接对参数加密。例如：${__MD5(${password})}。
方法二：开发提供加密JAR包
将开发编写的加密代码打成JAR包，放入JMeter的lib/ext目录，在测试计划中导入。在 BeanShell PreProcessor 或 JSR223 PreProcessor 中通过 import 调用加密方法，将结果存入变量（如 vars.put("encrypted", encryptedValue)），后续请求引用该变量。
【面试角度】
面试官关注实际落地细节：如何与开发协作获取加密算法、JAR包版本管理、加密参数动态拼接（如时间戳+密钥）。建议补充异常处理（如加密失败时的日志记录）和性能影响（加密操作对TPS的影响）。
【延伸知识】
对于更复杂的加密（如RSA、AES），可编写自定义Java请求或使用JSR223调用Groovy脚本。JMeter 5.0+支持直接调用Java类，无需额外插件。加密参数通常配合参数化和断言使用，确保加密结果正确。
```

## Q004245

- 题型：简答
- 难度：未标注
- 解析：AI 补全（原数据缺失解析）

**题目**

```text
接口测试的话，最终的测试结果的确认都会检查哪些？
```

**答案**

```text
首先会检查接口的响应消息是否跟开发文档的要求一致；
其次会查数据库的数据，进行测试结果的确认；
以及会查看日志确认测试结果和定位问题。
```

**解析**

```text
【核心考点】接口测试结果的验证维度。
【题目解析】结果确认不只看响应是否返回成功，还要对照接口文档核对字段、状态码和业务语义；涉及数据写入的，要到数据库确认落库内容和状态流转；出现异常时查看服务端日志，辅助判断是请求问题还是实现问题。
【答题要点】
1. 响应消息与接口文档一致，包括状态码和字段。
2. 数据库数据正确，字段值、关联关系和状态符合预期。
3. 日志可辅助确认执行过程和定位失败原因。
【面试提示】强调响应、数据库、日志三层验证，能体现测试的严谨性。
```
