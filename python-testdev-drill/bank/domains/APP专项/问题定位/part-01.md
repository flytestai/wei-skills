## Q006760

- 题型：简答
- 难度：入门

**题目**

```text
Android四大组件？
```

**答案**

```text
Android四大基本组件：Activity、BroadcastReceiver广播接收器、ContentProvider内容提供者、Service服务。
```

**解析**

```text
【核心考点】 Android基础知识 四大组件
【题目解析】
本题考查Android开发的基础概念，属于记忆性题目。Android四大组件是应用程序的核心构建块，每个组件都有特定的职责。
【参考答案要点】
1. Activity：负责用户界面的展示和交互，是用户可见的组件。每个Activity对应一个屏幕。
2. BroadcastReceiver：广播接收器，用于接收系统或应用发出的广播消息，如电量低、网络变化等。
3. ContentProvider：内容提供者，用于在不同应用之间共享数据，如联系人、短信等。
4. Service：服务，在后台执行长时间运行的操作，不提供用户界面，如音乐播放、文件下载。
【面试角度】
回答时，可以补充每个组件的生命周期或常见使用场景，例如“Activity有onCreate、onStart等生命周期方法，Service有startService和bindService两种启动方式”。这能展示对Android开发的深入理解。
【易错提示】
不要遗漏任何组件，或混淆组件的功能。例如，ContentProvider不是用于存储数据，而是用于数据共享；Service不是线程，而是在主线程中运行，需要手动管理线程。
```

## Q006758

- 题型：简答
- 难度：简单

**题目**

```text
Android Activity生命周期?
```

**答案**

```text
周期即活动从开始到结束所经历的各种状态。生命周期即活动从开始到结束所经历的各个状态。从一个状态到另一个状态的转变，从无到有再到无，这样一个过程中所经历的状态就叫做生命周期。

Activity本质上有四种状态：

1.运行（Active/Running）:Activity处于活动状态，此时Activity处于栈顶，是可见状态，可以与用户进行交互

2.暂停（Paused）:当Activity失去焦点时，或被一个新的非全面屏的Activity，或被一个透明的Activity放置在栈顶时，Activity就转化为Paused状态。此刻并不会被销毁，只是失去了与用户交互的能力，其所有的状态信息及其成员变量都还在，只有在系统内存紧张的情况下，才有可能被系统回收掉

3.停止（Stopped）:当Activity被系统完全覆盖时，被覆盖的Activity就会进入Stopped状态，此时已不在可见，但是资源还是没有被收回

4.系统回收（Killed）:当Activity被系统回收掉，Activity就处于Killed状态
```

**解析**

```text
【核心考点】 Android Activity生命周期
【题目解析】
本题考查Android开发中Activity的基本概念和状态转换。Activity是Android应用的核心组件，其生命周期管理对资源优化和用户体验至关重要。题目要求描述Activity的生命周期，即从创建到销毁过程中经历的各种状态。
【参考答案要点】
1. 运行状态（Active/Running）：Activity处于栈顶，可见且可与用户交互。
2. 暂停状态（Paused）：Activity失去焦点但部分可见，如被非全屏或透明Activity覆盖，此时不销毁但无法交互。
3. 停止状态（Stopped）：Activity完全不可见，但状态信息保留。
4. 销毁状态（Destroyed）：Activity被系统回收或主动结束。
【面试角度】
回答时建议结合实际开发场景，例如在暂停状态下保存用户输入数据，或利用生命周期方法（如onPause、onResume）优化资源管理，能体现工程实践能力。
【易错提示】
注意区分暂停和停止状态：暂停时Activity部分可见，停止时完全不可见。面试中常混淆这两个状态，需重点记忆。
```

## Q006780

- 题型：简答
- 难度：简单

**题目**

```text
如何分析一个bug是前端还是后端的
```

**答案**

```text
这种情况很容易判断，先抓包看请求报文，对着接口文档，看请求报文有没问题，有问题就是前端发的数据不对
请求报文没问题，那就看返回报文，返回的数据不对，那就是后端开发的问题咯
```

**解析**

```text
【核心考点】 Bug定位 前后端分离
【题目解析】
本题考查测试人员如何区分Bug是前端还是后端问题。核心方法是抓包分析请求和响应。
【参考答案要点】
1. 抓包分析请求：使用Fiddler、Charles等工具捕获HTTP请求，对比接口文档。
- 若请求报文（URL、参数、Header）与文档不符，则为前端Bug。
- 若请求报文正确，继续分析响应。
2. 分析响应：检查返回数据是否与预期一致。
- 若响应数据错误或状态码异常，则为后端Bug。
- 若响应正确但页面显示异常，则为前端渲染Bug。
【面试角度】
回答时建议补充实际案例，如“某次接口返回正确但页面空白，发现是前端未处理空数据”，能体现问题分析能力。
【易错提示】
注意前后端联调时，可能双方都有问题，需逐步排查。另外，网络问题（如超时）不属于前后端Bug。
```

## Q006801

- 题型：简答
- 难度：简单

**题目**

```text
请说明Android手机和IOS手机，系统有什么区别？
```

**答案**

```text
两者运行机制不同：IOS采用的是沙盒运行机制，安卓采用的是虚拟机运行机制;
两者后台制度不同：IOS中任何第三方程序都不能在后台运行；安卓中任何程序都能在后台运行，直到没有内存才会关闭。
IOS中用于UI指令权限最高，安卓中数据处理指令权限最高。
```

**解析**

```text
【核心考点】 移动端测试 Android vs iOS 系统差异
【参考答案要点】
1. 运行机制：iOS采用沙盒运行机制，每个应用独立运行在沙盒中；Android采用虚拟机运行机制，应用运行在Dalvik/ART虚拟机上。
2. 后台机制：iOS中任何第三方程序都不能在后台运行（除特定服务如音乐、定位）；Android中任何程序都能在后台运行，直到内存不足才会被关闭。
3. 权限优先级：iOS中UI指令权限最高，Android中数据处理指令权限最高。
【面试角度】
回答时建议结合测试实践，例如“在iOS上测试后台切换时，应用状态更易被系统回收，需要关注数据持久化；Android则需要关注多任务下的内存泄漏问题”。
【延伸知识】
iOS 13+开始对后台限制有所放宽，Android从8.0开始也加强了对后台服务的限制，了解这些演进有助于展现知识深度。
```

## Q006755

- 题型：简答
- 难度：中等

**题目**

```text
APP 测试常见的严重问题有哪些？ 分别引起的原因有哪些？
```

**答案**

```text
常见的有 crash、ANR（应用无响应、卡死），一般由设备碎片化、网络波动大、内存泄漏、代码编写错误。
```

**解析**

```text
【核心考点】 APP测试 严重问题 Crash ANR
【题目解析】
本题考查移动应用测试中常见的严重问题及其根因分析。Crash和ANR是APP最严重的两类问题，直接影响用户体验和留存率。测试人员需要理解其产生原因，以便有效复现和定位。
【参考答案要点】
1. Crash（崩溃）：应用意外退出。常见原因：内存泄漏、空指针异常、资源未释放、第三方SDK兼容性问题、设备碎片化导致的代码执行异常。
2. ANR（应用无响应）：主线程被阻塞超过5秒。常见原因：网络请求在主线程执行、大量IO操作、死锁、数据库操作耗时过长。
3. 其他严重问题：数据丢失、闪退、界面错乱、功能不可用等，多由代码逻辑错误或兼容性问题引起。
【面试角度】
回答时建议结合实际测试经历，例如描述一个复现Crash的案例，以及如何通过日志和工具（如Logcat、adb）定位问题。面试官可能追问如何预防ANR，可提及使用异步任务、优化主线程操作等。
【延伸知识】
除Crash和ANR外，APP测试还需关注：内存泄漏（使用LeakCanary检测）、UI卡顿（使用Systrace分析）、耗电、网络异常等。掌握这些有助于全面覆盖质量风险。
```

## Q006756

- 题型：简答
- 难度：中等

**题目**

```text
APP某个功能失效了，如何排查是App客户端还是服务端的问题？
```

**答案**

```text
1. 检查客户端网络是否有问题，可以查看其他APP能否正常使用
2. 检查是否为版本问题，可以换个操作系统（安卓、ios），或者换个其他软件版本试试
3. 检查是否为兼容性问题，可以换个手机试试
4. 抓包分析，如果APP没有向服务器发送请求，或者请求参数不对，就是APP的问题；如果服务端响
应数据不对，就是服务端的问题
```

**解析**

```text
【核心考点】 问题定位 客户端与服务端
【参考答案要点】
1. 网络检查：检查客户端网络连接是否正常，可尝试其他APP验证。
2. 版本检查：尝试不同操作系统或软件版本，排除版本问题。
3. 兼容性检查：更换不同手机或设备，排除兼容性问题。
4. 抓包分析：使用抓包工具（如Fiddler、Charles）分析请求和响应。若APP未发送请求或参数错误，则为客户端问题；若服务端响应数据错误，则为服务端问题。
【面试角度】
回答时建议结合实际项目经验举例，例如“在项目中，我曾通过抓包发现服务端返回了错误的状态码，从而定位到后端问题”，能体现实战能力。
【延伸知识】
除了抓包，还可以使用日志分析、性能监控工具（如APM）辅助定位，面试中可提及以展示全面性。
```

## Q006762

- 题型：简答
- 难度：中等

**题目**

```text
android 和ios 测试区别？
```

**答案**

```text
1、安装测试
测试版本安装

Android非常简单，提供一个apk包，就可以在任何设备上安装这个APP并进行测试了；

iOS比较复杂一些，没有经过苹果审核是不允许安装的；所以需要安装测试版本，就需要采取一些额外的手段，比如手动添加UDID到开发者账号，或者使用testflight工具，具体操作，可以见之前的一篇文章【附上之前文章的链接】
线上版本安装

Android可以上传的应用商店比较多，比如谷歌商店，360商店，安智市场等，还有各大应用管家都可以上传并提供给广大android用户下载使用；所以，测试人员对Android应用的线上测试需要覆盖所有支付的渠道；

iOS众所周知，只有一个苹果官方的App Store可以下载安装应用，其他的渠道都是不允许的。因为需要上传到线上发布，是需要苹果进行审核和授权的，而且一般审核周期要等到3天-2周不等。所以，iOS测试人员，需要等到苹果审核通过之后，从App Store上下载应用，验证线上版本的可用性。
2、兼容性测试
Android

因为系统被开源，很多不同厂商在这个基础上二次进行开发，所以导致出现的操作系统类型以及版本都非常多，比较常见主流的有：华为、小米、OPPO，Vivo等，还有很多比较小众非主流的操作系统；而且每个系统都有很多的版本，包括大版本和小版本；以及每个厂商的手机屏幕大小也差异比较大，所以Android APP的兼容性测试就会比较复杂一些；
iOS

就只有单一的苹果系统，虽然也经常更新版本，但是随着苹果官方系统版本的升级，一般我们只需要维护最新的几个主流版本的兼容性测试即可；选取的主流系统版本，再覆盖iOS的几款主流的屏幕大小的机型，兼容性测试会相对来说简单很多。
2、升级测试

升级测试ios限制也比Android多一些。

iOS有严格的降级限制，最开始只能单向升级，不能降级；虽然松懈了一点可以做降级操作，但是也限制了特定机型的最低降级版本，比如iPhone X最多只能降到iOS 11.2，iPhone 5最多可以降到iOS 6.1.3，之所以有这个限制其实是因为通常新的ios系统版本中的资源库不能完全兼容低版本中的应用，低版本ios系统中的应用如果调用了新系统中的资源库，有时会直接导致闪退（Crash）出现；所以，我们做iOS的升级测试的时候，基本只需要关注对应的版本之间的升级即可。

Android系统的降级限制没有那么严格，通过一定的工具都可以降级成功。
3、权限测试

Android众所周知的就是Android的个人信息泄露比较严重的，比如很多app在安装时会要求很多权限，Android系统会提示是否允许获取手机的某个权限，但是即使用户不给，Android也有各自手段偷偷的获取这些权限，所以Android APP的这种权限测试不是很严苛；

而ios一般情况下权限管理的很严格，用户没有同意的权限，APP是一定没有办法绕过并获取的，所以应用不会去获取一些没有意义的权限；而且应用要上线苹果商店时，苹果官方的审核机制也是比较严格，经常会出现审核不通过的情况。所以ios的权限一般情况下会要的很少。因此，iOS测试的权限场景较少，但是会很严格。
4、应用实现的机制

Android采用的虚拟机机制，而iOS采用的是沙盒机制。

虚拟机机制的特点是：

每个应用程序都在独立的虚拟机中，这些独立的虚拟机实例都是一个独立的进程空间。
跟linux内存管理很相似，是真正的多进程管理，虽然可用内存最后看着少，但是实际上很多程序已经分配了一定的内存了，在唤起时不会再次分配一次，而且已经有了缓存，启动和响应会比较快。

沙盒机制的特点是：

应用程序在自己的沙盒中运作，但是不能访问任何其他应用程序的沙盒；
应用之间不能共享数据，沙盒里的文件不能被复制到其他应用程序的文件夹中，也不能把其他应用文件夹复制到沙盒中；
3）苹果禁止任何读写沙盒以外的文件，禁止应用程序将内容写到沙盒以外的文件夹中；

5、安全机制

iOS安全机制主要通过一下两个方面来实现：

通过刚刚上面讲到的**“安全沙箱**” 机制来实现安全机制。应用之间数据和文件不能共享；
通过对代码签名，Apple需要所有开发人员对自己的iPhone应用程序使用数字签名技术。这个签名用来标识应用程序的开发者以及保证应用程序在签名之后不被更改和损坏。开发者证书由Apple提供（这是与android最大的区别，android是自签名），有以下两类证书：

Developer Certificate ：用于本机测试

Distribution Certificate ：用于100台设备以内的测试和共享；App Store用于发布应用程序所有的可执行文件、库文件都需要Apple签名后才可以运行在iOS中。

Android安全机制通过以下两个方面来实现：

虚拟机机制，每一个Android应用程序（apk文件）会在安装时分配一个独有的linux用户ID（即一个用户id识别一个应用程序），使其不能与其他应用程序进行接触。这个用户ID在安装时分配，并在该设备上一直保持同一个数值。所有存储在应用程序中的数据都会赋予该应用程序的用户ID，使其他应用程序无法访问这些数据。
代码签名，但是跟iOS不一样的是，Android采用自签名机制，不需要权威机构签名和审核，完全由用户自行判断是否信任该程序。
```

**解析**

```text
【核心考点】 移动端测试 Android vs iOS
【题目解析】
本题考查Android和iOS两大移动平台在测试方面的核心差异，涉及安装方式、分发渠道、测试工具等方面，是移动测试面试的常见问题。
【参考答案要点】
1. 安装测试差异：
Android：提供APK包即可在任何设备安装，测试版本安装简单，无需审核；线上版本可上传至多个应用商店（如Google Play、360、安智等），测试需覆盖所有支付渠道。
iOS：测试版本安装复杂，需通过TestFlight或添加UDID到开发者账号，受苹果审核限制；线上版本仅通过App Store分发，支付渠道单一（Apple Pay或内购）。
2. 其他差异：Android设备碎片化严重，需覆盖不同品牌、系统版本和屏幕尺寸；iOS设备相对统一，但需关注不同iOS版本兼容性。
【面试角度】
回答时建议结合实际项目经验，例如在测试Android应用时如何选择覆盖的机型，或使用TestFlight进行iOS内测的具体步骤，体现对移动测试流程的熟悉度。
【延伸知识】
移动测试还需关注：推送通知机制（Android使用FCM，iOS使用APNs）、后台运行策略、权限管理等，这些也是面试中可能深入追问的点。
```

## Q006776

- 题型：简答
- 难度：较难

**题目**

```text
假设一个刚升级的APP有用户反馈功能，上线后有一个用户反馈说能下载能安装，能用，但就是很卡，要从哪些方面考虑是什么原因？
```

**答案**

```text
1、是当前升级的这个反馈功能操作很卡，还是整个app操作都很卡？
如果是只反馈功能很卡，那可能原因：
1）反馈提交的资源过大，导致请求过慢

2)服务器对于当前请求的人数过多，导致卡

2、如果是整个app操作都很卡，可能原因：
1）网络异常

2)app占用内存大，导致手机内存不足

3)当前app与其他软件、手机系统不兼容

4）服务器资源不足，导致请求过慢
```

**解析**

```text
【核心考点】 性能测试 问题定位
【参考答案要点】
需要从两个维度分析：
1. 仅反馈功能卡顿：可能原因包括反馈提交的资源过大（如上传大图片或视频），导致请求过慢；或服务器处理请求时并发量高，响应延迟。
2. 整个APP卡顿：可能原因包括网络异常（如弱网或高延迟）；APP占用内存过大，导致手机内存不足；APP与其他软件或手机系统不兼容；服务器资源不足，导致请求响应慢。

【延伸知识】
除了上述原因，还需考虑APP版本兼容性、后台服务日志分析、用户设备环境（如低端机型）等因素，全面排查问题。
```

## Q006793

- 题型：简答
- 难度：较难

**题目**

```text
怎么判断前台的错误还是后台的错误？
```

**答案**

```text
如果这个bug是界面排版布局错误，像兼容性问题，则很明显是前端bug；
而对于数据或逻辑处理上的问题，则可以通过抓包工具或者查看日志来进一步确认问题，
用抓包工具的话，网站项目的话可以通过F12，移动端app项目通过fiddler
1）检查接口地址、传参正确性，若不正确，则为前端bug；若正确则进一步检查接口响应，若响应回的内容不正确，则可能是后端处理出错；可以查看报错日志、查看数据库数据判断哪一层面的问题
2）如果接口传参、响应的数据都正确，那就是前端渲染响应的数据出错，则前端bug
也通过查看日志来定位，查看前端传递请求数据是否正确，不正确，前端问题；请求正确，则查看返回数据，返回数据正确的话，那前端问题，获取数据后渲染到前端界面错误；如果返回数据错误，那么就是服务器端问题，进一步确认是否数据库表数据的正确性，是本身数据库表数据错误还是表数据正确，返回错误
```

**解析**

```text
【核心考点】 Bug定位 前后端分离 抓包工具
【参考答案要点】
1. 界面类Bug：如排版、兼容性、样式问题，通常直接判定为前端Bug。
2. 数据/逻辑类Bug：通过抓包工具（如Fiddler、浏览器F12）或日志分析定位：
- 检查请求的接口地址和传参是否正确：若错误，则为前端Bug；若正确，则继续检查响应数据。
- 若响应数据错误，则可能是后端处理出错，需查看后端日志和数据库。
- 若请求和响应均正确，但页面显示异常，则为前端渲染Bug。
3. 日志辅助：查看前端控制台日志和后端服务器日志，可快速定位异常堆栈。
【面试角度】
面试官期望看到系统化的排查思路，建议回答时按“界面→请求→响应→渲染”的顺序逐步缩小范围，并举例说明实际项目中如何通过抓包定位Bug。
【延伸知识】
在微服务架构中，Bug可能涉及多个服务间的调用链，需借助分布式追踪工具（如Jaeger、Zipkin）定位。
```

## Q006796

- 题型：简答
- 难度：较难

**题目**

```text
有一个app的登录页面输入账号密码后报错，但只出现一次，假设是万分之一的概率怎么复现并定位问题?
```

**答案**

```text
首先在问题出现的时候可以抓包看前端的请求和后端的响应，做出前端问题和后端问题的初步判断；
然后结合数据库确认数据是否入库，是否数据库有问题；
并在后台服务器收集项目的日志，帮助开发去修复bug；
把以上新信息都提供给开发，并提交bug；
因为无法复现，开发可以现根据以上信息尝试修复；测试同时也进行同步跟踪和尝试复现。要持续跟踪多个版本。
```

**解析**

```text
【核心考点】 缺陷定位 偶发问题 问题复现
【题目解析】
本题考查对偶发、低概率问题的处理能力。这类问题难以复现，需要结合多种手段收集信息，辅助开发定位，并持续跟踪。
【参考答案要点】
1. 初步判断：使用抓包工具（如Fiddler）查看前端请求和后端响应，判断是前端还是后端问题。
2. 数据库验证：检查数据是否正确入库，确认数据库层面是否异常。
3. 日志收集：收集后台服务器日志，查找错误信息或异常堆栈，提供给开发。
4. 提交缺陷：将收集到的信息（抓包、日志、数据库状态）详细记录并提交，即使无法复现。
5. 持续跟踪：开发根据信息尝试修复，测试在后续版本中持续关注，尝试复现。
【面试角度】
回答时可结合实际案例，如“我曾遇到一个偶发登录失败问题，通过抓包发现是特定网络延迟导致的”，能体现问题解决能力。
【易错提示】
不要只强调“无法复现”就放弃，要主动收集信息并推动解决，体现测试的主动性。
```
