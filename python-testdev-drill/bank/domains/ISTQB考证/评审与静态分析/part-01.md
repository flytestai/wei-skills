## Q006297

- 题型：单选
- 难度：简单

**题目**

```text
“向评审参与者解释评审的目标”属于下列哪个阶段的主要活动：
```

**选项**

```text
A. 计划阶段
B. 预备会阶段
C. 个人准备阶段
D. 评审会议阶段
```

**答案**

```text
B
```

**正确选项**

```text
B. 预备会阶段
```

**解析**

```text
【核心考点】 评审过程 软件评审阶段
【题目解析】
本题考查软件评审的各个阶段及其主要活动。评审通常包括计划、预备会、个人准备、评审会议、返工和跟踪等阶段。其中，“向评审参与者解释评审的目标”属于预备会阶段的活动，旨在确保所有参与者理解评审目的和范围。
【选项解析】
✗ A. 计划阶段 — 错误。计划阶段主要确定评审范围、时间表和资源，不涉及向参与者解释目标。
✓ B. 预备会阶段 — 正确。预备会阶段向参与者介绍评审目标、流程和角色，确保准备充分。
✗ C. 个人准备阶段 — 错误。个人准备阶段参与者独立审查材料，不进行集体解释。
✗ D. 评审会议阶段 — 错误。评审会议阶段主要讨论和发现缺陷，目标已在预备会中明确。
【易错提示】
注意区分预备会阶段和评审会议阶段：预备会用于统一认知，评审会议用于深入讨论。面试中常混淆这两个阶段的活动。
```

## Q006298

- 题型：单选
- 难度：简单

**题目**

```text
下列不属于正式审查的方式是（）。
```

**选项**

```text
A. 同事审查
B. 公开陈述
C. 检验
D. 编码标准和规范
```

**答案**

```text
D
```

**正确选项**

```text
D. 编码标准和规范
```

**解析**

```text
【核心考点】 软件审查类型
【题目解析】
本题考查软件审查的分类。正式审查（如审查会议）有结构化流程和角色分工，非正式审查（如同事审查、编码规范检查）更灵活。公开陈述属于正式审查的一种，通常有演示和评审环节。
【选项解析】
✓ D. 编码标准和规范 — 正确。编码标准和规范检查通常是非正式的，由工具或同事执行，不属于正式审查。
✗ A. 同事审查 — 错误。同事审查（Peer Review）可以是正式或非正式，但通常归类为非正式审查，但本题问“不属于正式审查”，需注意题干陷阱。
✗ B. 公开陈述 — 错误。公开陈述（Walkthrough）是正式审查的一种，由作者向团队演示并收集意见。
✗ C. 检验 — 错误。检验（Inspection）是最严格的正式审查，有明确角色和检查清单。
【易错提示】
注意区分“正式审查”与“非正式审查”。同事审查可灵活归类，但编码标准和规范通常自动化或非正式，故D为最佳答案。面试中常混淆Walkthrough和Inspection，需牢记其正式程度差异。
```

## Q006299

- 题型：单选
- 难度：简单

**题目**

```text
下列关于静态测试的描述中，哪一个是错误的？
```

**选项**

```text
A. 结合合适的流程，静态测试可以用来起到缺陷预防作用
B. 静态测试可以发现动态测试难以发现的问题
C. 静态测试因为可以早期发现缺陷，所以可以达到节省成本的效果
D. 静态测试是一种好的使软件产生失效的办法
```

**答案**

```text
D
```

**正确选项**

```text
D. 静态测试是一种好的使软件产生失效的办法
```

**解析**

```text
【核心考点】 静态测试 测试基础
【题目解析】
本题考查静态测试的基本概念。静态测试是指不执行程序代码的测试活动，包括代码审查、走查、静态分析等。其目的是发现缺陷、预防缺陷，而非使软件失效。动态测试才是通过执行代码来发现失效。
【选项解析】
✓ A. 结合合适的流程，静态测试可以用来起到缺陷预防作用 — 正确。静态测试在早期发现缺陷，有助于预防后续阶段的问题。
✓ B. 静态测试可以发现动态测试难以发现的问题 — 正确。例如代码逻辑错误、编码规范问题等，动态测试可能遗漏。
✓ C. 静态测试因为可以早期发现缺陷，所以可以达到节省成本的效果 — 正确。缺陷发现越早，修复成本越低，这是测试经济学的基本原则。
✗ D. 静态测试是一种好的使软件产生失效的办法 — 错误。静态测试不执行代码，不会导致软件失效。失效是动态测试的结果。
【易错提示】
注意区分“缺陷”与“失效”：静态测试发现缺陷，动态测试导致失效。混淆这两个概念是常见错误。面试中常通过类似判断题考察对测试基础概念的掌握。
```

## Q006303

- 题型：单选
- 难度：简单

**题目**

```text
下面不属于评审的好处的是？
```

**选项**

```text
A. 增加测试的时间
B. 尽早发现和修复缺陷
C. 改善开发能力，缩短开发时间
D. 缩减测试成本
```

**答案**

```text
A
```

**正确选项**

```text
A. 增加测试的时间
```

**解析**

```text
【核心考点】 软件评审 测试管理
【题目解析】
本题考查评审（Review）在软件测试中的价值。评审是一种静态测试技术，通过同行检查发现缺陷，主要好处包括早期发现缺陷、提高质量、减少返工成本，但不会直接增加测试时间或缩短开发时间。
【选项解析】
✗ A. 增加测试的时间 — 错误。评审本身是测试活动的一部分，其目的是提高效率，而非单纯增加时间。
✓ B. 尽早发现和修复缺陷 — 正确。评审可在需求或设计阶段发现缺陷，降低后期修复成本。
✗ C. 改善开发能力，缩短开发时间 — 错误。评审能提升团队能力，但主要目标不是缩短开发时间，而是提高质量。
✗ D. 缩减测试成本 — 错误。评审可能增加前期投入，但通过早期发现缺陷可降低整体成本，并非直接缩减测试成本。
【易错提示】
注意区分“评审的好处”与“测试的好处”，评审侧重于预防缺陷，而非加快进度或直接省钱。
```

## Q006312

- 难度：简单

**题目**

```text
为了改进项目，公司准备引入一种工具支持。哪一种工具可以帮助被审查代码的高质量?
```

**选项**

```text
A. 评审工具
B. 测试执行工具
C. 静态分析工具
D. 测试设计工具
```

**答案**

```text
C
```

**正确选项**

```text
C. 静态分析工具
```

**解析**

```text
【核心考点】 静态分析工具 代码审查
【题目解析】
本题考查测试工具的分类及适用场景。代码审查旨在发现代码缺陷和规范问题，静态分析工具无需执行代码即可检查，适合支持审查活动。
【选项解析】
✗ A. 评审工具 — 错误。评审工具用于管理审查流程（如会议、文档），但不直接分析代码质量。

✓ C. 静态分析工具 — 正确。静态分析工具（如SonarQube、Checkstyle）通过分析源代码发现潜在缺陷、代码异味和规范问题，直接提升代码质量。
✗ D. 测试设计工具 — 错误。测试设计工具辅助生成测试用例，不直接审查代码。
【易错提示】
静态分析工具与评审工具易混淆：静态分析是自动化代码检查，评审工具是流程管理，面试时需明确区分。
```

## Q006313

- 题型：简答
- 难度：简单

**题目**

```text
什么是走读？
```

**答案**

```text
是一个类似于评审的过程，参与者包括了产品、开发、测试等。
```

**解析**

```text
【核心考点】 软件评审 走读 静态测试
【参考答案要点】
走读（Walkthrough）是一种非正式的评审技术，通常由作者主导，向评审团队逐步介绍工作产品（如代码、设计文档、测试用例等），参与者包括产品经理、开发人员、测试人员等。其特点是：
1. 非正式性：没有严格的流程和角色分工，重在知识传递和问题发现。
2. 作者主导：由工作产品的作者进行讲解，参与者提问和反馈。
3. 多角色参与：产品、开发、测试等利益相关方共同参与，确保多视角审视。
【面试角度】
回答时建议补充走读与正式评审（如审查）的区别，例如：走读更灵活、成本低，适合早期发现明显问题；审查则更正式、角色明确，适合关键交付物。结合项目实际场景能提升答案深度。
【延伸知识】
ISTQB 将评审分为正式评审（审查、技术评审）和非正式评审（走读、结对评审）。走读常用于代码走读和需求走读，是敏捷开发中常用的轻量级质量保证手段。
```

```text
D. 为评审计划了足够的时间
```

**答案**

```text
C
```

**正确选项**

```text
C. 因为评审中发现大量问题项目经理责令作者修改
```

```text
【核心考点】 评审过程 质量管理

【易错提示】
注意题干问的是“不属于”成功关键因素。C选项看似合理，但强制修改违背了评审的协作精神，正确做法是记录问题并协商解决。
```

## Q006329

- 题型：单选
- 难度：简单

**题目**

```text
技术评审的目的是：
```

**选项**

```text
A. 保证软件在独立的模式下进行开发
B. 发现软件业务的错误
C. 与项目管理无关
D. 确认软件符合预先定义的开发规范和标准
```

**答案**

```text
D
```

**正确选项**

```text
D. 确认软件符合预先定义的开发规范和标准
```

**解析**

```text
【核心考点】 技术评审 软件质量保证
【题目解析】
技术评审（Technical Review）是软件质量保证活动的一部分，旨在检查软件产品（如需求文档、设计文档、代码等）是否符合预先定义的规范和标准，从而尽早发现缺陷并确保产品质量。它不直接涉及开发过程的管理或业务错误的发现。
【选项解析】
✗ A. 保证软件在独立的模式下进行开发 — 错误。技术评审不关注开发模式，而是关注产品本身的质量。
✗ B. 发现软件业务的错误 — 错误。发现业务错误是测试或业务评审的目标，技术评审更侧重于技术规范和标准符合性。
✗ C. 与项目管理无关 — 错误。技术评审是项目管理中质量控制的一部分，但并非其核心目的。
✓ D. 确认软件符合预先定义的开发规范和标准 — 正确。这是技术评审的核心目的，确保产品符合既定规范。
【易错提示】
技术评审与测试（发现业务错误）容易混淆，注意区分：评审是静态分析，测试是动态执行。
```


```text
A. 经理;
```

```text
C
```

```text
C. 主持人
```

```text
【核心考点】 正式评审角色 评审流程
【题目解析】
本题考查软件评审过程中各角色的职责。正式评审（如技术评审、走查）通常包括经理、作者、主持人、记录员、评审员等角色。题目中描述的职责是“负责策划评审、召开会议和会议后的跟踪”以及“需要的时候，进行不同观点之间的协调”，这符合主持人（Moderator）的职责。主持人负责组织整个评审活动，确保会议高效进行，并在出现分歧时进行协调。

✗ D. 记录员 — 错误。记录员负责记录会议中的问题和决策，不负责策划和协调。

注意区分主持人和记录员的职责：主持人负责流程和协调，记录员负责记录。面试中常混淆这两个角色。
```
