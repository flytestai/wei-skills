## Q007070

- 题型：简答
- 难度：较难

**题目**

```text
RAG 场景中你发现“召回很多但命中不准”，请设计一套检索策略与召回评测方法，能够定位问题并指导优化。
```

**答案**

```text
我会先把评测目标从“数量”切换到“有效性”。第一步定义问题类型，区分事实问答、流程问答、参数问答和长文定位，不同类型对召回策略的要求不同。第二步建立金标评测集，为每个问题标注应命中的文档片段和可接受证据范围，避免只看主观感觉。第三步拆解检索链路，分别评估召回器、重排器和查询改写模块，统计 Recall@K、MRR、NDCG、引用覆盖率和最终回答准确率，识别瓶颈位置。第四步做策略对照，比较向量检索、关键词检索和混合检索在不同题型下的表现，并测试阈值、topK、重排窗口对质量和时延的影响。第五步验证抗噪能力，加入同义词、歧义词、长尾表达和拼写错误样本，观察模型是否仍能找到关键证据。第六步落地治理，按题型配置检索策略并建立版本回放机制，任何策略更新都需通过基线集。这样评测结果既能解释“为什么不准”，也能直接指导优化方向。
```

**解析**

```text
高质量回答会同时覆盖离线指标和端到端效果。常见误区是只提高 topK，导致噪声上升而准确率不升反降。
```

## Q007071

- 题型：简答
- 难度：较难

**题目**

```text
企业希望上线知识问答系统服务测试团队，你负责给出可落地的测试方案。请说明你的实施阶段、验收标准和风险控制点。
```

**答案**

```text
我会按“可用、可控、可运营”三阶段推进。第一阶段先验证基础可用，确保文档入库、索引构建、检索与回答链路打通，重点看回答是否能引用正确证据，避免无依据输出。第二阶段强化质量控制，构建分层评测集覆盖高频问题、歧义问题、边界问题和过期信息，持续评估准确率、拒答合理性、引用一致性和稳定性。第三阶段建设运营能力，接入监控告警、版本管理、回滚机制和人工复核入口，保证系统在文档更新和模型升级后仍可控。风险控制方面，我会设置发布闸门：关键题型不达标不放量，证据不足必须拒答，异常波动触发自动降级。协作机制上，建立业务与测试共同维护的反馈闭环，把线上错误样本回灌评测集。通过分阶段实施与数据化验收，问答系统才能从演示能力变成可长期依赖的生产能力。
```

**解析**

```text
回答重点不是“怎么做一个聊天窗口”，而是如何保证上线后持续可靠。可补充你会如何设计人工复核和降级触发规则。
```

## Q007072

- 题型：简答
- 难度：较难

**题目**

```text
你如何设计“测试经验资产化与知识库结构”，既保证检索命中率，又避免知识快速过时？
```

**答案**

```text
我会先明确资产化目标：不是存文档，而是让经验能被检索、被复用、被验证。第一步定义最小知识单元，每条知识至少包含场景、触发条件、步骤、断言、证据、结论、适用边界。第二步做元数据建模，统一业务域、系统版本、风险等级、来源、更新时间、责任人、可用状态，支持多维过滤和排序。第三步设计分层结构：规范层放长期稳定原则，策略层放方法模板，案例层放真实问题及解决路径，脚本层放可执行产物。第四步做更新与退役机制，新增知识必须有来源和评审，过期知识通过时效规则自动降权，连续低命中或低采纳条目进入归档。第五步提升检索命中率，可结合关键词检索+向量召回+重排策略，并引入术语同义词表，解决“同义词搜不到”。第六步建立质量评测，核心指标包括命中率、采纳率、回答准确率、知识老化率、人工修订成本。第七步闭环运营，用户每次引用后都要反馈有效性，系统据此更新权重。最后强调治理边界：敏感信息脱敏、权限分级、访问审计必不可少。这样才能避免知识库沦为“文档墓地”，真正成为团队质量生产力。
```

**解析**

```text
重点看是否能同时回答“如何建”和“如何活”，即结构设计与持续运营并重。
```

## Q007073

- 题型：简答
- 难度：较难

**题目**

```text
你要为企业内网知识库问答做端到端验收，目标是证明“可查、可答、可追溯、可回归”。请给出完整测试链路与关键指标。
```

**答案**

```text
我会沿诊断链做端到端验收，先定义四个目标：可查、可答、可追溯、可回归。可查阶段验证文档入库完整性、切分质量和索引构建时效；可答阶段验证多轮问答准确率、引用一致性、拒答合理性；可追溯阶段要求每次回答能回看到检索片段、模型版本和参数；可回归阶段把历史缺陷样例固化成自动回放。提出假设后，我会构造分层数据：标准FAQ、长文档细节、歧义问题和过期信息，覆盖常见失败模式。执行时使用统一观测模板记录链路时延、命中位置、上下文利用率和人工复核结论。对关键异常做复现实验，如知识库热更新、索引重建中断、模型回滚，验证系统恢复能力。最终我会输出验收报告与上线门槛，并建立周度回归，确保后续文档增量和模型升级不会破坏已达成质量。
```

**解析**

```text
面试官更看重你是否能把“端到端”拆成可执行检查点。常见问题是只讲问答准确率，没有链路追踪和回归机制。可延伸说明异常注入怎么做、如何让业务方参与人工复核与阈值确认。
```

## Q007074

- 题型：简答
- 难度：较难

**题目**

```text
你要落地一个基于文档知识的问答能力，第一版经常因为切分策略不合理导致关键信息丢失。请说明你的分阶段优化方案。
```

**答案**

```text
我会把问题拆成三个阶段推进。第一阶段先做数据基线，统一文档清洗规则、编码格式和元数据标签，确保后续切分与向量化输入质量一致，避免脏数据放大误差。第二阶段聚焦切分策略，分别验证固定长度、语义分段、标题层级分段和滑窗重叠等方案，评估召回率、片段完整性、上下文冗余和索引体积，选出适配业务语料的默认策略。第三阶段优化向量化与检索联动，调整嵌入模型、topK、重排和阈值，让检索片段既相关又不过长，避免上下文被无效信息挤占。第四阶段做端到端回归，用标准问答集验证最终准确率、引用命中率和拒答质量，并对高风险问题建立专项测试集。最后把所有配置版本化，升级时先离线评测再灰度上线。这样可以让 RAG 链路从“能答”逐步进化到“答得准、答得稳、可追溯”。
```

**解析**

```text
不要只回答“调 chunk 大小”，应体现数据治理、检索评测与上线流程。若能提到配置版本化和灰度验证，工程意识更强。
```

## Q007075

- 题型：简答
- 难度：较难

**题目**

```text
在使用 ChromaDB 做向量检索时，如何平衡召回效果、存储成本与查询时延？请给出你的测试与优化方法。
```

**答案**

```text
我会先用数据说话，而不是凭经验调参数。第一步做数据分层，按文档类型、长度、更新频率和业务价值分类，决定不同数据采用不同切分与索引策略。第二步建立检索评测集，覆盖高频问答、长尾问答、歧义表达和噪声输入，评估 Recall@K、MRR、引用命中率和最终回答准确率。第三步做性能压测，观察不同向量维度、批量写入大小、索引参数和并发量下的查询延迟、吞吐和资源占用。第四步进行成本分析，比较全量实时索引与冷热分层索引的存储开销和更新时效，找出性价比最优组合。第五步引入混合检索和重排机制，减少单纯扩大 topK 带来的噪声。第六步形成配置版本与回滚机制，任何参数调整都先离线验证再灰度发布。通过“质量指标+性能指标+成本指标”联合评估，才能让向量检索在生产中长期稳定，而不是阶段性最优。
```

**解析**

```text
高分点是同时考虑质量、时延、成本三维。常见误区是只追召回率，忽视噪声增长和资源成本。
```

## Q007076

- 题型：简答
- 难度：较难

**题目**

```text
某RAG问答系统命中率下降，业务反馈“明明文档里有答案却答不出来”。请说明你会如何验证嵌入模型与召回策略，并定位问题根因。
```

**答案**

```text
我会按诊断链把问题拆成“索引前、检索中、生成后”三段。第一步先确认现象：是完全召回不到，还是召回到了但排序靠后，或生成阶段忽略证据。第二步提出假设：文档切分粒度不合适、嵌入模型与语料领域不匹配、topK设置偏小、重排器失效、查询改写质量差。第三步采证：构建带标准答案的检索评测集，记录每次查询的召回片段、相似度分布、重排前后排名变化。第四步实验：对比不同切分策略、嵌入模型、topK与阈值组合，并同时观测召回率、MRR、上下文长度占用和最终回答准确率。第五步结论闭环：把最优组合固化为默认策略，对长尾问题加查询扩展与同义词库，并建立版本对比面板。这样我不仅能找到“答不出来”的具体环节，还能持续跟踪召回质量是否回升，避免问题反复出现。
```

**解析**

```text
好的回答会把问题分层到检索链路，不把所有责任都推给模型。常见失误是只看最终答案准确率，忽略中间召回证据。建议补充离线评测与线上监控如何打通，以及版本回滚策略。
```

## Q007077

- 题型：简答
- 难度：较难

**题目**

```text
知识库频繁更新后，用户反馈回答质量波动明显。你要负责召回测试与版本管理，请描述你的诊断与治理方案。
```

**答案**

```text
我会采用诊断链把“质量波动”定位到具体版本与环节。先确认现象：是某类问题下降，还是全局下降；是召回不足还是回答偏离。再提出假设：可能由文档切分策略变化、嵌入模型替换、索引构建失败或版本混用导致。证据采集上，我会建立版本快照机制，记录每次更新的文档集、分块参数、向量模型和索引时间戳，并对同一查询在不同版本做回放对比。实验阶段执行离线评测与线上抽样双轨验证，关注召回率、相关性、引用命中率和回答稳定性。结论落地时我会定义发布闸门：新版本必须超过基线且高风险场景不退化，未达标则自动回滚。同时建立增量回归集和变更审计流程，确保每次更新可追责、可解释。这样既能提升知识库迭代速度，也能避免“更新越多质量越不稳”的问题。
```

**解析**

```text
关键在于把波动问题和具体版本绑定，形成可回放证据。常见失误是只做主观体验比较，没有基线和闸门。可继续说明版本审计字段怎么设计、如何处理增量更新与全量重建的选择。
```
