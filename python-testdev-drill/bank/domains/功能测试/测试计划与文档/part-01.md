## Q000012

- 题型：单选
- 难度：入门

**题目**

```text
一个软件需求项可以对应一个/多个/甚至数十个系统测试项目。
```

**选项**

```text
A. 对
B. 错
```

**答案**

```text
A
```

**正确选项**

```text
A. 对
```

**解析**

```text
【核心考点】 需求与测试用例关系
【题目解析】
本题考查软件需求项与系统测试项目之间的对应关系。在软件测试中，一个需求项可能对应多个测试项目，因为需要从不同角度（如功能、性能、边界等）进行验证，甚至可能对应数十个测试项目，以充分覆盖需求。
【选项解析】
✓ A. 对 — 正确。一个软件需求项可以对应一个、多个甚至数十个系统测试项目，这取决于需求的复杂度和测试的充分性要求。
✗ B. 错 — 错误。该说法否认了需求与测试项目之间的多对多关系，不符合实际测试实践。
【易错提示】
本题为判断题，容易误以为需求与测试项目是一一对应关系。实际上，一个需求通常需要多个测试用例来覆盖，包括正常流程、异常流程、边界条件等，因此对应多个测试项目是常见情况。
```

## Q000033

- 题型：简答
- 难度：入门

**题目**

```text
什么是测试环境？
```

**答案**

```text
答案：完成软件测试工作所必需的计算机硬件、软件、网络设备、历史数据的总称。测试环境是模拟真实用户使用环境而配置。
```

**解析**

```text
【核心考点】 测试环境概念 测试基础
【题目解析】
测试环境是软件测试的基础设施，包括硬件、软件、网络和数据等组件，目的是模拟真实用户环境以验证系统功能、性能和稳定性。面试中常作为基础概念题，考察对测试环境组成和重要性的理解。
【参考答案要点】
1. 定义：测试环境是执行测试所需的硬件、软件、网络设备、历史数据等资源的总称，用于模拟真实用户使用环境。
2. 组成：包括操作系统、数据库、中间件、应用服务器、网络配置、测试数据等。
3. 重要性：环境配置错误可能导致测试结果失真，如生产环境与测试环境差异过大时，性能测试结果不可信。
4. 管理：需进行版本控制、配置管理和定期维护，确保环境稳定性。
【面试角度】
回答时建议结合实际项目经验，例如“在项目中，我们使用Docker容器化测试环境，确保环境一致性”。同时可提及环境隔离（如开发、测试、预发布环境分离）的重要性。
【延伸知识】
现代测试环境管理趋势包括基础设施即代码（IaC，如Terraform）、持续集成中的环境自动部署（如Jenkins Pipeline），以及云环境（如AWS Device Farm）的使用。
```

```text
提测标准通常包括：代码编译通过、单元测试通过率≥80%、核心功能无阻塞缺陷、接口文档完整等。不同公司可能有细化要求。
```

- 难度：入门

**题目**

```text
功能测试里用例一般包含哪些内容？
```

**答案**

```text
核心内容：
用例编号、标题、前提条件、测试步骤、预期结果、用例优先级、所属模块、输入数据等
```

**解析**

```text
【核心考点】 测试用例设计 用例要素
【题目解析】
本题考查测试用例的基本组成要素。功能测试用例是测试执行的基础，标准化的用例结构有助于提高可读性和可维护性，是测试工程师必须掌握的内容。
【参考答案要点】
功能测试用例通常包含以下核心内容：
1. 用例编号：唯一标识，便于管理和追溯。
2. 标题：简洁描述测试场景。
3. 前提条件：执行用例前需满足的环境或数据状态。
4. 测试步骤：详细的操作步骤。
5. 预期结果：期望的系统行为或输出。

【易错提示】
注意区分测试用例与测试场景，用例更具体，场景更宏观；用例必须包含预期结果，否则无法判断测试通过与否。
```

## Q000122

- 题型：简答
- 难度：入门

**题目**

```text
在整个测试的过程中，你们提交了哪些交付物？
```

```text
测试计划、测试用例、buglists、用例执行结果、测试报告、测试通过后的版本/代码
```

**解析**

```text
【核心考点】 测试交付物 测试文档
【题目解析】
本题考查测试过程中需要产出的文档和交付物。测试交付物是测试工作成果的体现，也是项目管理和质量保证的重要依据。面试中常作为基础问题，考察候选人对测试流程的熟悉程度。
```

```text
试的地址等等
```

```text
【核心考点】 提测流程 测试管理工具
```

- 题型：简答
- 难度：简单

**题目**

```text
一个完整的测试流程包括哪些？测试人员需要做什么？
```

**答案**

```text
1、需求交接
当一个需求确认后，产品经理一般会把需求说明书发给开发和测试人员，然后三方讨论需求，进行需求交接。这个非常重要，因为需求不明确，后续工作开展起来会有很大麻烦。

2、编写测试用例
需求确定后，测试人员就要开始编写测试用例了。
首先是梳理全部测试点。当然，这步并不是必须的。梳理全部测试点相当于是梳理一个框架，一方面，根据这个框架写测试用例，可以防止编写测试用例时丢失测试点；另一方面，项目经理会根据你的全部测试点去排期，安排人员和时间。
然后是编写测试用例。编写测试用例要尽可能的用最少的用例覆盖最多的测试点。编写测试用例的工具也有多种，要以公司使用的为准。编写测试用例最好是跟你的前辈去要一个模板，因为大家已经熟悉他们的测试用例风格，如果你是新人，尽管你的测试用例很棒，但是由于大家不熟悉你的写作方式，很可能会大打折扣。

3、冒烟测试
开发进行开发联调后，测试人员就开始正式介入了。进行联调后，测试人员首先要进行冒烟测试。好多不规范的公司会跳过冒烟测试，直接进行下一环节。如果冒烟测试不通过的话，会打回，也就是重新进入开发联调阶段。如果顺利通过，开发就会开始部署，进行下一步了。
新人可能会问：冒烟测试怎么测？这个时候，你就要明白，冒烟测试的目的就是为了保证主流程顺利通过。也就是说，你只要测试主流程就可以，或者说执行测试用例中优先级为1的测试用例。

4、SIT测试
SIT测试主要包括两轮测试：第一轮执行用例，回归bug；第二轮是系统回归测试。
也就是说，这个阶段的测试，就是你一条一条执行测试用例，遇到bug提交给开发，开发修改后要去回归bug。注意，也许当前bug的修复会引起别的bug，这个时候不要着急去关闭bug，要大致的点一点其他功能，确保没有问题后才去关闭。
这个阶段，需要同步进行的是，修改调整测试用例。测试用例是在开发还没开发完成的时候写的，会有些微的出入，在执行测试用例的时候，要进行修改，同时也会有遗漏的地方，要及时的加入测试用例中。
当所有的测试用例执行完成，所有bug都关闭掉后，要系统的再进行一边测试。SIT测试结束的标志就是覆盖率和通过率达到100%。

5、数据升级测试（视情况而定）
数据升级测试一般是在SIT测试后，也可在SIT测试的后期进行。数据升级测试不是都需要这一步的，如果需求分析中确认需要进行数据升级，就安排。

6、系统培训（视情况而定）
系统培训主要是针对客户的，为了让客户更快的熟悉系统，会由测试人员和产品共同商定，向培训对象分发操作手册，进行系统培训。

7、UAT测试
UAT测试就不仅仅是有测试人员，同时要包括业务人员一起测试。最终由客户验收，验收成功，开发会进行封版。封板之后，代码不会再进行更改。

8、上线
上线之后，测试人员还要进行上线验证。注意：这是生产环境，这个时候是不能随便操作做数据的，测试人员能做的也就是点点，保证按钮、界面正常。如果是业务人员做好数据，测试人员要验证数据的准确性和界面显示无误。
上线验证后，这个需求就算结束了。
```

**解析**

```text
【核心考点】 软件测试流程 测试活动
【参考答案要点】
1. 需求交接：产品经理确认需求后，组织开发、测试三方讨论，确保需求明确，避免后续返工。
2. 编写测试用例：先梳理全部测试点（形成框架），再基于测试点编写用例，力求用最少用例覆盖最多测试点，并参考公司模板和前辈经验。
【面试角度】
回答时建议结合实际项目经历，例如“在XX项目中，需求交接时我们通过评审会澄清了3个模糊点，后续用例设计效率提升20%”，能体现流程理解和实践能力。
【延伸知识】
完整测试流程通常还包括：测试计划、测试执行、缺陷跟踪、测试报告等阶段。面试中可补充说明测试人员在不同阶段的角色，如计划阶段评估工作量、执行阶段记录缺陷等。
```

## Q000011

- 题型：简答
- 难度：简单

**题目**

```text
一个测试报告的组成应该包括哪些方面？
```

**答案**

```text
测试报告编写包括：测试范围、测试环境、测试用例覆盖率，通过率，执行率，bug的统计与分析，遗留的bug，风险有哪些，版本测试评估，发布的建议等
```

**解析**

```text
【核心考点】 测试报告 测试文档
【题目解析】
本题考查测试报告的组成要素。测试报告是测试工作的总结，需包含测试范围、环境、用例覆盖率、通过率、执行率、缺陷统计与分析、遗留缺陷、风险评估、版本评估和发布建议等。回答时需全面列出关键部分，并说明其作用。
【参考答案要点】
1. 测试范围：被测功能模块及版本。
2. 测试环境：硬件、软件、网络配置。
3. 测试执行情况：用例总数、通过率、执行率。
4. 缺陷统计：按严重程度、模块、状态分类的缺陷分布。
5. 遗留缺陷：未修复缺陷及影响分析。
6. 风险评估：未覆盖或高风险区域。
7. 测试结论与建议：版本是否可发布，改进建议。
【易错提示】
不要遗漏风险评估和发布建议，面试中常要求结合实际项目说明报告如何辅助决策，如根据缺陷趋势判断是否延期发布。
```

## Q000014

- 题型：简答
- 难度：简单

**题目**

```text
一个项目大概多少测试用例，bug大概有多少？
```

**答案**

```text
按照项目的功能去合计算下，以物业项目为例：
不太记得具体数据了，项目总共是x(2000~3000去选某个值)多条用例吧。最近的迭代版本写了x(200~300去选某个值)多条用例；

一天写多少，没具体算过，看项目需求复杂度，一天x(50~100)条；
执行的用例，主要是这次迭代版本负责的x(100~200)多条；
bug有x(30~50)多个。
```

**解析**

```text
【核心考点】 测试用例规模估算 缺陷密度
【题目解析】
本题考查测试工程师对项目测试规模的宏观认知。面试官通过询问用例数和Bug数，评估候选人对项目复杂度的理解、数据敏感度以及是否具备实际项目经验。回答时应基于真实项目经验，给出合理范围，并强调数据因项目而异。
【参考答案要点】
1. 总用例数：以物业项目为例，总用例约2000-3000条，覆盖核心功能模块和边界场景。
2. 迭代用例数：最近迭代版本新增约200-300条用例，针对新功能和回归测试。
3. 日写用例数：视需求复杂度而定，平均每天约50-100条。
4. 执行用例数：本次迭代负责约100-200条用例的执行。
5. Bug数量：发现约30-50个Bug，其中严重级别Bug占比约10%-20%。
【面试角度】
回答时建议结合实际项目背景，如项目类型、团队规模、测试周期等，并说明估算依据。例如：“总用例数约2500条，因为项目包含10个主要模块，每个模块约250条用例。” 避免给出绝对数值，强调“因项目而异”。
【易错提示】
不要给出过于夸张或模糊的数据，如“几万条用例”或“没统计过”。面试官期望看到候选人对测试工作量的量化能力。
```

## Q000026

- 题型：简答
- 难度：简单

**题目**

```text
与开发人员如何进行有效的沟通的
```

**答案**

```text
沟通的时候最好遵循五要四不要原则，分别是哪四不要和五要呢？
五要
1、要耐心和细心
细心是测试工程师的一个基本素质，测试工程师是对质量负责的人，涉及到质量问题，就不能含糊，因此一定要细心，细心对待每一个可能的Bug，细心对待每一个你撰写的Bug报告，细心的跟开发阐述你的观点。细心是一种态度，你的态度迟早会感染和你合作的开发人员，而这往往是合作愉快的基础。
至于说到耐心，在我的工作经历中，不厌其烦地向开发人员解释一个Bug，让他认识到Bug的重要性是经常的事情，其实想想也很正常，对任何人来说，被人指出自己的缺点和不足都不是让人舒服的事情，因此，一点不耐烦的情绪就可能引起对方很大的反感，给自己的工作带来不必要的麻烦。
2、要懂得尊重对方
开发是一件需要全面和综合考虑的工作，开发工作中，由于各种原因导致程序中出现问题是很正常的现象，作为测试工程师，发现了这些问题并不值得你夸耀，也不能 说明你比开发工程师聪明。一个好的测试工程师一定是懂得尊重开发工程师的人，尊重对方的技术水平，尊重对方的代码。我接触过的开发人员都是挺和善的，一般来说，对他们最大的尊重就是承认他的专业水平，承认他的代码。对他们来说，代码就像是自己的孩子一样。因此，记得在合适的时候表达你对他的尊重，赞扬一下他代码的精妙之处。
3、要能设身处地为对方着想
开发工程师一般都处在较大的工作压力下，他的上司直接考核他们的指标很大程度上是已完成的代码，所以在工作任务紧张的时候，对于测试工程师报上来的Bug会 拖延解决甚至是推脱，给测试工程师的感觉就是很不合作。那么在这个时候，就需要设身处地的为对方着想了，每个人都会为自己的工作在内心排定优先级，如果他 认为解决你发现的Bug不是重要的事情，那么最大的可能就是你并没有向他解释清楚这个Bug的严重程度。
发现Bug是我们的责任，阐述Bug得到解决是我们更重要的责任，因此，我们可以心平气和地和开发人员坐下来讨论一下Bug的严重程度，和他一起排定Bug的优先级别并确定解决的时间。
4、要有原则
不要忘记，测试工程师需要对产品的质量负责，在这一点上一定要有原则。测试工程师可以和开发工程师建立良好的个人关系，但在具体的事情上，一定要按照公司的 相关流程来处理。当然，在坚持原则的同时，可以采用一些委婉的表达方式，可以在允许的情况下尽量体谅开发工程师，但请记住，一个有原则的测试工程师才能真 正帮助开发工程师，才能赢得开发工程师的尊重。
5、要主动承担
如果开发工程师要求你承担部分不属于你的责任，比如，定位你发现的Bug到代码一级，或者是帮助他编写部分文档和代码（不要不相信，真的有这样的事情），那么你会怎么做呢？
在我的测试经历中，这些事情都遇到过，我的原则是在可能的情况下尽量多承担。其实都是工作上的事情，有能力的话，多做一点也无妨。当然， 肯定有人不同意我的意见，在这里我也不想争辩，个人意见而已，仅供参考。
在我的测试经历中，我会根据自己的进度和时间安排尽可能地提供更多的关于Bug的参考意见，甚至是定位到代码一级，这种方式不是正规的方式，但对于提高自己被信任的程度是非常有益的。但在主动承担时，一定要明确是在自己确有余力的情况下才能去承担，否则，婉拒是最好的对策。
四不要
1、不要嘲笑
不要嘲笑你所发现的Bug，即使是非常愚蠢的错误也绝对不要嘲笑，说不定那个错误是因为开发工程师联系加班24小时犯下的，对别人的工作始终应该尊重。如果 你觉得有必要提醒他不再犯一些经常犯的错误，可以采用这样的方式：编写一份测试过程中发现的开发人员常犯错误的文档（记住，千万不要写上谁犯了这些错 误），用轻松的口气调侃一下，发送给开发人员。这种方法我采用过，开发人员都能很快接受。
2、不要在背后评论开发工程师
永远不要在背后评论开发工程师的技术能力，这个绝对是非常忌讳的事情，一时的口舌之快或许会使你永远不再能同他良好地合作，要知道，开发工程师最在意地就是别人对他的技术能力的评价。其实这个不仅仅是作为测试工程师的准则，也应该是做人的准则。
3、不要动辄用上层来压制对方
在出现和对方的意见分歧的时候，应该采用什么方式说服对方呢？
直接向上层求助当然是一个办法，但这种办法带来的负面左右也是很明显的，首先是作为上层的处理 结果可能不一定符合你的愿望（在很多公司，开发工程师的地位高于测试工程师的地位，这种地位的不平等导致上层在处理分歧时会有一定的偏向性）；其次是动辄 拿出上层来压制对方只能给他人留下无用的印象。所以在出现分歧时，尽量尝试通过沟通解决吧，实在不行，再动用最后的手段。
4、和开发人员的沟通不要只有Bug
除了在Bug记录单上，在其它的地方也让和你合作的开发工程师接触到你吧，午餐或是集体活动的时候多和对方聊聊天，一方面可以增进彼此的感情，混个脸熟，打交道的时候也方便；另一方面，从他那里了解业务的知识和他负责模块的方方面面，对自己也是提升。开发工程师其实一 般都是比较健谈的，尤其是对自己程序的精妙之处，多了解一些，多接触一些，对自己总是有益的。可以在沟通中了解到开发的一个逻辑，或者在后续的测试中可以帮助自己总结测试逻辑和经验
写了这么多，其实关键的就是两点：多从别人的角度去想想，所谓“换位思考”，多尊重对方就一定能得到对方的尊重与配合；其次是加强和开发工程师的沟通，让他清楚地认识到你的工作对他的价值，你发现的每一个Bug的重要性。
```

**解析**

```text
【核心考点】 沟通技巧 团队协作
【参考答案要点】
五要：
1. 要耐心和细心：细心对待每个Bug，耐心向开发解释问题，避免因情绪影响合作。
2. 要客观描述：基于事实和数据描述缺陷，避免主观评价。
3. 要换位思考：理解开发的工作压力，用建设性语气沟通。
4. 要明确优先级：清晰标注Bug严重程度，帮助开发合理安排修复顺序。
5. 要持续跟进：跟踪缺陷状态，及时反馈验证结果。
四不要：
1. 不要指责：避免使用“你错了”等负面语言，聚焦问题本身。
2. 不要模糊：Bug报告应包含复现步骤、环境、预期/实际结果等细节。

【面试角度】
回答时建议结合实际项目案例，例如“在一次版本发布前，我通过耐心沟通推动开发修复了一个隐藏较深的Bug”，能体现沟通能力和责任心。
```

## Q000075

- 题型：简答
- 难度：简单

**题目**

```text
你公司的测试流程是怎么样的？
```

**答案**

```text
1、测试参与需求评审，明确需求的问题，熟悉需求规格说明书
2、测试老大编写测试计划，测试计划中会安排测试内容、时间进度、任务分配以及使用工具和环境配置。然后召集组内成员进行评审，让组员明确测试进度和任务安排
3、测试人员根据测试计划安排进行测试用例设计，输出测试用例文档，组内会开展用例评审会议，评审后会对用例进行修改，对于修改的部分会再次评审，评审通过后归档保存
4、开发发版后，测试提测，在服务器上进行测试环境的部署
5、然后进行新版本的冒烟测试 ，把主流程及核心功能跑一遍，没有问题则可以进入正式测试，如有冒烟测试不通过，则直接打回开发，让开发修改后再次发版
6、正式测试：根据测试用例执行详细的测试，测试过程中有发现bug，就将bug提交到禅道并进行跟踪处理
7、开发修复bug后，测试人员会进行回归测试，验证bug是否有修复。已修复则关闭bug，这个过程会循环多次
8、最后测试用例都执行完了， bug开发修复完了，那么测试负责人会出具测试报告，来评估测试质量 ，并给出是否达到了上线的标准的结论
9、如果测试报告通过，则发布上线
```

**解析**

```text
【核心考点】 软件测试流程 测试生命周期
【题目解析】
本题考察对标准测试流程的熟悉程度。面试官通过此问题评估候选人是否具备规范的测试思维，以及是否了解从需求到上线的完整环节。回答应逻辑清晰、步骤完整。
【参考答案要点】
1. 需求评审：测试人员参与需求评审，明确需求细节，提前发现歧义或遗漏。
2. 测试计划：测试负责人制定测试计划，明确范围、资源、时间、工具和环境，并组织评审。
3. 测试设计：根据需求编写测试用例，进行用例评审，修改后归档。
4. 环境部署：开发提测后，测试人员部署测试环境，确保环境可用。
5. 冒烟测试：执行核心功能冒烟测试，通过则进入正式测试，否则打回开发。
6. 正式测试：按测试用例执行，提交缺陷并跟踪，进行回归测试。
```

```text
【参考答案要点】
1. 测试需求分析：由产品经理、开发和测试共同参与需求评审，明确测试范围。

4. 测试执行：由测试成员搭建环境、执行冒烟测试和系统测试，提交并跟踪缺陷。
```

## Q000213

- 题型：简答
- 难度：简单

**题目**

```text
测试流程。
```

**答案**

```text
首先就是要做需求评审，作为一名测试人员，要先对你所测试的项目有深入的了解，这样才能发掘测试点，编写测试用例；

第二就是要编写测试用例，测试用例要应用自己所知道的测试方法，再结合需求的实际场景来编写；

第三就是做用例评审（这个不是必需，根据项目大小来看），用例评审听取研发和产品的意见，可能可以发现更多的测试点，完善你的测试用例；

第四就是待项目提测后介入测试，根据编写的测试用例去执行用例；

第五在执行用例过程后发现了Bug，提交给研发，研发改好了，再进行回归测试；

第六在当前功能所有Bug解决（或剩余Bug确认延期）后就会提交到上线前的分支，再在上线前的分支进行系统测试；

第七验收测试（如有需要），一般对于一个大的项目来讲，会有多个项目组，每个组都会有自己的开发和测试分支，然后会合并到一个最终分支进行整体测试，然后还会有一个回归测试组专门做验收！

验收测试完成后，进入到第八个步骤：线上冒烟测试，所有功能部署到生产环境后，进行主要功能的冒烟。然后整个测试的流程就算是结束了。
```

**解析**

```text
【核心考点】 软件测试流程 测试生命周期
【题目解析】
本题为基础题，考查测试工程师对标准测试流程的理解。回答需覆盖从需求评审到上线验收的全过程，体现流程的完整性和规范性。
【参考答案要点】
1. 需求评审：深入了解项目需求，发掘测试点。
2. 编写测试用例：结合测试方法和实际场景设计用例。
3. 用例评审（可选）：听取研发和产品意见，完善用例。
4. 测试执行：项目提测后，按用例执行测试。
5. Bug提交与回归：发现Bug后提交，开发修复后回归测试。
6. 系统测试：所有Bug解决后，在上线前分支进行系统测试。
7. 验收测试：如有需要，进行验收测试确认功能符合需求。
【易错提示】
不要遗漏需求评审和用例评审环节，这些是保证测试质量的关键。面试中建议结合实际项目经验说明，例如“在XX项目中，通过用例评审发现了多个遗漏场景”。
【延伸知识】
不同公司测试流程可能略有差异，但核心阶段一致。了解敏捷测试流程（如Scrum中的迭代测试）也是加分项。
```

## Q000219

- 题型：简答
- 难度：简单

**题目**

```text
测试生命周期、测试过程分为几个阶段，以及各阶段的含义？
```

**答案**

```text
一、计划--问题的定义及规划
主要确定软件的开发目的及其可行性。制定项目总体开发计划。
二、需求分析
在确定软件开发可行的情况下，对软件需要实现的各个功能进行详细分析,明确客户的需求，输出需求规格说明书(+原型图)，提交评审。 召开需求评审会议。
三、设计
把需求分析得到的结果转换为软件结构和数据结构，形成系统架构。
概要设计：主要是架构的实现，指搭建架构、表述各模块功能、模块接口连接和数据传递的实现等项事务。
详细设计：对概要设计中表述的各模块进行深入分析等，出具伪代码。其中需要包含数据库设计说明。
四、编码
按照详细设计好的模块功能表，开发人员编写出计算机可运行的程序代码
五、软件测试
在软件设计完成后要经过严密的测试，以发现软件在整个设计过程中存在的问题并加以纠正。
测试的方法主要有白盒测试跟黑盒测试。建立详细的测试计划并严格按照计划进行。
六、运行维护
软件维护是软件生命周期中持续时间最长的阶段。在软件开发完成并投入使用后，由于多方面的原因，软件不能继续适应用户的需求。要延续软件的使用寿命，就必须对软件进行维护。软件的维护主要包括纠错性维护和改进性维护两个方面。
```

**解析**

```text
【核心考点】 软件测试生命周期 软件开发流程
【题目解析】
本题考查软件测试生命周期或软件开发流程的基本阶段划分。通常软件测试过程与开发过程紧密相关，常见的阶段包括：计划、需求分析、设计、编码、测试、部署和维护。本题答案中描述了前五个阶段，但缺少明确的测试阶段细节，需补充测试执行、缺陷跟踪和测试总结等内容。
【参考答案要点】
1. 计划阶段：定义问题、确定可行性、制定项目计划。
2. 需求分析阶段：分析用户需求，输出需求规格说明书和原型图，进行需求评审。
3. 设计阶段：包括概要设计（架构、模块接口）和详细设计（伪代码、数据库设计）。
4. 编码阶段：开发人员根据设计编写代码。
5. 测试阶段：执行测试用例、记录缺陷、跟踪修复、输出测试报告。
6. 部署与维护阶段：软件上线后持续监控和修复问题。
【面试角度】
回答时建议结合实际项目经验，例如“在测试阶段，我们使用JIRA管理缺陷，并定期召开缺陷评审会”，以体现实践能力。
【易错提示】
常见错误是遗漏测试阶段或混淆开发与测试阶段。注意测试阶段不仅包括执行，还包括计划、设计、总结等子阶段。
```

## Q000312


```text
3.测试计划主要包含测试的目的与范围、角色与职责、资源及安排、风险与应对、测试标准等相关信息，而测试方案主要包含测试方法、测试环境与测试工具等内容。
```

```text
【核心考点】 测试计划 测试方案 测试文档
【参考答案要点】
1. 性质不同：测试计划是管理型文档，测试方案是技术型文档。
```
