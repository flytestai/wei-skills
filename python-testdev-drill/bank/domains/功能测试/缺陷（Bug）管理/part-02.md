## Q001162

- 题型：简答
- 难度：中等

**题目**

```text
列举测试中出现的bug
```

**答案**

```text
1、输入框为空/最大值判断;为空、最大值显示
设计时，应统一规范规则，特别是输入框最大值。还有内容为空时页面如何展示。一般会出现文字内容过多或为空时，页面排版错乱。以及内容为空时，会显示：NULL。
图片数据为空，会保留为空的图片数据位置。
链接为空时，点击图片，会刷新页面。
服务端部分字段为空，整个页面出现空白。

2、重复性判断
比如身份证号，手机号等唯一性的值，提交时应有重复性的判断。如导入时手机号重复，用户的部分信息应更新显示为最新的数据。

3、输入框文本内容判断未加限制
像手机号不能输入非数字以外的字符，长度的限制；这些在输入或者提交的时候应加判断，不允许非法输入。

4、接口传值有误：
经常遇见的问题有：值为空，未获取到值；传值错误，值显示其他字段值。

5、判断顺序/逻辑缺陷
对界面进行多个输入判断的时候，非常容易出现这种问题。例如判断年月顺序，判断长度，判断非空等。假如操作员仅仅满足单个条件，保存不能成功;而按界面从上之下顺序一一满足条件之后，保存是没有问题的。但是，改变一下输入的次序，校验失效。
输入框判断应按控件顺序从上往下，经常遇到先判断下面输入框合法性，再判断上面输入框的合法性的问题。不符合用户的操作习惯。

6、多地点登录/单点登录
设计时应考虑是否允许多点登录。例如涉及到用户提交数据以及订单购买的功能，应只允许用户单点登录。

7、信息同步
网站+APP+微信数据未同步。

8、兼容性问题
经常会出现不同平台的浏览器，功能、样式问题。
PC与手机浏览器，同段代码会展示不同的样式。
不同的手机，弹窗处理机制会不一样，导致有些手机点击弹窗按钮，弹窗不会出现同个功能在不同的浏览器上面，功能会出现失效的现象。

9、功能未实现或只实现了部分/功能实现错误
这类问题在测试过程中也经常出现，交测试的版本有的只实现了部分功能，未实现产品需求说明书里的全部功能，或者功能与需求不一致，测试时流程走不通，这一般都是开发没有自测引起的。

10、第三方应用，访问网页
第三方应用分享，微信、QQ、微博三种分享渠道，有三种不一样的分享机制。经常出现微信能分享，而QQ不能分享的问题。

11、图片能否正常显示及压缩问题

12、不同设备的界面显示问题
```

**解析**

```text
【核心考点】 Bug类型与场景 测试思维
【题目解析】
本题要求测试人员列举实际测试中发现的Bug，考察对常见缺陷类型的归纳能力和测试经验。答案从输入框边界、数据唯一性、输入校验、接口传值等角度展开，体现了功能测试和异常场景的覆盖。
【参考答案要点】
1. 输入框边界问题：如空值或超长文本导致页面排版错乱、显示NULL或空白，需统一规范。
2. 数据重复性判断：如身份证号、手机号等唯一字段，提交或导入时应有重复校验，并合理更新显示。
3. 输入框文本内容未加限制：如手机号允许输入非数字字符或超长，需在前端或后端做校验。
4. 接口传值错误：前后端字段不匹配或参数缺失，导致功能异常。
【面试角度】
回答此类问题时，建议结合实际项目案例具体描述Bug发现过程、影响及修复验证，展现测试深度和问题分析能力。
【易错提示】
避免只罗列Bug类型而不举例，面试官更关注测试思维和场景覆盖的全面性。
```

## Q001166

- 题型：简答
- 难度：中等

**题目**

```text
发现的缺陷越多，说明软件缺陷越多吗?
```

**答案**

```text
这是一个比较常见的现象。测试工程师在没有找到缺陷前会绞尽脑汁的思考，但是找到一个后，会接二连三的发现很多缺陷，颇有个人成就感。其中的原因主要如下：

　
-代码复用、拷贝代码导致程序员容易犯相同的错误。类的继承导致所有的子类会包含基类的错误，反复拷贝同一代码意味可能也复制了缺陷。

　
-程序员比较劳累是可以导致某些连续编写的功能缺陷较多。程序员加班是一种司空见惯的现象，因此体力不只时容易编写一些缺陷较多的程序。而这些连续潜伏缺陷恰恰时测试工程师大显身手的地方。

　
“缺陷一个连着一个”不是一个客观规律，只是一个常见的现象。如果软件编写的比较好，这种现象就不常见了。测试人员只要严肃认真的测试程序就可以了。
```

**解析**

```text
【核心考点】 缺陷分析 测试心理学
【题目解析】
本题考查对缺陷发现现象的理解，属于中等难度。题目答案解释了“缺陷一个连着一个”的常见原因，包括代码复用、拷贝代码导致的错误传播，以及程序员疲劳导致的连续缺陷。但需注意，这并非客观规律，而是常见现象。
【参考答案要点】
1. 代码复用和拷贝：程序员容易复制相同代码，导致缺陷传播。类的继承会使子类包含基类错误。
2. 程序员疲劳：加班导致体力不支，连续编写功能时容易产生多个缺陷。
3. 并非规律：如果软件质量较好，这种现象不常见。测试人员应严肃认真测试，不必过度解读。
【面试角度】
回答时建议结合实际项目案例，例如“在某项目中，我们发现多个缺陷集中在同一模块，经分析是开发人员连续加班导致”，能体现分析能力。
【延伸知识】
缺陷聚集现象也常与模块复杂度相关，高复杂度模块缺陷密度更高。测试时应对高风险模块重点测试，并推动开发改进代码质量。
```

## Q001168

- 题型：单选
- 难度：中等

**题目**

```text
发现错误多的模块，残留在模块中的错误也多（）
```

**选项**

```text
A. 对
B. 错
```

**答案**

```text
A
```

**正确选项**

```text
A. 对
```

**解析**

```text
【核心考点】 缺陷分布规律 帕累托原则
【题目解析】
本题考查软件测试中缺陷分布的经典规律。根据软件工程经验，缺陷往往呈集群现象，即少数模块集中了大部分缺陷，且发现错误多的模块，残留错误也往往更多。
【选项解析】
✓ A. 对 — 正确。缺陷集群性表明，错误密集的模块通常代码复杂度高、逻辑混乱，残留缺陷概率更大，测试时应重点关注。
✗ B. 错 — 错误。该说法与软件工程实践和统计规律相悖。
【易错提示】
本题容易误选“错”，因为直觉上可能认为发现错误多意味着测试充分，残留错误少。但实际规律是：错误多的模块往往质量差，残留错误也多，这体现了帕累托原则（80/20法则）在缺陷分布中的应用。
```

## Q001170

- 题型：简答
- 难度：中等

**题目**

```text
可采取哪些方法来分离和再现软件缺陷？
```

**答案**

```text
1，确保所有的步骤都被记录；
2，注意时间和运行条件上的因素；
3，注意软件的边界条件、内容容量和数据溢出的问题；
4，注意事件发生次序导致的软件缺陷；
5，考虑资源依赖性和内存、网络、硬件共享的相互作用；
6，不要忽视硬件。
```

**解析**

```text
【核心考点】 缺陷管理 缺陷复现
【题目解析】
本题考查软件测试中分离和再现缺陷的系统性方法。缺陷复现是定位和修复的关键步骤，需要从环境、操作、数据等多维度分析。回答应体现结构化思维和实际经验。
【参考答案要点】
1. 记录完整步骤：详细记录操作序列、输入数据和预期结果。
2. 考虑时间与条件：注意特定时间点、系统负载或网络状态。
3. 关注边界与溢出：测试边界值、大容量数据或内存限制。
4. 分析事件次序：检查操作顺序或并发操作的影响。
5. 检查资源依赖：考虑内存、网络、硬件共享的竞争条件。
6. 不忽视硬件：硬件差异（如磁盘、外设）可能导致缺陷。
【易错提示】
常见遗漏点是环境因素（如浏览器版本、操作系统）和数据状态（如数据库初始数据），这些常是复现失败的原因。
【面试角度】
面试官期望看到实际案例，例如“在电商项目中，一个订单状态更新缺陷只在特定时间窗口复现，通过日志分析定位到缓存问题”。
```

## Q001173

- 题型：单选
- 难度：中等

**题目**

```text
在下列描述中，关于一个软件缺陷状态完整变化的错误描述是（）
```

**选项**

```text
A. 打开——修复——关闭
B. 打开——关闭
C. 打开——保留
D. 激活——修复——重新打开
```

**答案**

```text
D
```

**正确选项**

```text
D. 激活——修复——重新打开
```

**解析**

```text
【核心考点】 缺陷生命周期 缺陷状态
【题目解析】
本题考查软件缺陷状态的完整变化过程。典型缺陷状态包括：New（新建）→ Open（打开）→ Fix（修复）→ Close（关闭），或包含Reopen（重新打开）等状态。
【选项解析】
✗ A. 打开——修复——关闭 — 错误。缺少“新建”状态，且修复后通常需验证再关闭。
✗ B. 打开——关闭 — 错误。缺少修复和验证步骤，不符合实际流程。
✗ C. 打开——保留 — 错误。“保留”不是标准状态，且流程不完整。
✓ D. 激活——修复——重新打开 — 正确。激活（对应New/Open）→ 修复（Fix）→ 重新打开（Reopen，用于验证失败时），但更完整流程应包含关闭状态。此选项描述了缺陷从发现到重新验证的循环，是常见状态变化之一。
【易错提示】
注意缺陷状态定义因工具而异，但核心流程必须包含“修复”和“验证”环节。选项D虽不完整，但相比其他选项更符合实际变化。
```

## Q001179

```text

```

**答案**

```text
一条 Bug 记录最基本应包含:编号、 Bug 所属模块、 Bug 描述、 Bug 级别、 发现日期、 发现人、修改日期、修改人、修改方法、回归结果等等;
要有效的发现 Bug 需参考需求以及详细设计等前期文档设计出高效的测试用例,然后严格执行测试用例,对发现的问题要充分确认肯定,然后再向外发布如此才能提高提交 Bug 的质量。
```

**解析**

```text
【核心考点】 缺陷管理 测试流程
【参考答案要点】
1. Bug记录基本内容：编号、所属模块、描述、级别、发现日期、发现人、修改日期、修改人、修改方法、回归结果等。
2. 高质量Bug提交方法：参考需求文档和详细设计，设计高效测试用例；严格执行用例；充分确认问题后再发布；确保描述清晰、可复现。
【面试角度】

【易错提示】
不要遗漏“回归结果”或“修改方法”，这些是缺陷闭环的关键；同时避免描述模糊，如“功能不正常”应具体到操作步骤和预期结果。
```

```text
2、若无日志，可抓包分析，一样的是按照请求、返回结果去分析，如果是后端返回结果错误，可进一步查看数据库业主表数据的正确性，如果本身就是表数据少了，那可能是添加业主时插入数据库表的数据少了，数据库问题；如果数据库数据无问题，那就是接口返回错了
```

```text

2. 抓包分析：使用工具（如Fiddler、Charles）截获请求和响应，按同样逻辑判断问题归属。
```

## Q001209

- 题型：简答
- 难度：中等

**题目**

```text
如果发生漏测怎么解决？如何确定是否发生漏测？
```

**答案**

```text
解决如下：

（1）在测试过程中，如果碰到规格没有明确的，需要和需求分析进行沟通，以便确定我们的一些疑惑点，完成测试工作。如果规格未进行定义，我们可以以沟通的结果作为基础编写一定的测试用例进行测试，待规格明确之后，再进行测试用例的增删修补。

（2）如果碰到测试用例与规格不相符合的地方，我们需要记录下，并根据新规格补充完善测试用例，对存在有疑问的地方需要和规格设计进行沟通和确认，可以要求需求规格进行明确定义，事后将新增的、修改的测试用例整理成文，发给组内同事组织评审，并将评审之后的用例更新到用例库中去。
（3）对于外部反馈的缺陷，是因为场景设计不全引起的，我们先分析出现问题的场景是客户必须的场景还是偶然的场景，如果该场景是客户操作习惯，我们可以通过和技术接口人沟通，确认该场景的一些具体细节，在完善测试用例的过程中我们也要考虑一些和该场景相关联的场景，将多种场景下测试用例及时完善、评审，增加到用例库中去。

（4）在测试任务明显紧张的情况下，为避免出现明显缺陷遗漏，我们可以采取一些方式来最大程度上保障缺陷的遗漏。

（5）进行缺陷漏测分析的目的是为了促进软件质量和开发测试过程得到持续改进，使我们在测试过程中可以考虑得更加周全，弥补思维僵局。具体来讲，就是通过分析测试过程中漏测的缺陷，采取一些相应的预防措施以避免今后再发生类似的漏测。 确定方法：是否满足需求规格说明书的要求；需求规格变更，测试用例未及时更新；测试用例覆盖不全面，场景出现遗漏；测试过程中未严格按照测试用例执行；测试任务紧张，留给测试的时间较少，导致功能点的测试在测试过程中被省略。
```

**解析**

```text
【核心考点】 测试流程管理 缺陷预防 漏测分析
【题目解析】
本题考查测试人员面对漏测问题的处理方法和分析能力。漏测是测试中常见但严重的问题，面试官关注候选人的复盘思维、改进措施以及沟通协调能力。
【参考答案要点】
1. 确定漏测：通过缺陷分析，确认该缺陷是否属于测试范围、是否在测试用例中覆盖、是否因环境或数据差异导致。与开发和需求方沟通，确认是否为预期行为。
2. 临时措施：立即修复缺陷，补充测试用例，回归验证。对于紧急缺陷，优先修复并发布补丁。
3. 根因分析：分析漏测原因：是需求不明确、用例设计遗漏、测试执行疏忽，还是测试环境与生产环境不一致？使用5Why或鱼骨图等工具深入分析。
4. 改进措施：针对根因制定改进计划，如完善需求评审流程、增加测试场景、加强交叉测试、优化测试数据管理、引入探索性测试等。将新增用例纳入用例库，并组织评审。
5. 流程优化：建立漏测复盘机制，定期回顾缺陷数据，持续改进测试过程。
【面试角度】
回答时建议结合实际案例，例如“在XX项目中，我们曾因未覆盖XX场景导致漏测，后来通过增加XX测试手段避免了类似问题”。同时体现对测试流程的全局观，而非仅停留在修补层面。
【易错提示】
常见错误是只回答“补充用例”而不进行根因分析，显得缺乏深度。面试官期望看到系统性的改进思维。
```

## Q001234

- 题型：简答
- 难度：中等

**题目**

```text
怎么划分缺陷的等级？
```

**答案**

```text
1. Blocker(崩溃):奔溃：阻碍开发或测试工作的问题.

造成系统崩溃, 死机, 死循环, 导致数据库数据丢失, 与数据库连接错误, 主要功能丧失, 基本模块缺失等问题. 如: 代码错误, 死循环, 数据库发生死锁, 重要的一级菜单功能不能使用等(该问题在测试中较少出现, 一旦出现应立即终止当前版本测试.)
造成数据泄露的安全性问题, 比如恶意攻击造成的账户私密信息泄露
涉及金钱计算
阻断性测试, 所有测试工作进行不下去--阻断错误一般发生在冒烟测试等主流程上, 比如, 如果注册之后才能进行内部操作, 然后无法注册.

2. Critical(严重)严重: 系统主要功能部分丧失, 数据库保存调用错误, 用户数据丢失, 一级功能菜单不能使用但是不影响其他功能的测试.

功能设计与需求严重不符, 模块无法启动或调用, 程序重启, 自动退出, 关联程序间调用冲突, 安全问题, 稳定性等.
如: 软件中数据保存后数据库中显示错误, 用户所要求的功能缺失, 程序接口错误, 数值计算统计错误等.(该等级问题出现在不影响其他功能测试的情况下可以继续该版本测试).
重要功能不能实现
错误的涉及面广, 影响到其他重要功能正常实现
非常规操作导致的程序崩溃, 死机, 死循环, 闪退
界面超级难看
密码明文显示

3. Major(一般)
一般: 功能没有完全实现但是不影响使用, 功能菜单存在缺陷但不会影响系统稳定性
如: 操作时间长, 查询时间长, 格式错误, 边界条件错误, 删除没有确认框, 数据库表中字段过多等(该问题实际测试中存在最多)
不影响产品的运行, 不会成为故障起因, 但对产品外观和下道工序影响较大的缺陷.
次要功能不能实现(次要功能和主要功能的区别: 主流程之外的功能算是次要以及主要功能模块中的控件出现问题, 但主要流程仍然能正常实现)比如说: 注册时, 指明用户名为中文, 但输入英文注册成功了, 但不影响登录后的功能使用
操作错误(数据库中列明, 类型错误等)
查询结果错误
前端界面的简单输入限制未做出错误提示
例如: 删除操作未给提示, 防止误操作

4. Minor(次要)
次要: 界面, 性能缺陷, 建议类问题, 不影响操作功能的执行, 可以优化性能的方案等. 如: 错别字, 界面格式不规范, 页面显示重叠, 不该显示的要隐藏, 描述不清楚, 提示语丢失, 文字排列不整齐, 光标位置不正确, 用户体验感受不好, 可以优化性能的方案等(此类问题在测试初期较多, 优先程度较低, 在测试后期出现较少, 应及时处理)
界面上的错误, 界面布局, 文字格式, 按钮样式等轻微错误
辅助说明描述不清楚
提示窗口文字未采用行业术语
改进建议
```

**解析**

```text
【核心考点】 缺陷管理 缺陷等级
【参考答案要点】
缺陷等级通常分为四级，从高到低：
1. Blocker（崩溃）：阻碍测试或开发，如系统崩溃、数据丢失、主功能不可用。出现应立即停止测试。
2. Critical（严重）：主要功能部分丧失，数据错误，但系统可继续运行。如支付功能异常。
3. Major（主要）：功能不符合需求，但影响范围较小。如界面错误、次要功能缺失。
4. Minor（次要）：轻微问题，如UI排版、提示语错误，不影响功能。
【面试角度】
面试官关注实际应用能力，建议举例说明：例如“在项目中，登录功能崩溃设为Blocker，按钮颜色不对设为Minor”。同时，不同公司可能使用不同分级（如P0-P3），需灵活应对。
【延伸知识】
缺陷等级可能影响修复优先级，但不等同于优先级。例如，一个Minor缺陷但影响用户体验，可能优先级高。ISTQB建议区分严重性和优先级。
```

## Q001235

- 题型：简答
- 难度：中等

**题目**

```text
怎么区分一个bug是前端还是后端
```

**答案**

```text
参考：
一、通过抓包定位bug
a、传入参数错误（缺参、错参等），导致的问题往往是前端bug；
b、传入的参数与接口文档一致，数据返回正确，界面显示错误（字段取错），往往是前端的bug；
c、传入参数正确，数据返回错误，往往是后端的bug。
d、根据响应状态码：404客户端请求路径错误，500服务器内部错误
二、根据前后端的bug特点来定位问题
a、前端bug特点：界面相关（文本问题可能是html产生的bug）、布局相关（样式问题可能是css产生的bug，图片尺寸分辨率等）、兼容性相关
b、后端bug特点：业务逻辑相关（排序、分页）、数据相关、性能相关、安全性相关
三、查询系统日志
如果查不到错误日志前端的问题概率大，反之后台的问题
```

**解析**

```text
【核心考点】 Bug定位 前后端分离
【参考答案要点】
1. 抓包分析：检查请求参数、响应数据和状态码。参数错误或响应正确但界面异常多为前端Bug；参数正确但响应错误多为后端Bug；404为前端路径错误，500为后端错误。
2. 特点区分：前端Bug多涉及界面、布局、兼容性；后端Bug多涉及业务逻辑、数据、性能、安全。
3. 日志查询：通过系统日志定位异常，如后端日志中的堆栈信息。
【面试角度】
回答时建议结合实际项目中的调试工具（如Chrome DevTools、Fiddler）举例，并强调与开发协作的沟通方式，能体现实战能力。
【易错提示】
不要只罗列方法，需说明每种方法的适用场景。例如，抓包是基础手段，但复杂问题需结合日志和代码走查。
```

## Q001241

- 题型：简答
- 难度：中等

**题目**

```text
所有的软件缺陷都能修复吗?所有的软件缺陷都要修复吗?
```

**答案**

```text
从技术上讲，所有的软件缺陷都是能够修复的，但是没有必要修复所有的软件缺陷。测试人员要做的是能够正确判断什么时候不能追求软件的完美。对于整个项目团队，要做的是对每一个软件缺陷进行取舍，根据风险决定那些缺陷要修复。发生这种现象的主要原因如下：

　
-没有足够的时间资源。在任何一个项目中，通常情况下开发人员和测试人员都是不够用的，而且在项目中没有预算足够的回归测试时间，再加上修改缺陷可能引入新的缺陷，因此在交付期限的强大压力下，必须放弃某些缺陷的修改。

　
-有些缺陷只是特殊情况下出现，这种缺陷处于商业利益考虑，可以在以后升级中进行修复。

　
-不是缺陷的缺陷。我们经常会碰到某些功能方面的问题被当成缺陷来处理，这类问题可以以后有时间时考虑再处理。

　
最后要说的是，缺陷是否修改要由软件测试人员、项目经理、程序员共同讨论来决定是否修复，不同角色的人员从不同的角度来思考，以做出正确的决定。
```

**解析**

```text
【核心考点】 缺陷管理 风险决策
【参考答案要点】
1. 所有软件缺陷理论上都能修复：从技术角度，只要投入足够资源，任何缺陷都可被修复。
2. 并非所有缺陷都需要修复：需要基于风险和商业价值进行取舍。主要原因包括：
- 时间资源不足：项目交付期限压力大，修复可能引入新缺陷，需优先修复高风险问题。
- 缺陷影响范围小：仅在特殊条件下出现，商业利益上可接受，留待后续版本修复。
- 非缺陷的误报：某些功能特性被误认为缺陷，实际是需求或设计如此。
【面试角度】
回答时建议结合实际项目决策案例，例如："在XX版本中，我们曾有一个偶现的UI错位Bug，因修复风险高且影响用户量小，团队决定推迟到下一版本。" 这能体现测试人员的风险意识和商业思维。
【延伸知识】
缺陷取舍是测试经理的常见决策场景，常与缺陷优先级和严重程度矩阵结合使用。面试中可进一步讨论如何量化风险（如影响用户数、发生频率等）。
```

## Q001254

- 题型：简答
- 难度：中等

**题目**

```text
有没有偶然性的问题？怎判断偶然？怎么处理？
```

**答案**

```text
1）怎么判断偶现？一会出现一会不出现就是偶现的bug

2）测试碰到偶现bug，具体怎么处理呢？

a.首先，在遇到复现率低的bug，一定要提bug，描述清楚当时出现问题的步骤、操作环境、账号及测试数据、及必要的日志信息。

b.在发现bug时，要分析产生的原因，尽量多尝试可能出现的步骤，排除环境和自己电脑配置的原因，比如浏览器的版本等。甚至可以让开发同学对相应地方的代码进行检查，看一下是否可以通过代码层面检查出问题。

c.如果未复现，在接下来的测试中，时刻保持关注，每次执行同样或者相近的步骤的时候，看下是否能够复现之前的bug。

d.那些一直未能复现的bug，需要测试经理定期将这些bug汇总，选择优先级高的缺陷，组织开发人员和测试人员专门投入到复现问题。如果经过这样的专门复现依然不能复现，可以降低问题的优先级。如果在项目前期，跟踪至少3个版本，如果仍然无复现，可以暂时关闭该bug，备注说明并不是因为修复关闭，而是经过x个版本后不复现了。

e. 如果项目周期比较紧张，不能跟踪多个版本，那么bug就不能关闭，上线后及时关注用户的使用反馈，如果持续3或者4个版本没有出现，那么可以将bug暂时关掉了，同时关掉的时候要进行备注说明。
```

**解析**

```text
【核心考点】 缺陷管理 偶现Bug处理
【题目解析】
本题考察测试工程师对偶现Bug的识别和处理能力。偶现Bug是指不能稳定复现的缺陷，其处理流程是面试中的高频考点，体现了测试人员的分析能力和沟通协作能力。
【参考答案要点】
1. 判断偶现：通过多次执行相同或相似操作，观察缺陷是否时有时无，若无法稳定复现，则判定为偶现Bug。
2. 处理流程：
a. 记录缺陷：即使复现率低，也必须提交缺陷报告，详细描述操作步骤、环境、账号、数据及日志信息。
b. 分析原因：尝试多种可能场景，排除环境或配置因素（如浏览器版本），必要时请开发审查代码。
c. 持续关注：在后续测试中，对相关步骤保持警惕，尝试复现。
d. 定期汇总：对长期未复现的Bug，由测试经理定期汇总，评估风险并决定是否关闭。
【面试角度】
回答时建议结合实际项目案例，例如“在项目中曾遇到一个偶现的登录超时问题，通过增加日志和多次尝试环境组合最终定位”，能体现实战经验。
【易错提示】
不要忽略偶现Bug的记录，认为无法复现就不提交，这是测试大忌。偶现Bug往往隐藏严重问题，需持续跟踪。
```

```text
提测===提交版本到测试部分进行测试 、打包===将代码进行压缩成项目包
```

**解析**

```text
【核心考点】 测试流程管理 版本控制 回归测试
【题目解析】
本题考察测试流程管理中的轮次划分、测试策略和版本提测规范。测试轮次通常根据项目规模和复杂度确定，一般包括冒烟测试、系统测试、回归测试等阶段。针对开发频繁提测的问题，需要建立规范的提测流程，避免测试资源浪费。
【参考答案要点】
1. 测试轮次：一般进行3-5轮。第一轮：冒烟测试+系统测试；第二轮：回归测试（修复的bug）；第三轮：全面回归测试；最后一轮：冒烟测试或验收测试。
2. 每轮测试内容：第一轮覆盖所有功能；后续轮次重点验证bug修复和受影响模块，逐步缩小范围。
3. 版本提测规范：开发修改bug后，应等待当前测试轮次结束，统一提交版本，避免频繁打包。测试人员需拒绝未经完整回归的临时版本。
【面试角度】
回答时建议结合实际项目经验，如“我们项目采用敏捷开发，每轮测试后召开评审会，确定下一轮范围和优先级”，并强调版本管理和沟通机制的重要性。
【易错提示】
注意区分“提测”和“打包”：提测是开发提交版本给测试，打包是代码编译成可执行包。测试人员应关注提测流程，而非打包细节。
```


```text
5. 持续集成：代码提交后自动构建并运行测试，即时反馈问题，避免缺陷累积。
【面试角度】
回答时建议结合实际项目经验，例如“在XX项目中，我们通过需求评审发现了多个逻辑漏洞，避免了后期返工”，体现实践深度。
【易错提示】
```

## Q001271

- 题型：简答
- 难度：中等

**题目**

```text
测试工作完成后，你没有发现一个bug，该怎么办？
```

**答案**

```text
第一种情况：正常执行测试
1、如果测试的人只有你一个，看看测试的软件版本是开发中的还是已经上线的，如果是开发中未上线的版本，发现不了bug要引起注意， 毕竟绝大部分情况下应该是能发现bug的
2、如果测试的人不止你一个的时候，看看其他人是否可以找到bug，分两种场景讨论：

场景1、如果测试的bug不多，那说明软件质量应该还不错， 你测试不出来bug 也不要着急，
场景2、其他人能够发现bug，但是你发现不了， 这个情况就要去思考，你的测试方法是不是不对， 你对需求是否理解到位，是否还有遗漏， 仔细分析下其他人发现的bug是否在自己负责的模块存在，

第二种情况：新人到公司， 为了让新人尽快熟悉业务，会让新人跑跑 测试用例， 这个时候测试的模块一般都比较成熟了，或者可能都已经上线了， 发现不了bug很正常
```

**解析**

```text
【核心考点】 测试执行 问题分析 测试思维
【题目解析】
本题考察测试人员在未发现Bug时的应对思路和问题分析能力。首先需要区分场景：如果是单人测试，需确认被测版本是开发中还是已上线版本，开发中版本通常有Bug，若未发现需反思测试覆盖是否充分；如果是多人测试，需对比他人是否发现Bug，若他人能发现而自己不能，则需检查测试方法、需求理解、测试用例设计是否存在遗漏。此外，还需考虑软件质量本身是否较高，或测试环境、数据是否与生产环境一致。
【参考答案要点】
1. 分析被测版本状态：确认是开发中版本还是已上线版本，开发中版本通常存在Bug。
2. 对比他人测试结果：若团队中其他人发现Bug，需分析自己是否遗漏了测试点或测试方法不当。
3. 检查测试覆盖：回顾测试用例是否覆盖了所有功能、边界、异常场景，是否遗漏了关键路径。
4. 考虑环境与数据因素：确认测试环境、测试数据是否与生产环境一致，是否存在环境差异导致Bug未复现。
5. 与开发沟通：了解代码变更情况，确认是否有已知问题未修复。
【面试角度】
面试官期望看到主动反思和问题分析能力，而非简单回答“没Bug就是质量好”。建议结合具体项目案例说明如何排查问题。
【易错提示】
不要直接认为“没Bug说明软件质量好”，这可能是测试不充分或测试方法有误的信号。
```

## Q001272

```text
测试流程、缺陷是怎么管理的？
```

```text
2、缺陷是提交到禅道进行管理，对于提交的bug，会持续进程跟踪和回归验证，如果确定已经修改了，就会关闭bug。遇到延期解决的问题也会及时去进行跟进处理。
```

```text
【核心考点】 软件测试流程 缺陷管理
【参考答案要点】

1. 需求分析阶段：熟悉需求文档、原型图，明确被测项目、业务逻辑、支持平台、应用场景，考虑兼容性、安全、性能等测试需求。
2. 测试规划阶段：制定测试计划，包括测试范围、资源、时间表、风险等。

5. 测试总结阶段：汇报测试结果，输出测试报告。

缺陷通常提交到禅道等管理工具，持续跟踪和回归验证，确认修改后关闭bug。遇到延期问题需及时跟进处理。

【延伸知识】
ISTQB将测试流程分为：计划→监控→分析→设计→实现→执行→完成，与国内常见流程略有差异，了解两种体系有助于应对不同风格的面试。
```

## Q001278

- 题型：简答
- 难度：中等

**题目**

```text
测试问题的严重性分为几级？如何区分？
```

**答案**

```text
分为4-5级，依据公司情况而定
（1）致命错误 ：---- P1
1、常规操作引起的系统崩溃、死机、死循环、闪退 --- 阻塞，冒烟测试都不通过
2、造成数据泄漏的安全性问题，比如恶意攻击造成的账户私密信息泄露 --- 安全漏洞
3、涉及巨额的金钱计算和金钱损失
4、阻断性测试，所有测试工作进行不下去
5、权限问题 --- 用户越权

（2）严重错误：----- P2
1、重要功能不能实现；
2、次要功能错误的波及面广，影响到其它重要功能正常实现；
3、非常规操作导致的程序崩溃、死机、死循环、闪退 --- 网络异常情况，或者连续点击四五次才能出现的问题
4、外观(界面)难以接受的缺陷 --- UI
5、密码明文显示；--- 前端密码是标*处理，后端传输数据的时候密码也是需要加密处理
6、偶现的致命性bug
（3）一般错误：---P3
不影响产品的运行、不会成为故障起因，但对产品外观和下道工序影响较大的缺陷
1、次要功能不能正常实现；
2、操作界面错误（包括数据窗口内列名定义、含义不一致）；
3、查询错误，数据错误显示
4、简单的输入限制未放在前端进行控制；-- 减轻后端(服务器+开发)压力，手机号/邮箱/空/长度/类型的校验
5、删除操作未给出提示 -- 防止误操作，友好型
6、偶现的严重性bug
（4）细微错误：---P4
程序在一些显示上不美观，不符合用户习惯，或者是一些文字的错误
1、界面不规范；
2、辅助说明描述不清楚；
3、提示窗口文字未采用行业术语；--- 约定俗成

4、界面存在文字错误；

（5）改进建议 ----P5
可以提高产品质量的建议，包括新需求和对需求的改进。--- 先保证功能的正确性，再去提建议
```

**解析**

```text
【核心考点】 缺陷管理 严重性分级
【题目解析】
本题考查对缺陷严重性分级的理解。通常分为4-5级，常见为P1-P4或致命、严重、一般、轻微。分级依据包括：功能影响范围、数据安全、用户体验、是否阻塞测试等。
【参考答案要点】
1. 致命错误（P1）：系统崩溃、死机、数据泄露、巨额金钱损失、阻塞所有测试。
2. 严重错误（P2）：重要功能无法实现、次要功能波及面广、非常规操作导致崩溃、界面严重缺陷。
3. 一般错误（P3）：次要功能异常、界面显示问题但不影响核心流程。
4. 轻微错误（P4）：文字错误、排版不美观、建议性改进。
【易错提示】
注意区分“严重性”与“优先级”：严重性指缺陷对系统的影响程度，优先级指修复的紧急程度，两者不同但常混淆。
```

## Q001282

- 题型：简答
- 难度：中等

**题目**

```text
碰到一些偶发性bug，开发也不认为这是bug该怎么办？
```

**答案**

```text

d.那些一直未能复现的bug，需要测试经理定期将这些bug汇总，选择优先级高的缺陷，组织开发人员和测试人员专门投入到复现问题。如果经过这样的专门复现依然不能复现，可以降低问题的优先级。
e、另外，项目发布后，跟踪至少3个版本，及时关注用户的使用反馈，如果仍然无复现，可以暂时关闭该bug，备注说明并不是因为修复关闭，而是经过n个版本后不复现了。
```

**解析**

```text
【核心考点】 缺陷管理 沟通协作
【题目解析】
本题考查测试人员处理偶发性Bug的策略和与开发人员的沟通技巧。偶发性Bug因难以复现，常被开发质疑，但测试人员需坚持原则并采取系统化方法。
【参考答案要点】
1. 记录与报告：无论能否复现，都应详细记录Bug出现的步骤、环境、数据、日志等信息，并提交Bug报告。
2. 尝试复现：分析可能原因，排除环境因素（如浏览器版本、操作系统），尝试多种操作组合，甚至请开发协助代码审查。
3. 持续关注：在后续测试中，对类似场景保持警惕，每次执行相近步骤时留意是否复现。
4. 团队协作：对于长期未复现的高优先级Bug，由测试经理组织专项复现会议，集中资源定位问题。
【面试角度】
回答此类问题时，建议结合实际项目经历举例说明，例如“在我们项目中，曾遇到一个偶发性登录失败问题，通过日志分析和环境对比最终定位到网络延迟”，能有效提升答案深度。
```

```text
1. 快速响应与定位：第一时间配合开发重现bug，确认影响范围。
2. 分级处理：严重bug立即修复并更新版本；非严重bug可放入下一迭代。
3. 经验总结与改进：分析bug根因，优化测试用例、增加用例评审、规划充分测试时间、考虑mock测试等。

【易错提示】
避免只谈应急处理而忽略事后复盘，面试官更看重持续改进能力。
```

## Q001316

- 题型：简答
- 难度：中等

**题目**

```text
请描述如何划分缺陷与错误严重性和优先级别？
```

**答案**

```text
给软件缺陷与错误划分严重性和优先级的通用原则： （1）表示软件缺陷所造成饿危害和恶劣程度。 （2）优先级表示修复缺陷的重要程度和次序。 严重性： （1）、严重：系统崩溃、数据丢失、数据毁坏 （2）、较严重：操作性错误、结果错误、遗漏功能 （3）、一般：小问题、错别字、UI布局、罕见故障 （4）、建议：不影响使用的瑕疵或更好的实现。
优先级： （1）、最高优先级：立即修复，停止进一步测试。 （2）、次高优先级：在产品发布之前必须修复。 （3）、中等优先级：如果时间允许应该修复。 （4）、最低优先级：可能会修复，但是也可能发布。
```

**解析**

```text
【核心考点】 缺陷管理 严重性 优先级
【参考答案要点】
1. 严重性（Severity）定义：表示软件缺陷对系统造成的危害程度和恶劣影响，通常分为：严重（系统崩溃、数据丢失、数据毁坏）、较严重（操作性错误、结果错误、遗漏功能）、一般（小问题、错别字、UI布局、罕见故障）、建议（不影响使用的瑕疵或更好的实现）。
2. 优先级（Priority）定义：表示修复缺陷的重要程度和次序，通常分为：最高优先级（立即修复，停止进一步测试）、次高优先级（在产品发布之前必须修复）、中等优先级（如果时间允许应该修复）、最低优先级（可能会修复，但是也可能发布）。
【面试角度】
回答此类问题时，建议结合实际项目经历举例说明，例如“在我们项目中，严重性高的缺陷不一定优先级高，比如一个罕见但严重的bug可能优先级较低”，能有效提升答案深度。
【延伸知识】
严重性和优先级是独立的两个维度，常见误区是认为严重性高则优先级一定高。实际中需结合业务影响、用户反馈和发布计划综合判断，例如UI错别字严重性低但优先级可能高（如影响品牌形象）。
```

## Q001340

- 题型：简答
- 难度：中等

**题目**

```text
那你们遇到过哪些线上bug?
```

**答案**

```text
用户bug提的一些建议性的bug，
或者是跟浏览器兼容性有关系的bug ，还有就是跟用户的环境比如 网络环境 或者微信版本等这些相关的bug。
```

**解析**

```text
【核心考点】 缺陷管理 线上问题排查
【参考答案要点】
线上bug通常包括以下几类：
1. 建议性bug：用户反馈的体验优化或功能改进建议，非功能性缺陷。
2. 兼容性bug：与浏览器、操作系统、设备型号等相关的显示或功能问题。

```

```text
Open：确认 bug，并且认为需要进行修改，指派给相应的开发人员。
Fixed：开发人员进行修改后标识成修改状态，有待测试人员的回归测试验证。
Rejected：如果认为不是 Bug，则拒绝修改。
Delay：如果认为暂时不需要修改或暂时不能修改，则延后修改。
Closed：修改状态的 Bug 经测试人员的回归测斌验证通过，则关闭 Bug。
```

## Q001143

- 题型：简答
- 难度：较难

**题目**

```text
你们会统计一条需求的缺陷密度吗？
```

**答案**

```text
依据实际情况来回答，有就有，没有就没有。
缺陷密度是软件/模块在特定运行或开发期间确认的缺陷数量除以软件/模块的大小。它使人们能够决定某个软件是否已准备好发布。

缺陷密度是按每千行代码（即 KLOC）计算的。

如何计算缺陷密度：缺陷密度=缺陷数量/版本大小

版本的大小可以用一行代码（LoC）来衡量。
缺陷密度示例

假设有3个模块集成到软件产品中。每个模块都发现了以下数量的缺陷：

• 模块1 = 10个缺陷

• 模块2 = 20个缺陷

• 模块3 = 10个缺陷

缺陷总数= 10 + 20 + 10 = 40

每个模块的代码总行是：

• 模块1 = 1000 LoC

• 模块2 = 1500 LoC

• 单元3 = 500 LoC

总代码行= 1000 + 1500 + 500 = 3000

缺陷密度的计算公式为：

缺陷密度= 40/3000 = 0.013333缺陷/位置= 13.333缺陷/KLoC
```

**解析**

```text
【核心考点】 缺陷密度 质量度量
【题目解析】
本题考查缺陷密度的概念及其在项目中的应用。缺陷密度是衡量软件质量的重要指标，但实际项目中是否统计取决于团队成熟度和项目需求，回答时应体现对度量指标的理解和实际经验。
【参考答案要点】
1. 是否统计：依据实际情况来回答，有就有，没有就没有。通常大型项目或成熟团队会统计，小型项目可能不统计。
2. 缺陷密度定义：软件/模块在特定运行或开发期间确认的缺陷数量除以软件/模块的大小，通常按每千行代码（KLOC）计算。
3. 计算公式：缺陷密度 = 缺陷数量 / 版本大小（LoC）。
4. 示例：假设3个模块，缺陷总数40，代码总行数3500 LoC，则缺陷密度 = 40 / 3.5 ≈ 11.43 缺陷/KLOC。
【面试角度】
回答此类问题时，建议结合实际项目经验说明统计缺陷密度的目的，例如“我们通过缺陷密度评估模块质量，对密度过高的模块进行重点回归测试”，能展示对质量度量工具的理解。
【延伸知识】
缺陷密度并非唯一质量指标，常与缺陷移除效率（DRE）结合使用。此外，不同行业和语言的标准不同，如安全关键系统要求极低缺陷密度。
```

## Q001208

- 题型：简答
- 难度：较难

**题目**

```text
如果发生了漏测怎么解决？如何确定是否发生漏测？
```

**答案**

```text
解决如下：
（1）在测试过程中，如果碰到规格没有明确的，需要和需求分析进行沟通，以便确定我们的一些疑惑点，完成测试工作。如果规格未进行定义，我们可以以沟通的结果作为基础编写一定的测试用例进行测试，待规格明确之后，再进行测试用例的增删修补。
（2）如果碰到测试用例与规格不相符合的地方，我们需要记录下，并根据新规格补充完善测试用例，对存在有疑问的地方需要和规格设计进行沟通和确认，可以要求需求规格进行明确定义，事后将新增的、修改的测试用例整理成文，发给组内同事组织评审，并将评审之后的用例更新到用例库中去。
（3）对于外部反馈的缺陷，是因为场景设计不全引起的，我们先分析出现问题的场景是客户必须的场景还是偶然的场景，如果该场景是客户操作习惯，我们可以通过和技术接口人沟通，确认该场景的一些具体细节，在完善测试用例的过程中我们也要考虑一些和该场景相关联的场景，将多种场景下测试用例及时完善、评审，增加到用例库中去。
（4）在测试任务明显紧张的情况下，为避免出现明显缺陷遗漏，我们可以采取一些方式来最大程度上保障缺陷的遗漏。
（5）进行缺陷漏测分析的目的是为了促进软件质量和开发测试过程得到持续改进，使我们在测试过程中可以考虑得更加周全，弥补思维僵局。具体来讲，就是通过分析测试过程中漏测的缺陷，采取一些相应的预防措施以避免今后再发生类似的漏测。
确定方法：
是否满足需求规格说明书的要求；需求规格变更，测试用例未及时更新；测试用例覆盖不全面，场景出现遗漏；测试过程中未严格按照测试用例执行；测试任务紧张，留给测试的时间较少，导致功能点的测试在测试过程中被省略。
```


```text

5. 如果项目周期比较紧张，不能跟踪多个版本，那么bug就不能关闭，上线后及时关注用户的使用反馈，如果持续3或者4个版本没有出现，那么可以将bug暂时关掉了，同时关掉的时候要进行备注说明。
```

```text
2. 深入分析：尝试不同环境、数据或操作顺序，排除环境因素。
3. 协作排查：请开发检查代码逻辑，定位潜在问题点。
```

## Q001223

```text
第一：前提，熟透系统业务、团队成员情况
第二：巧用工具懂得如何定位并分析问题
1. 分析问题场景进行预判
先查看页面表象，根据问题表像判断问题可能出现的原因，进行缩小范围，并且准备好录制工具，录制问题
系统页面无法正常访问的提示5开头的找后端，4开头的先检查请求地址或者对应的权限，进入系统页面正常打开，提示异常代码错误的直接找后端
进入系统页面展示异常图片视频相关提示Flash等相关信息进行安装Flash如若还不行找前端，界面UI展示兼容性错误找前端

4**开头的状态码一般都是客户端（前端）的问题；例如常见的404确认下是否是请求的地址有错，403确认是否有权限访问，具体可百度
5**开头的状态码一般都是服务端（后端）问题，例如常见的500，则表示是服务器内部错误，503网络过载导致服务端延时，502服务器崩溃等，具体可百度
3.关注请求的入参与响应数据
通过访问报错的页面，加载错误请求时我们通过F12进行分析请求包，查看对应的入参以及响应数据
4. 查看日志
针对服务端类型的报错，我们可以进行登录日志平台或者服务器对应Log目录下查看打印出的日志
常用查看日志命令tail ,/error进行快速检索关键词接口名等相关内容
拿到对应的日志,将日志文件贴进bug单，指派给后端，提高专业性，测试人员也要养成看日志的习惯，看着看着就懂了
5. 经验法则
在系统前端页面当碰见服务器配置相关报错的信息例如Nginx***或者代码以及SQL相关的提示报错信息直接找后端处理，例如JAVA 、.PHP、SQL等异常报错前端字符校验、格式校验等，浏览器界面UI兼容性以及插件，或者APP、小程序类调用手机相关功能拍照、语音无法正常调用直接找前端
```

**解析**

```text
【核心考点】 缺陷分析 问题定位
【参考答案要点】
1. 分析问题场景进行预判：先观察页面表象，根据错误类型缩小范围。例如，5xx状态码找后端，4xx状态码检查请求地址或权限，UI兼容性问题找前端，功能异常则进入抓包分析。

3. 复现和记录：录制操作步骤，确保缺陷可复现，并详细记录环境、步骤和截图，便于开发修复。

【延伸知识】

```

## Q001239

- 题型：简答
- 难度：较难

**题目**

```text
怎样定位bug？
```

**答案**

```text
1、软件未达到需求文档标准功能；
2、软件出现了需求文档指明不会出现的错误；
3、软件功能超出了需求文档指明范围；
4、软件未达到需求文档没有指出但应达到的目标；
5、测试人员认为软件难以理解、不易使用、运行速度缓慢，或最终用户认为不好。（站在使用者的角度，功能是否易操作、易理解）
6、对于需求文档里没有的需要根据自己的测试经验来判断。或者寻找相应的竞品来对比。
```

**解析**

```text
【核心考点】 缺陷管理 测试思维 需求分析
【题目解析】
本题考查如何定位和定义Bug。Bug的定位不仅限于功能缺陷，还包括需求符合性、用户体验和性能等方面。测试人员需要从多个维度判断问题是否属于Bug，包括对照需求文档、用户期望和行业标准。
【参考答案要点】
1. 功能未达标：软件未达到需求文档标准功能。
2. 不应出现的错误：软件出现了需求文档指明不会出现的错误。
3. 功能超出范围：软件功能超出了需求文档指明范围。
4. 隐含需求未满足：软件未达到需求文档没有指出但应达到的目标。
5. 用户体验问题：测试人员认为软件难以理解、不易使用、运行速度缓慢，或最终用户认为不好。（站在使用者的角度，功能是否易操作、易理解）
6. 经验判断：对于需求文档里没有的需要根据自己的测试经验来判断。或者寻找相应的竞品来对比。
【面试角度】
回答此类问题时，建议结合实际项目经历举例说明，例如“在项目中，我们曾发现一个功能虽然满足需求文档，但用户操作流程复杂，最终被定义为易用性Bug”，能有效提升答案深度。
【延伸知识】
Bug的定义在不同组织中可能有差异，有的团队将性能问题、安全漏洞也纳入Bug范畴。了解ISTQB的缺陷分类（功能、性能、安全、易用性等）有助于全面定位问题。
```

## Q001243

- 题型：简答
- 难度：较难

**题目**

```text
描述使用bugzilla缺陷管理工具对软件缺陷（BUG）跟踪的管理的流程？
```

**答案**

```text
1) 测试人员或开发人员发现bug后，判断属于哪个模块的问题，填写bug报告后，系统会自动通过Email通知项目组长或直接通知开发者。
2) 经验证无误后，修改状态为VERIFIED.待整个产品发布后，修改为CLOSED.
3) 还有问题，REOPENED，状态重新变为“New"，并发邮件通知。
4) 项目组长根据具体情况，重新reassigned分配给bug所属的开发者。
5) 若是，进行处理，resolved并给出解决方法。(可创建补丁附件及补充说明)
6) 开发者收到Email信息后，判断是否为自己的修改范围。
7) 若不是，重新reassigned分配给项目组长或应该分配的开发者。
8) 测试人员查询开发者已修改的bug，进行重新测试。
```

**解析**

```text
【核心考点】 缺陷管理 Bugzilla 缺陷生命周期
【参考答案要点】
1. 提交缺陷：测试人员发现bug后，判断模块，填写bug报告，系统自动通过Email通知项目组长或直接通知开发者。
2. 分配缺陷：项目组长根据具体情况，重新分配（reassigned）给所属开发者。
3. 处理缺陷：开发者收到Email后，判断是否属于自己的修改范围；若是，进行处理并标记为已解决（Resolved），可创建补丁附件及补充说明；若不是，重新分配回项目组长或正确开发者。
4. 验证缺陷：测试人员验证修复无误后，修改状态为已验证（VERIFIED）。
5. 关闭缺陷：待整个产品发布后，修改为已关闭（CLOSED）。
6. 重新打开：若还有问题，重新打开（REOPENED），状态变为New，并发邮件通知。
【面试角度】
建议结合实际项目经验说明缺陷流程中的协作细节，如如何处理争议、如何设置优先级等，能有效提升答案深度。
【延伸知识】
常见缺陷状态包括：New、Assigned、Resolved、Verified、Closed、Reopened。不同工具可能略有差异，但核心流程一致。
```

## Q001260

```text
面试官期望看到清晰的排查逻辑，建议按“前端→后端→数据库”顺序描述，并提及具体工具（如tail -f日志、Fiddler）。
【易错提示】
```

## Q001323

- 难度：较难

```text
软件已经上线，客户在使用的时候又有新的问题，这种情况\n怎么处理？
```

**答案**

```text

2.确定问题的优先级。在了解问题详细情况后，请评估该问题的紧急程度和影响范围。对于高优先的问题，应当及时分配专人处理，并跟进处理的进展。

3.给出解决方案。根据问题的特点和原因，提供可行的解决方案，同时告知客户计修复。

4.认真记录问题。在解决问题的过程中，要认真记录所有相关，包括问题的起因、解决方案和实施过程等。以便更好地处理类似问题。

5.检查并验证。在解决问题后，需要仔细检查和验证，确保问题得到了彻底解决，以避免同类问题再次出现。

6.跟进和反馈。在问题得到解决后，应该及时向客户反馈和跟进处理过程，让客户感受到我们的贴心服务，增加客户对我们的信任感和满意度。
```

**解析**

```text
【核心考点】 缺陷管理 客户沟通 应急响应
【参考答案要点】
1. 及时响应与安抚：第一时间回复客户，确认收到反馈，表达重视并承诺跟进。
2. 问题评估与优先级：分析问题严重性（P0-P4）和影响范围，高优先级问题立即分配专人处理。

4. 记录与跟踪：在缺陷管理系统中详细记录问题描述、复现步骤、根因和修复过程。
5. 验证与回归：修复后进行全面测试，确保问题已解决且无副作用。
6. 反馈与闭环：向客户通报修复结果，必要时提供临时规避措施，并收集客户满意度。
【面试角度】

【延伸知识】
```

## Q001338

- 难度：较难

```text
遇到的印象最深的 BUG 是？
```

**答案**

```text
答题思路：
（1）可以是体现 BUG 定位问题能力的 BUG
（2）可以是体现测试思维模式扩展的 BUG
（3）可以是体现相关技能提升的 BUG
（4）可以是业务逻辑复杂的 BUG

（7）可以是线上严重级别较低但用户体验效果非常差的 BUG
1）我印象最深的一个 BUG，是一个线上 BUG，这个 BUG 的严重级别是 P4，用
户体验级别的 BUG。领红包活动，产品设计了一个领红包的 icon 放在那里。在测试的
```

## Q001351

- 题型：简答
- 难度：较难

**题目**

```text
项目马上要上线了，然后bug又没修复完，怎么处理？
```

**答案**

```text
1、bug进行分类，按照类型、优先级、难易度；优先修复容易和级别高的bug；
2、与客户提前做好沟通，做好可能延期交付的应对；
3、协调增加资源，加速bug修复速度；
4、与客户协商非必要bug放到上线后逐步修复。
```

**解析**

```text
【核心考点】 缺陷管理 上线策略 风险管理
【参考答案要点】
1. 缺陷分类与优先级排序：按严重程度（致命、严重、一般、轻微）和优先级（P0-P3）分类，优先修复P0/P1级缺陷。
2. 与客户沟通：提前告知可能延期风险，协商是否接受部分缺陷上线后修复，或调整上线时间。
3. 协调资源：申请增加开发或测试资源，加速缺陷修复和验证。
4. 非关键缺陷后移：与产品、客户确认，将非必要缺陷（如UI样式、非核心功能）放到上线后迭代修复。
【面试角度】
回答时需体现风险意识和沟通能力。建议结合案例，如“在XX项目中，我们通过缺陷分类和客户协商，最终按时上线了核心功能，次要问题在后续版本修复”，展示解决问题的思路。
【延伸知识】
还可提及上线决策流程：组织上线评审会，由测试、开发、产品共同评估风险，决定是否上线。以及灰度发布策略，先小范围验证，降低风险。
```
