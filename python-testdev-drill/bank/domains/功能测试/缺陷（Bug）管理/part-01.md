## Q001072

- 题型：简答
- 难度：入门

**题目**

```text
BUG 描述中都包括那些内容？
```

**答案**

```text
一条bug记录，要包含编号、标题、所属模块、重现步骤、预期结果、实际结果、发现版本、优先级、重要程度、创建人、指派给谁以及适当的截图。
```

**解析**

```text
【核心考点】 缺陷管理 Bug报告
【题目解析】
本题考查Bug报告的基本要素，是软件测试的基础知识。一个完整的Bug描述应包含足够的信息，以便开发人员能够重现和修复问题。
【参考答案要点】
1. 编号：唯一标识Bug。
2. 标题：简洁描述Bug。
3. 所属模块：指明功能模块。
4. 重现步骤：详细描述操作步骤。
5. 预期结果：正确行为。
6. 实际结果：错误行为。
7. 发现版本：软件版本号。
8. 优先级：修复紧急程度。
9. 重要程度：影响范围。
10. 创建人：报告者。
11. 指派给：负责修复的开发人员。
12. 附件：截图、日志等辅助信息。
【易错提示】
缺少重现步骤或预期/实际结果，会导致开发人员无法理解Bug，降低修复效率。建议附上截图或日志以增强可读性。
```

## Q001074

```text
BUG报告包括哪些内容？
```

**答案**

```text
bug报告 包含什么内容：
1.缺陷编号（bug编号），
2.缺陷标题，
3.缺陷状态，
4.提交人，
5.负责人，
6.优先级，
7.严重程度，
8.缺陷描述，
9.时间
10.截图
```

**解析**

```text
【核心考点】 缺陷管理 Bug报告
【题目解析】
本题考查Bug报告的基本构成要素，是软件测试的基础知识。一份高质量的Bug报告能帮助开发人员快速定位和修复问题，是测试人员专业性的体现。
【参考答案要点】
一份完整的Bug报告通常包含以下内容：
1. 缺陷编号：唯一标识符，用于跟踪。
2. 缺陷标题：简洁明了地描述问题。
3. 缺陷状态：如New、Open、Fixed、Closed等。
4. 提交人：发现缺陷的测试人员。
5. 负责人：负责修复的开发人员。
6. 优先级：决定修复的紧急程度。
7. 严重程度：影响系统的程度，如崩溃、功能异常、界面问题等。
8. 缺陷描述：详细描述复现步骤、实际结果和期望结果。
9. 时间：发现缺陷的时间。
10. 截图/日志：辅助定位问题的证据。
【面试角度】
面试中，除了列出要素，建议举例说明如何写一个高质量的缺陷标题和描述。例如“标题：登录页面输入正确用户名和密码后点击登录，页面无响应；描述：步骤1.打开登录页...”。这能展示你的沟通能力。
【易错提示】
容易混淆优先级和严重程度。优先级是业务维度，严重程度是技术维度。例如，一个严重程度为“崩溃”的Bug，如果发生在非核心功能且用户很少使用，优先级可能较低。
```

## Q001104

- 题型：简答
- 难度：入门

**题目**

```text
一个bug的生命周期？
```

**答案**

```text
新建bug--指派给对应的开发人员--开发人员对bug进行确认---开发对bug进行修复---测试对bug进行验证---如果bug已经修复，测试人员直接关闭 OR 如果bug未修复，则激活重新指派给开发人员，重新修复。
```

**解析**

```text
【核心考点】 缺陷管理 Bug生命周期
【题目解析】
本题考查Bug生命周期的基本流程，是测试基础概念题。需清晰描述从发现到关闭的完整状态变化。
【参考答案要点】
1. 新建Bug：测试人员发现缺陷并提交Bug报告。
2. 指派给开发：将Bug分配给对应开发人员。
3. 开发确认：开发人员确认Bug是否有效。
4. 开发修复：开发人员修复Bug。
5. 测试验证：测试人员验证修复结果。
6. 关闭或激活：若修复成功则关闭Bug；若未修复则重新激活并指派给开发。
【面试角度】
回答此类问题时，建议结合实际项目经历举例说明，例如“在我们项目中，Bug状态还包括‘延迟修复’和‘重复Bug’”，能有效提升答案深度。
【易错提示】
不要忽略开发确认和重新激活环节，这些是Bug生命周期中的关键状态。
```

```text

```

```text
【核心考点】 软件缺陷定义 测试基础
【题目解析】
本题考查软件缺陷的标准定义。根据 IEEE 标准，软件缺陷是指软件中存在的、导致其无法满足需求或用户期望的问题。选项 A 描述的是主观感受，不属于标准缺陷定义范畴。
```

## Q001129

- 题型：简答
- 难度：入门

**题目**

```text
什么是崩溃？
```

**答案**

```text
计算机系统或组件突然并完全的丧失功能，例如软件或系统突然退出或没有任何反应（死机）。
```

**解析**

```text
【核心考点】 缺陷分类 崩溃定义
【题目解析】
本题考察对软件缺陷严重级别中“崩溃”的理解。崩溃是最高严重级别的缺陷之一，指系统或组件完全丧失功能，通常导致程序意外退出或无响应。
【参考答案要点】
崩溃（Crash）：计算机系统、应用程序或组件突然且完全丧失功能，表现为软件意外退出、死机、蓝屏或无法响应任何操作。例如，点击某个按钮后程序直接关闭。
【面试角度】
面试官通过此题考察对缺陷严重级别的认知。建议回答时区分崩溃与其他级别（如严重、一般、轻微），并举例说明，如“崩溃会导致数据丢失，需立即修复”。
【易错提示】
避免将崩溃与“卡顿”或“功能异常”混淆。崩溃是系统完全丧失功能，而卡顿是性能问题，功能异常是部分功能失效。
```

## Q001131

- 题型：简答
- 难度：入门

**题目**

```text
什么是测试包？
```

**答案**

```text
答案：测试包英文名：Testing suite。一组测试用里的执行框架；一种组织测试用例的方法。在测试包里，测试用例可以组合起来创造出独特的测试条件。
```

**解析**

```text
【核心考点】 测试包 测试用例组织
【题目解析】
本题考察软件测试中的基本概念——测试包（Test Suite）。测试包是一组测试用例的集合，用于组织和管理测试用例，以便按特定顺序或条件执行。它是测试执行框架的一部分，可以帮助测试人员更高效地运行相关测试。常见的测试包管理工具包括JUnit、TestNG、pytest等。
【参考答案要点】
1. 定义：测试包（Test Suite）是一组测试用例的集合，用于组织和管理测试执行。
2. 作用：将相关测试用例组合在一起，便于批量执行、生成报告和跟踪测试进度。
3. 示例：在JUnit中，使用@Suite注解将多个测试类组合成一个测试包。
【面试角度】
虽然概念简单，但面试时若能结合实际项目中的测试包设计经验（如按模块、优先级或功能划分），会显得更专业。
```

## Q001191

- 题型：简答
- 难度：入门

**题目**

```text
如何定义一个bug？
```

**答案**

```text
1、软件的缺陷和漏洞

2、软件可改进的细节

3、与需求文档存在差异的功能实现
```

**解析**

```text
【核心考点】 缺陷定义 软件质量
【题目解析】
```

```text
简述bug的生命周期
```

**答案**

```text
BUG的生命周期，就是一个BUG被发现到这个BUG被关闭的过程。

生命周期中缺陷状态：新建-->指派-->已解决-->待验-->关闭

发现BUG-->提交BUG-->指派BUG-->研发确认BUG-->研发去修复BUG-->回归验证BUG-->是否通过验证-->关闭BUG
```

**解析**

```text
【核心考点】 缺陷管理 Bug生命周期
【题目解析】
本题考查软件测试中缺陷管理的基础知识。Bug生命周期描述了缺陷从发现到关闭的完整过程，是测试流程管理的重要组成部分。
【参考答案要点】
Bug生命周期通常包含以下状态和流转过程：
1. 新建（New）：测试人员发现并提交Bug，状态为“新建”。
2. 指派（Assigned）：开发经理将Bug指派给对应的开发人员处理。
3. 已解决（Resolved）：开发人员修复Bug后，将状态改为“已解决”。

【易错提示】
注意区分“已解决”和“已关闭”状态，前者表示修复完成但待验证，后者表示验证通过。另外，不同团队可能对状态定义略有差异，但核心流程一致。
```

## Q001128

- 题型：简答
- 难度：简单

**题目**

```text
什么是严重性？
```

**答案**

```text
错误对被测系统的影响程度，在终端用户条件下发生的可能性，软件错误妨碍系统使用的程度
```

**解析**

```text
【核心考点】 缺陷管理 严重性定义
【参考答案要点】
严重性（Severity）是衡量软件缺陷对系统影响程度的指标，通常从以下三个维度评估：
1. 错误对被测系统的影响程度：例如功能完全失效、数据丢失、系统崩溃等属于高严重性；界面错位、提示不友好等属于低严重性。
2. 在终端用户条件下发生的可能性：即缺陷被触发的概率。高可能性意味着用户容易遇到该问题，即使影响小也可能需要优先修复。
3. 软件错误妨碍系统使用的程度：指缺陷是否导致用户无法完成核心业务。例如登录失败会完全妨碍使用，而页面样式问题可能只是轻微影响。
【面试角度】
回答时需注意区分严重性与优先级。严重性由测试人员评估，优先级由项目经理或开发团队决定。例如，一个严重性高但发生概率低的缺陷，优先级可能较低。结合项目实例说明能提升答案质量。
【延伸知识】
常见的严重性分级（如P1-P5或Critical/Major/Minor/Trivial）在不同公司可能不同，但核心思想一致。ISTQB中严重性通常与功能、性能、安全性等维度关联。
```

**题目**

```text
什么是软件缺陷？表现形式有哪些？
```

**答案**

```text
从产品内部看，软件缺陷是软件产品开发或维护过程中所存在的错误、毛病等各种问题；从外部看，软件缺陷是系统所需实现的某种功能的失效或违背。 它的表现形式主要有以下几种：
（1）软件未达到产品说明书中已经标明的功能；
（2）软件出现了产品说明书中指明不会出现的错误；
（3）软件未达到产品说明书中虽未指出但应当达到的目标；
（4）软件功能超出了产品说明书中指出的范围；
（5）软件测试人员认为软件难以理解、不易使用，或者最终用户认为该软件使用效果不良。
```

**解析**

```text
【核心考点】 软件缺陷定义 缺陷表现形式 基础概念
【题目解析】
本题考察软件缺陷的基本概念和常见表现形式。软件缺陷是测试领域的核心概念，理解其定义有助于准确识别和报告问题。
【参考答案要点】
1. 定义：从产品内部看，软件缺陷是开发或维护过程中存在的错误、毛病等问题；从外部看，是系统所需功能的失效或违背。
2. 表现形式：
- 功能未达到说明书标明的功能。
- 出现了说明书指明不会出现的错误。
- 未达到说明书虽未指出但应当达到的目标。
- 功能超出了说明书指出的范围。
- 测试人员或用户认为难以理解、不易使用，即可用性问题。
【易错提示】
注意缺陷不仅包括功能错误，还包括性能、安全、可用性等方面的问题。面试时建议结合实际项目中的缺陷案例说明，如“某次因未处理边界值导致系统崩溃”。
【面试角度】
```

```text
唯一性。一个bug说明一个问题或者说明一类问题可重现。
提供这个bug的精确步骤，要让开发人员容易看懂一致性。
Bug描述及所有信息要前后一致，不可有歧义完整性。

提高质量的做法：
能附带bug现象截图的就带截图，有报错日志的就贴上日志信息客观性。Bug描述不要带有个人观点，不要对开发人员进行评价，对事不对人
```

**解析**

```text
【核心考点】 缺陷报告 Bug管理
【题目解析】
本题考察如何编写高质量的缺陷报告。好的Bug报告应清晰、完整、可复现，帮助开发人员快速定位问题。核心要素包括标题、模块、版本、严重级别、详细步骤和附件。

- 可复现：提供精确步骤，开发可重现。
```

## Q001146

- 题型：简答
- 难度：简单

**题目**

```text
你们线上bug都怎么处理的？
```

**答案**

```text
我们是收集客户反馈的bug,由我们客服人员记录下bug产生的详细步骤，然后我们复线这个bug，然后开发去修复；
然后如果发现是我们用例里缺失的部分 需要加到我们的用例库里进行完善和补充。
```

**解析**

```text
【核心考点】 缺陷管理 线上问题处理
【题目解析】
线上bug处理流程是测试工程师的基本功，通常包括：收集反馈、复现问题、提交缺陷、开发修复、回归验证、补充用例。重点是确保问题闭环，并持续改进测试用例库。
【参考答案要点】
1. 收集反馈：客服人员记录用户反馈的bug，包括详细步骤、环境、截图等。

5. 补充用例：如果发现是测试用例缺失导致的漏测，需补充到用例库中。
【易错提示】
```

```text
5. 非紧急Bug：可记录到缺陷库，纳入下一迭代修复。
【面试角度】
建议结合实际项目经历举例，例如“我们曾遇到支付Bug，立即回滚版本并修复后重新上线”。
【易错提示】
不要忽略沟通环节，线上问题处理中与客户、开发、运维的协作至关重要。
```

## Q001184

- 题型：简答
- 难度：简单

**题目**

```text
在软件工程或软件测试中，哪些软件问题被称为软件缺陷？
```

**答案**

```text
按照软件缺陷的产生原因，可以将其划分为不同的缺陷类别：
1、功能不正常
简单地说就是所应提供的功能，在使用上并不符合产品设计规格说明书中规定的要求，或是根本无法使用。这个错误常常会发生在测试过程的初期和中期，有许多在设计规格说明书中规定的功能无法运行，或是运行结果达不到预期设计。最明显的例子就是在用户接口上所提供的选项及动作，使用者操作后毫无反应。

2、软件在使用上感觉不方便
只要是不知如何使用或难以使用的软件，在产品设计上一定是出了问题。所谓好用的软件，就是使用上尽量方便，使用户易于操作。如微软推出的软件，在用户接口及使用操作上确实是下了一番功夫。有许多软件公司推出的软件产品，在彼此的接口上完全不同，这样其实只会增加使用者的学习难度，另一方面也凸显了这些软件公司的集成能力不足。

3、软件的结构未做良好规划
这里主要指软件是以自顶向下方式开发，还是以自底向上方式开发。如果是以自顶向下的结构或方法开发的软件，在功能的规划及组织上比较完整，相反以自底向上的组合式方法开发处的软件则功能较为分散，容易出现缺陷。

4、提供的功能不充分
这个问题与功能不正常不同，这里指的是软件提供的功能在运作上正常，但对于使用者而言却不完整。即使软件的功能运作结果符合设计规格的要求，系统测试人员在测试结果的判断上，也必须从使用者的角度进行思考，这就是所谓的“从用户体验出发”。

5、与软件操作者的互动不良
一个好的软件必须与操作者之间可以实现正常互动。在操作者使用软件的过程中，软件必须很好地响应。例如在浏览网页时，如果操作者在某一网页填写信息，但是输入的信息不足或有误。当点击“确定”按钮后，网页此时提示操作者输入信息有误，却并未指出错误的哪里，操作者只好回到上一页重新填写，或直接放弃离开。这个问题就是典型的在软件对操作互动方面未做完整的设计。

6、使用性能不佳
被测软件功能正常，但使用性能不佳，这也是一个问题。此类缺陷通常是由于开发人员采用了错误的解决方案，或使用了不恰当的算法导致的，在实际测试中有很多缺陷都是因为采用了错误的解决方法，需要加以注意！

7、为做好错误处理
软件除了避免出错之外，还要做好错误处理，许多软件之所以会产生错误，就是因为程序本身对于错误和异常处理的缺失。例如被测软件读取外部的信息文件并已做了一些分类整理，但刚好所读取的外部信息文件内容已被损毁。当程序读取这个损毁的信息文件时，程序发现问题，此时操作系统不知该如何处理这个情况，为保护系统自身只好中断程序。由此可见设立错误和异常处理机制的重要性！

8、边界错误
缓冲区溢出问题在这几年已成为网络攻击的常用方式，而这个缺陷就属于边界错误的一种。简单来说，程序本身无法处理超越边界所导致的错误。而这个问题，除了编程语言所提供的函数有问题之外，很多情况下是由于开发人员在声明变量或使用边界范围时不小心引起的。

9、计算错误
只要是计算机程序，就必定包括数学计算。软件之所以会出现计算错误，大部分出错的原因是由于采用了错误的数学运算工时或未将累加器初始化为0.

10、使用一段时间所产生的错误
这类问题是程序开始运行正常，但运行一段时间后却出现了故障。最典型的例子就是数据库的查找功能。某些软件在刚开始使用时，所提供的信息查找功能运作良好，但在使用一段时间后发现，进行信息查找所需的时间越来越长。经分析查明，程序采用的信息查找方式是顺序查找，随着数据库信息的增加，查找时间自然会变长。这就需要改变解决方案了！

11、控制流程的错误
控制流程的好坏，在于开发人员对软件开发的态度及程序设计是否严谨。软件在状态间的转变是否合理，要依据业务流程进行控制。例如，用软件安装程序解释这类问题最方便直观。用户在进行软件安装时，输入用户名和一些信息后，软件就直接进行了安装，未提示用户变更安装路径、目的地等。这就是软件控制流程不完整导致的错误问题。

12、在大数据量压力下所产生的错误
程序在处于大数据量状态下运行出现问题，就属于这类软件错误。大数据量压力测试对于Server级的软件是必须进行的一项测试，因为服务器级的软件对稳定性的要求远比其它软件要高。通常连续的大数据量压力测试是必须实施的，如让程序处理超过10万笔数据信息，再来观察程序运行的结果。

13、在不同硬件环境下产生的错误
这类问题的产生与硬件环境的不同相关。如果软件与硬件设备有直接关系，这样的问题就是数量相当多。例如有些软件在特殊品牌的服务器上运行就会出错，这是由于不同的Server内部硬件了不同的处理机制。

14、版本控制不良导致的错误
出现这样的问题属于项目管理的疏忽，当然测试人员未能尽忠职守也是原因之一。例如一个软件被反映有安全上的漏洞，后来软件公司也很快将修复版本提供给用户。但在一年后他们推出新版本时，却忘记将这个已解决的bug-fix加入到新版本中。所以对用户来说，原本的问题已经解决了，但想不到新版本升级之后，问题又出现了。这就是由于版本控制问题，导致不同基线的merge出现误差，使得产品质量也出现了偏差。

15、软件文档的错误
最后这类缺陷是软件文档错误。这里所提及的错误，除了软件所附带的使用手册、说明文档及其它相关的软件文档内容错误之外，还包括软件使用接口上的错误文字和错误用语、产品需求设计PD、UI Spec等的错误。错误的软件文档内容除了降低产品质量外，最主要的问题是会误导用户！
```

**解析**

```text
【核心考点】 软件缺陷定义 缺陷分类
【题目解析】
本题考察软件缺陷的基本概念。软件缺陷不仅包括功能错误，还涵盖可用性、性能、安全性等方面的问题。根据ISTQB定义，缺陷是软件中导致无法满足用户需求或规格说明的问题。
【参考答案要点】
1. 功能不正常：软件功能未按规格说明实现，如按钮无响应、计算结果错误。
2. 使用不便：用户界面设计不合理，导致操作困难或易出错，如缺少提示、流程繁琐。
3. 性能问题：响应时间过长、资源消耗过高，影响用户体验。
4. 安全性漏洞：存在数据泄露、未授权访问等风险。
5. 兼容性问题：在不同操作系统、浏览器或设备上表现不一致。
【面试角度】
回答时建议结合实际项目中的缺陷案例，如“在电商项目中，支付按钮在特定浏览器下无响应，属于功能缺陷”，体现对缺陷的全面理解。
【延伸知识】
缺陷管理流程包括：发现→提交→评审→分配→修复→验证→关闭。了解不同严重级别（致命、严重、一般、轻微）有助于面试中深入讨论。
```

## Q001246

**题目**

```text
提交BUG的流程
```

**答案**

```text
1、提交
刚刚提交的BUG为打开状态

2、分配/认领/确认
开发看到BUG，如果确认不是自己的工作范围，可能会指派给其它人，指派后确认是有效BUG，一般需要确认

已经解决的，指派给BUG提交者。确定是无效BUG的话，一般予以驳回，延期和待定一般是一个意思，就是暂时不予修改，延期的BUG需要产品经理确认。最后挂在开发人员的名下。

4、重启/验证
已经解决或者驳回的BUG需要测试进行验证或者确认。如果没有修复成功的BUG需要重启再指派回开发者。

5、关闭/取消
已经验证通过或者确认是无效的BUG，需要关闭。如果测试在开发认领之前发现BUG无效，则可以主动取消。
```

**解析**

```text
【核心考点】 缺陷管理 测试流程
【题目解析】
本题考查BUG提交后的标准处理流程，涉及测试与开发的协作。需清晰描述各阶段状态转换，体现对缺陷生命周期的理解。
【参考答案要点】
1. 提交：测试人员提交BUG，状态为“打开”。
2. 分配/认领/确认：开发人员确认BUG有效后，分配给自己或指派给他人，状态变为“已确认”。
3. 解决/驳回/延期：开发修复后状态为“已解决”；若无效则“驳回”；若暂不处理则“延期”（需产品经理确认）。
4. 重启/验证：测试验证修复是否成功，成功则“关闭”，失败则“重启”并重新指派。
5. 关闭/取消：验证通过后关闭BUG；若测试发现无效可主动取消。

回答时可结合常用工具（如JIRA、Bugzilla）说明状态流转，并强调沟通的重要性，例如“在驳回时需提供详细理由，避免测试与开发冲突”。
【延伸知识】
高级流程包括：引入“回归测试”阶段，确保修复不引入新缺陷；使用“严重程度”和“优先级”字段辅助排序。了解这些可体现对缺陷管理的全面认识。
```

## Q001077

- 题型：简答
- 难度：中等

**题目**

```text
BUG管理工具的跟踪过程(用BugZilla为例子)
```

**答案**

```text
测试人员发现了BUG，提交到Bugzilla中，状态为new，BUG的接受者为开发接口人员

开发接口将BUG分配给相关的模块的开发人员，状态修改为已分配，开发人员和测试确认BUG，如果是本人的BUG，则设置为接收;如果是别的开发人员的问题，则转发出去，由下一个开发人员来进行此行为;如果认为不是问题，则需要大家讨论并确认后，拒绝这个BUG，然后测试人员关闭此问题。

如果开发人员接受了BUG，并修改好以后，将BUG状态修改为已修复，并告知测试在哪个版本中可以测试。

测试人员在新版本中测试，如果发现问题依然存在，则拒绝验证;如果已经修复，则关闭BUG。
```

**解析**

```text
【核心考点】 缺陷管理流程 Bugzilla工具
【题目解析】
本题考查Bugzilla中缺陷的生命周期管理流程。Bugzilla是常用的开源缺陷跟踪工具，其状态流转包括New、Assigned、Accepted、Resolved、Closed、Reopened等。理解状态转换和责任人角色是测试工程师的基本功。

1. 提交阶段：测试人员发现BUG后提交到Bugzilla，状态为New，分配给开发接口人员。
2. 分配阶段：开发接口人员将BUG分配给相关模块开发人员，状态修改为Assigned。
3. 确认阶段：开发人员确认是否本人BUG，若是则状态改为Accepted；否则转发给其他开发；若认为非问题则讨论后Rejected，测试人员关闭。
```

## Q001079

- 题型：简答
- 难度：中等

**题目**

```text
Bug 优先级和严重程度如何划分？
```

**答案**

```text
Priority(优先级)和 Severity(严重程度)是提交 bug 的两个重要属性。
通常，测试 人员在提交 Bug 时，只定义 Bug 的 Severity, 即该 Bug 的严重程度，而将 Priority
交给 Project Leader 或 Team Leader 来定义，由他们来决定该 Bug 被修复的优先等级。某种
意义上来说，Priority 的定义要依赖于 Severity，在大多数情况下，Severity 越严重，那这个
Bug 的 Priority 就越高。
Severity（严重程度）如下：
Blocker（有妨碍的）: 即系统无法执行、崩溃或严重资源不足、应用模块无法启动或异
常退出、无法测试、造成系统不稳定
Critical（紧要的）：即影响系统功能或操作，主要功能存在严重缺陷，但不会影响到系
统稳定性
Major（严重的）：即界面、性能缺陷、兼容性。
Minor/Trivial（次要的/不严重的）:即易用性及建议性问题。
Priority（优先级）：Immediate（立刻）、Urgent（紧要、优先）、High（高度重视）、
Normal（正常）、Low（稍缓）
```

**解析**

```text
【核心考点】 缺陷管理 Bug优先级 Bug严重程度
【题目解析】
本题考查Bug管理中的两个核心属性：优先级（Priority）和严重程度（Severity）。两者相关但不同，严重程度定义缺陷对系统的影响，优先级定义修复的紧迫性。通常测试人员定义严重程度，项目经理或团队领导定义优先级。
【参考答案要点】
Severity（严重程度）划分：
• Blocker（阻塞）：系统无法执行、崩溃、严重资源不足，导致无法继续测试。
• Critical（严重）：主要功能失效、数据丢失、安全漏洞。
• Major（主要）：功能部分失效，但可绕过。
• Minor（次要）：界面问题、非关键功能异常。
• Trivial（轻微）：拼写错误、格式问题。

Priority（优先级）划分：
• P1（最高）：立即修复，阻塞发布。
• P2（高）：尽快修复，影响核心功能。
• P3（中）：在发布前修复。
• P4（低）：可延期修复。

通常严重程度越高，优先级也越高，但并非绝对。例如，界面拼写错误（Severity低）但出现在首页（Priority高）。
【面试角度】
回答时建议结合实际案例，例如“在项目中，一个登录按钮错位（Minor）但影响用户体验，我们将其优先级设为P2”，能体现对业务影响的理解。
【延伸知识】
面试中常问：Severity和Priority哪个更重要？答案取决于上下文，但通常Severity是客观的，Priority是主观的，需根据项目需求平衡。
```

```text
第一，测试用例覆盖不全面，尤其用户不可控的使用场景，导致出现漏测。 解决方案：优化测试用例，增加用例评审。
```

```text
【题目解析】

【参考答案要点】
1. 快速响应与定位：第一时间配合开发重现bug，确认影响范围。
2. 分级处理：严重bug立即修复并更新版本；非严重bug可放入下个迭代。
```

## Q001144

```text
3）所有发现的缺陷（不管是测试发现的还是走读代码发现的）都必须全部即时的、准确的提交到缺陷管理工具中，这是缺陷提交的管理。

5）为了更好的改进开发过程和测试过程，需要对缺陷进行分析，总结如缺陷的类别、缺陷的龄期分布等信息，这是缺陷分析的管理。
```

```text
【核心考点】 缺陷管理 缺陷生命周期 管理流程

【参考答案要点】
1. 工具引入：使用缺陷管理工具（如Jira、Bugzilla、禅道等）进行统一管理。

3. 及时准确提交：所有发现的缺陷必须即时、准确地提交到管理工具中，确保信息完整（如步骤、环境、截图等）。
```
