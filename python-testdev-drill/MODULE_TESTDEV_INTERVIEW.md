# 测试开发面试题（上海中小厂 25K 定向版）

> 定位：中小厂测开/自动化测试岗。面试官多为测试主管，重实战、重项目落地、重"你能不能干活"。
> 三大套路题：项目介绍、场景排查、框架设计。答案口语化，30-60 秒说完。

### 1. 自我介绍怎么说（测开版）
- tags: 面试套路, 自我介绍
- difficulty: easy
- frequency: 必考
- prompt: 面测开岗，自我介绍应该怎么组织？
- answer: 三段式：①2 年/3 年经验+技术栈一句话（Python+Pytest+Requests+Selenium/Playwright，做过接口和 UI 自动化，熟悉 Jenkins 持续集成）；②挑一个最有含金量的项目讲数字化成果（自动化覆盖 300+ 接口、回归时间从 2 天缩到 2 小时、发现过什么线上级 bug）；③一句话表达求职动机。不要背简历，控制在 1 分钟内。

### 2. 介绍一个你最有代表性的自动化项目（STAR 法则）
- tags: 项目介绍, 高频
- difficulty: medium
- frequency: 必考
- prompt: 让你介绍自动化测试项目，怎么讲最有说服力？
- answer: 用 STAR：背景（S）-回归全靠手工，一轮 3 人天；目标（T）-核心链路自动化；行动（A）-我负责什么：框架选型 Pytest+Allure，分层设计（API 层/用例层/数据层分离），数据驱动 YAML，接 Jenkins 每日构建；结果（R）-数字化：覆盖 XX 条用例，回归缩到 X 小时，发现 X 个缺陷。关键：讲"我做了什么"而不是"我们团队"，每一步都有数字。

### 3. 你们的自动化框架是什么结构（分层设计）
- tags: 框架设计, 高频
- difficulty: medium
- frequency: 必考
- prompt: 说说你们自动化框架的分层结构？
- answer: 五层：①基础层：封装 requests（Session 复用、统一日志、Token 自动注入）；②业务层：按模块封装 API 对象（如 LoginApi、OrderApi）；③用例层：Pytest 测试用例，只写业务流程和断言；④数据层：YAML/Excel 数据驱动，参数化；⑤报告层：Allure+Jenkins 集成+飞书通知。一句总结：用例和代码分离、数据和用例分离，改业务不用改用例。

### 4. 自动化发现过什么有价值的 bug（最有价值的问题）
- tags: 项目深挖, 高频
- difficulty: medium
- frequency: 必考
- prompt: 面试官问"自动化测试发现过什么印象深刻的 bug"，怎么回答？
- answer: 提前准备 1-2 个真实故事，结构：场景-现象-排查过程-根因-价值。比如：压测后发现接口偶发返回 500，自动化持续回归脚本捕捉到 0.3% 失败率，追查发现是数据库连接池未释放导致泄漏，高峰期耗尽连接。价值句：自动化不只能验功能，还能发现人手工测不出的概率性问题。切忌说"我们自动化没发现过 bug"。

### 5. UI 自动化和接口自动化怎么取舍
- tags: 测试策略, 高频
- difficulty: easy
- frequency: 必考
- prompt: 资源有限，UI 和接口自动化怎么分配？为什么？
- answer: 接口为主 UI 为辅，比例大概 7:3。理由：接口执行快（秒级 vs 分钟级）、稳定（不受前端渲染影响）、能覆盖大部分业务逻辑；UI 只留核心端到端链路（登录-下单-支付）。中小厂更看重性价比，接口自动化投入产出比最高。UI 全覆盖是伪需求，改一个页面控件全崩。

### 6. 元素定位不稳定怎么办（flaky 定位问题）
- tags: Selenium, UI自动化, 高频
- difficulty: medium
- frequency: 必考
- prompt: UI 自动化经常因为元素定位不到而失败，怎么解决？
- answer: 四步：①优先级换定位方式：id > 语义化 css > xpath，绝不依赖动态 class 或绝对路径；②显式等待替代 sleep：WebDriverWait+expected_conditions，等元素可点击再操作；③换帧/换窗口处理：iframe 切换、弹窗拦截先关掉；④兜底重试：封装 click 重试（失败重新定位再点）。一句总结：80% 的不稳定来自定位方式和等待策略，不是网络。

### 7. 显示等待、隐式等待、强制等待的区别
- tags: Selenium, 等待策略, 高频
- difficulty: easy
- frequency: 必考
- prompt: Selenium 三种等待的区别？你用哪种？
- answer: 强制等待 sleep(3)：写死等 3 秒，浪费且不可靠；隐式等待 implicitly_wait：全局设一次，找不到元素等 N 秒，但只能判断"存在"，不能判断"可点击"，且影响全局速度；显式等待 WebDriverWait：针对单个元素等特定条件（可见/可点击/消失），最精准。项目实践：显式为主+极少数场景 sleep 兜底，绝不用隐式（和显式混用会叠加等待时间，且行为难预测）。

### 8. 怎么做接口测试（不依赖文档怎么测）
- tags: 接口测试, 高频
- difficulty: medium
- frequency: 必考
- prompt: 给你一个没有任何文档的接口，你怎么测试它？
- answer: 先抓包（F12/Charles 看请求结构）→ 再看代码（FastAPI/Flask 路由和参数校验逻辑）→ 然后按套路测：正常参数、必填参数缺失、类型错误、边界值（长度/大小/空串）、鉴权失败（无 token/过期/伪造）、幂等重复提交、并发。再补数据库验证：接口返回成功后数据有没有正确落库。中小厂特别爱问这个，考察独立测试能力。

### 9. 接口间的依赖怎么处理（token/上下文传递）
- tags: 接口自动化, 依赖管理, 高频
- difficulty: medium
- frequency: 必考
- prompt: 接口自动化中登录后的 token 怎么传给后面的用例？
- answer: 三种方案：①fixture：写一个 autouse 或 session 级 fixture，登录拿 token 后返回/写入全局对象，后续用例直接引用（最常用）；②全局变量/上下文管理器：维护一个 context dict，登录后存 token，请求封装层自动从 context 取并塞进 header；③缓存中间件：token 存 Redis，跨进程共享（并发场景用）。要能说清为什么用 session 级 fixture：登录一次全部用例复用，省时间又贴近真实会话。

### 10. 自动化用例怎么设计才算好的用例
- tags: 用例设计, 高频
- difficulty: medium
- frequency: 必考
- prompt: 自动化用例和手工用例设计上有什么不同？
- answer: 三个原则：①选稳定的测：需求频繁变的、一次性的不进自动化，优先核心回归路径；②独立可重复：用例不依赖执行顺序、不依赖其他用例的残留数据，每条用例自造数据自清理；③断言完整：不只断 status code，要断业务 code、关键字段、数据库落库结果。反面教材：一条用例从头测到尾塞 20 个步骤，任何一环挂了都不知道哪里的问题。

### 11. 你们的自动化跑在什么时候（CI 集成方式）
- tags: CI/CD, Jenkins, 高频
- difficulty: easy
- frequency: 高频
- prompt: 自动化测试什么时候触发执行？怎么和 Jenkins 集成？
- answer: 两个触发点：①研发提交代码/MR 合并时跑冒烟用例（-m smoke，只跑 50 条核心链路，5 分钟内出结果，失败阻断合并）；②每日凌晨定时跑全量回归，早上上班看 Allure 报告，失败推送飞书群 @责任人。Jenkins 配置：Pipeline 拉代码→装依赖→pytest 命令→Allure 插件出报告。强调分层：门禁要快要稳，全量要全要深。

### 12. 数据库校验在自动化里怎么做的
- tags: SQL, 数据校验, 高频
- difficulty: medium
- frequency: 高频
- prompt: 接口自动化怎么验证数据真的写进数据库了？
- answer: 用 pymysql 封装一个 DBUtil（连接池+query/execute 方法），在用例里三步走：前置造数据（INSERT 测试记录或调业务接口）、执行被测接口、后置 SQL 查库断言（SELECT 结果和接口返回比对+清理数据）。高频考点：断言不只看接口返回"成功"，更要查库确认状态流转、金额计算这些核心字段对不对。面试官爱追问 SQL 功底，left join/索引/慢查询要能接得住。

### 13. 不会代码的测试人员怎么用你的框架（框架易用性）
- tags: 框架设计, 加分
- difficulty: medium
- frequency: 中高频
- prompt: 你怎么让功能测试同学也能用你的自动化框架？
- answer: 关键词：数据驱动+降低门槛。用例写成 YAML/Excel，功能同学只填"接口+参数+断言"三要素，不碰 Python 代码；框架解析 YAML 自动生成 Pytest 参数化用例；再加一套简单的命令行或 Web 入口（选环境、选用例集、跑完出报告）。中小厂团队小，面试官很看重你能不能让整套东西"赋能团队"而不是只有你自己会用。

### 14. 遇到的最大的技术难点是什么
- tags: 项目深挖, 高频
- difficulty: medium
- frequency: 高频
- prompt: 面试官问"项目中最大的技术挑战"，怎么回答？
- answer: 准备一个真实+有技术含量+已解决的故事。模板：现象（并发跑 CI 时用例批量失败）→ 排查（日志发现测试数据互踩：多个进程用同一账号互相顶下线）→ 解决（数据隔离方案：按进程号切分测试账号+fixture 动态分配）→ 沉淀（封装成通用并发数据隔离器）。切忌说"没遇到什么难点"，也别说"环境总是不稳定"这种无解的抱怨型答案。

### 15. 为什么离职/为什么选择测开方向
- tags: 面试套路, 必考
- difficulty: easy
- frequency: 必考
- prompt: 中小厂必问的软性问题怎么答？
- answer: 离职原因公式：客观原因+不贬低前公司+发展方向。例：现公司测试以手工为主，我希望往技术深度走，贵司的自动化建设阶段正是我能发挥的价值点。反向提问环节准备 2-3 个问题：团队自动化覆盖率现状、测开在团队里的定位（偏工具开发还是偏质量保障）、入职后前三个月的期望。中小厂特别看重"来了就能干活、能独当一面"。
